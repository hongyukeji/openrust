# Request Lifecycle

The Tokio entry point passes `bootstrap::create_application` to `openrust::foundation::run_application`. The framework selects the entry point before creating the application. With no arguments it calls `Application::start()` for HTTP. With `artisan` as the first argument it calls [`Application::handle_command`](../digging-deeper/artisan.md).

The application entry declares its root as `base_path` and passes it to `Application::configure(base_path)`, matching `configure(base_path: ...)`. It then calls `create()` to validate the root and create the service container. The selected kernel boots the application. Boot loads environment variables and configuration, runs every eager provider’s `register` before their `boot` hooks, and registers shared routes. Process environment variables take precedence over the environment file.

An absolute `APP_BASE_PATH` in the process environment takes precedence. Otherwise, source builds use the application crate directory recorded at build time, including when you run `cargo run --release`. Builds with the `standalone` feature use the executable’s directory as the application root. HTTP and Artisan both read `.env` from the selected root, regardless of the working directory.

Build with `cargo build --release --locked --features standalone` and place `target/release/main` (`target/release/main.exe` on Windows) in the deployment root. Include `resources/views/welcome.blade.html` at that relative path. The deployment directory can then be moved as a unit. For a deployment that keeps the executable outside the application root, set `APP_BASE_PATH` to that root’s absolute path. Include the contents of `public/` at the same relative path. With the default public disk mount, include any public storage files under `storage/app/public/` or at the configured location.

The HTTP kernel configures middleware when it is created and resolves each route’s middleware stack after boot. It completes both steps before binding the listener. The Console Kernel boots the same application and then registers commands.

The HTTP kernel runs [middleware](../the-basics/middleware.md) and dispatches the request through the framework [router](../the-basics/routing.md). `GET /` redirects to the destination set by `app.home_path` in `config/app.rs`. Set `APP_HOME_PATH` to a destination accepted by `Redirect::to`, such as a path or an absolute HTTP(S) URL. An unset or blank value sends requests to `/index.html`, which can be served from `public/index.html`. The example environment file selects `/welcome`. The redirect appends the request query string after any configured query and before any fragment. A fragment-only destination uses the current URL. At `/welcome`, `WelcomeController::index` calls `view("welcome")`. The framework resolves the name to `resources/views/welcome.blade.html` in the application root and reads it at request time. The Blade view reads the application name and version with `config()` and the current application language with `app()->currentLocale()`, without repeating these values as controller data. Editing the HTML takes effect on the next request. The skeleton also exposes the health check at `/up`.

The default application loads Web routes, console routes and the health path through `with_routing` in `bootstrap/app.rs`. Web routes use the [default Web middleware group](../the-basics/middleware.md). Console routes are registered after the Console Kernel boots. API, broadcasting and gRPC have separate optional registration paths. The `/up` handler returns `200 OK` after the application boots.

When routing or middleware returns an HTTP error, the kernel applies the [exception rendering policy](../the-basics/errors.md#rendering-exceptions-as-json) declared in `bootstrap/app.rs`.

Deferred providers are loaded by first service resolution. The Console Kernel loads all remaining deferred providers before command registration; the HTTP kernel leaves unused providers deferred. See [deferred providers](providers.md#deferred-providers) for ordering and asynchronous resolution.

## Request completion events {#request-handled}

After middleware completes or an exception is rendered, the HTTP kernel dispatches `openrust::foundation::http::events::RequestHandled` in the application scope. Register listeners through the existing `Event::listen` or `Event::listen_class` API using `OpenRust\Foundation\Http\Events\RequestHandled`. The event contains `request` and `response` metadata (`RequestParts` / `ResponseParts`), a detached `attributes` map, `route_name`, and a monotonic `duration: Duration`. `response_content` contains shared bytes when a response was already buffered by JSON/text construction or `Response::set_content`; `Response::get_content` exposes that known content. Opaque bodies and streams yield `None`. Observation does not read or buffer a body: streamed responses remain streamed. The event observes response generation, before transport sends the body; it does not measure completed downloads. A cancelled request that has not produced a response does not emit it.

`RequestHandled.request_started_at` is the request start time in Unix milliseconds (`i64`), captured before middleware and error rendering. Its `duration` uses a monotonic clock; use the start timestamp directly for time-window membership.
