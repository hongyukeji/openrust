# Mail

## Generating mailables {#generating-mailables}

Use Artisan to generate a Rust mailable. Use `--view` to generate a Blade template as well, and `--test` for a matching feature test.

```sh
./artisan make:mail OrderShipped
./artisan make:mail Billing/InvoiceReady --view=mail.billing.invoice --test
```

In a terminal, run `./artisan make:mail` without a name to enter the type name and choose a Markdown view, an empty Blade view, or no view. If you pass options, Artisan only asks for the name. With `--no-interaction` or piped input, provide the name explicitly.

The command writes the type under `app/mail` using snake_case files and module directories. Declare the generated module in its parent `mod.rs` before building. The default template name starts with `mail.`, followed by the kebab-case name components. Use `--force` to replace the generated Rust source while keeping any existing view. Application overrides for the source stubs live under `stubs/`.

## Sending mail

Implement `Mailable` with an envelope and content. `Mail::to` adds recipients before sending. Select a named mailer with `Mail::mailer(Some("smtp"))` or override `Mailable::mailer`.

```rust
use openrust::{
    mail::{MailResult, Mailable, mailables::{Content, Envelope}},
    support::facades::Mail,
};

pub struct OrderShipped;

impl Mailable for OrderShipped {
    fn envelope(&self) -> MailResult<Envelope> {
        Ok(Envelope { subject: "Order shipped".into(), ..Envelope::default() })
    }

    fn content(&self) -> MailResult<Content> {
        Ok(Content { text: Some("Your order is on its way.".into()), ..Content::default() })
    }
}

pub async fn send_order() -> MailResult<()> {
    Mail::to("customer@example.test")?.send(&OrderShipped).await?;
    Ok(())
}
```

`Content` accepts text, HTML, or named views with data. Set `view` and `text_view` for the two MIME alternatives. Use `attachments` for bytes with a filename and MIME type, and `headers` for custom headers. The mailer removes Bcc from the MIME headers and retains those recipients in the transport envelope.

### Attachments {#attachments}

Return attachment sources from `Mailable::attachment_sources`. Use `Attachment::fromPath` for a local file, `fromStorage` for the default disk, `fromStorageDisk` for a named disk, and `fromData` for generated bytes. Set the display name with `r#as` and override the MIME type with `withMime`.

```rust
use openrust::mail::{
    MailResult,
    mailables::{Attachment, AttachmentSource},
};

fn attachment_sources(&self) -> MailResult<Vec<AttachmentSource>> {
    Ok(vec![
        Attachment::fromPath(&self.local_report),
        Attachment::fromStorage("reports/monthly.csv"),
        Attachment::fromStorageDisk("s3", "reports/annual.pdf")
            .r#as("annual-report.pdf")
            .withMime("application/pdf"),
        Attachment::fromData(self.generated_report.clone(), "summary.csv")
            .withMime("text/csv"),
    ])
}
```

File and disk sources default to the file name. S3 uses the object’s content type when present. Local files use type detection with a filename-extension fallback. Generated bytes default to `application/octet-stream`. The mailer resolves file and disk sources when sending, including in a queue worker. A queued attachment therefore needs a path or disk accessible to the worker. Generated bytes are included in the queue payload.

Use `Attachment::fromUploadedFile(&file)` with an uploaded file returned by the HTTP request. It uses the client’s basename and the detected MIME type, falling back to the declared MIME type when detection is unavailable. Uploaded bytes travel with queued mail. Use `Attachment::fromCloudStorage(path)?` to select the disk configured by `filesystems.cloud`. It defaults to `s3`.

Use `Attachment::fromUrl(url)?` for an absolute HTTP or HTTPS URL. The mailer downloads the attachment when sending, including in a queue worker. The URL path supplies the default filename and the response can supply the MIME type. To rename a download or override its type, use `r#as` and `withMime`.

### Inline attachments {#inline-attachments}

Return an `InlineAttachment` from `Mailable::inline_attachments` and use its `cid()` value for the image source. The same Content-ID must be used in the attachment and the view.

```rust
let logo = InlineAttachment::new("logo@example.test", Attachment {
    name: "logo.png".into(),
    mime: "image/png".into(),
    bytes: logo_bytes,
});
let image_src = logo.cid();
```

Pass `image_src` to Blade as `<img src="{{ $image_src }}">` or use it as the destination of a Markdown image. A worker receives the attachment bytes with the job. SMTP and other raw MIME transports send the image alongside the HTML. For a browser preview, matching image sources become data URLs. Postmark, Resend, and Cloudflare preserve the filename and Content-ID through their JSON attachment fields. In Mailgun's form API, the inline part uses the Content-ID as its multipart filename so it matches the HTML. Mailgun's raw MIME mode preserves the original filename.

### Attachable objects {#attachable-objects}

Implement `Attachable` when a domain object is responsible for choosing its attachment. Convert the object with `toMailAttachment()` when returning the mailable’s attachment sources.

```rust
use openrust::{
    contracts::mail::Attachable,
    mail::{MailResult, mailables::{Attachment, AttachmentSource}},
};

struct Report(String);

impl Attachable for Report {
    #[allow(non_snake_case)]
    fn toMailAttachment(&self) -> MailResult<AttachmentSource> {
        Ok(Attachment::fromUrl(&self.0)?.r#as("report.pdf"))
    }
}
```

### Tags and metadata {#tags-and-metadata}

Set `Envelope::tags` and `Envelope::metadata` to group and track a message. Both fields travel with a queued mailable.

```rust
fn envelope(&self) -> MailResult<Envelope> {
    Ok(Envelope {
        subject: "Order shipped".into(),
        tags: vec!["shipment".into()],
        metadata: [("order-id".into(), "R123".into())].into(),
        ..Envelope::default()
    })
}
```

Match these declarations in tests with `assertHasTag` and `assertHasMetadata`. SMTP and raw MIME carry `X-Tag` and `X-Metadata-*` headers. Mailgun’s structured API maps tags to `o:tag` and metadata to `v:*`. Postmark accepts one tag and a metadata map. SES and SES v2 append envelope metadata to the configured provider tags. Resend sends tags as name-value pairs and carries metadata in headers. Cloudflare carries metadata and the last tag in its header map.

### Customizing the message {#customizing-the-message}

Register message customizers on the application’s `MailManager` when its service provider boots. List them in `Envelope::using` in the order they should run. A customizer receives the envelope, headers, and rendered text and HTML in a `MessageDraft` before declared attachments are loaded and delivery events are dispatched. A customizer can also add attachments to the draft.

```rust
manager.registerMessageCustomizer("shipment.tracking", |draft, data| {
    if let Some(code) = data["code"].as_str() {
        draft.headers.text.insert("X-Tracking-Code".into(), code.into());
    }
    Ok(())
})?;
```

```rust
fn envelope(&self) -> MailResult<Envelope> {
    Ok(Envelope {
        subject: "Order shipped".into(),
        using: vec![
            MessageCustomization::new("shipment.tracking", serde_json::json!({"code":"R123"})),
        ],
        ..Envelope::default()
    })
}
```

Queued mail stores the customizer name and JSON data. The worker application registers the same name and runs the customizer on each delivery attempt. A missing customizer or an error stops that attempt. Rendering a mailable for preview uses its original content.

## Configuration

`config/mail.rs` defines the default mailer, named mailers and sender. The skeleton defaults to the `log` transport, which writes the MIME message at debug level. Use `array` to inspect messages in the current application with `Mailer::sent`.

For SMTP, set `MAIL_MAILER=smtp` and configure `MAIL_HOST` and `MAIL_PORT`, or set `MAIL_URL`. The URL overrides the connection fields it supplies. `smtps` uses implicit TLS. `smtp` upgrades with STARTTLS when offered, and credentials require a successful TLS upgrade.

Select `sendmail` to run the program configured by `MAIL_SENDMAIL_PATH`. It supports SMTP over standard I/O with `-bs` and delivery through standard input with `-t`.

Select `ses`, `ses-v2`, `postmark`, `resend`, `mailgun`, or `cloudflare` to deliver through a provider. Configure the corresponding service in `config/services.rs` and select its name with `MAIL_MAILER`.

- SES and SES v2 use AWS credentials or the AWS SDK credential chain. SES v2 accepts mailer options such as `ConfigurationSetName`, `EmailTags`, and `ListManagementOptions`.
- Postmark uses `POSTMARK_TOKEN`, and Resend uses `RESEND_KEY`.
- Mailgun uses `MAILGUN_DOMAIN` and `MAILGUN_SECRET`. Set `MAILGUN_ENDPOINT=api.eu.mailgun.net` for the EU API. The default `https` scheme submits the composed MIME message. To send multipart fields, configure `scheme` as `api`.
- Cloudflare uses `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_KEY`.

In `config/mail.rs`, `failover` keeps the active mailer while it succeeds and switches on failure. `roundrobin` rotates delivery across mailers. Both use the named `mailers` list and skip failed transports during the `retry_after` interval in seconds.

## Markdown mail

Set `Content::markdown` to a named Blade view containing CommonMark. The mailer creates HTML and plain-text alternatives and inlines the theme stylesheet in HTML. The default theme is built in. Set `MAIL_MARKDOWN_THEME=receipt` and place `receipt.css` under `resources/views/vendor/mail/html/themes/` to use an application stylesheet. Use `text_view` to provide your own plain-text alternative.

```rust
let content = Content {
    markdown: Some("markdown-receipt".into()),
    with: [("name".into(), serde_json::json!("Sam"))].into_iter().collect(),
    ..Content::default()
};
```

### Generating Markdown mailables {#generating-markdown-mailables}

Use `--markdown` to generate a Blade template using the mail components. To use the generated type, declare its module and rebuild. When both view options are supplied, the Markdown template is selected.

```sh
./artisan make:mail Orders/ShipmentNotice --markdown=mail.orders.shipment
```

### Write Markdown messages {#writing-markdown-messages}

Wrap a Markdown mail view in `<x-mail::message>`. It uses the application name and URL for the header and includes a footer. Use a named `subcopy` slot for secondary text. Buttons support `url`, `color`, and `align`. Panels render Markdown in their body. The table component renders a Markdown table in HTML and omits it from the generated plain-text alternative.

Use `<x-mail::header url="https://example.com">`, `<x-mail::footer>`, and `<x-mail::subcopy>` for standalone sections. The default message footer uses the application time zone for the year and resolves `All rights reserved.` in the message locale. To translate it, add that key to the locale's JSON translation file.

```blade
<x-mail::message>
# Order ready

<x-mail::button :url="$url" color="success">
Review order
</x-mail::button>

<x-mail::panel>Keep this receipt for your records.</x-mail::panel>

<x-mail::table>
| Item | Qty |
| --- | ---: |
| Book | 1 |
</x-mail::table>

<x-slot:subcopy>Contact support if you have questions.</x-slot:subcopy>
</x-mail::message>
```

Wrap the entire view in `<x-mail::layout>` to choose its sections yourself. The named slots are `head`, `header`, `subcopy`, and `footer`. The `head` slot accepts HTML for the document head and is omitted from plain text.

```blade
<x-mail::layout>
<x-slot:header>
<x-mail::header :url="$url">Orders</x-mail::header>
</x-slot:header>

# Order ready

<x-slot:footer>
<x-mail::footer>Thank you for your order.</x-mail::footer>
</x-slot:footer>
</x-mail::layout>
```

### Customize the Markdown layout {#customizing-the-components}

Publish the HTML and text layouts, component templates, and default stylesheet into `resources/views/vendor/mail`.

```sh
./artisan vendor:publish --tag=laravel-mail
```

Edit `html/layout.blade.html` and `text/layout.blade.html` to add headers, footers, or other wrapping content. Keep `{!! $slot !!}` where the rendered message belongs. Edit `html/themes/default.css` to update the default theme. Roots in `mail.markdown.paths` are resolved relative to the application and are checked in order before the standard published directory. Publishing preserves existing files unless you pass `--force`.

Edit the `header.blade.html`, `footer.blade.html`, and `subcopy.blade.html` templates under `html/` or `text/` to customize those sections. The built-in `message` template uses these same templates.

The published default layout uses `$mail_content` for the assembled content and includes a responsive 570 px message table. With an explicit layout, a custom template can place the body with `$slot` and position `$header`, `$subcopy`, and `$footer` separately.

#### Customize the CSS for one mailable {#customizing-the-css}

Place `receipt.css` in `resources/views/vendor/mail/html/themes/` and return a `Content` with `theme: Some("receipt".into())` from the mailable.

```rust
use openrust::mail::mailables::Content;

let content = Content {
    markdown: Some("mail.receipt".into()),
    theme: Some("receipt".into()),
    ..Content::default()
};
```

The theme applies to the HTML version of this Markdown message, including when a worker delivers it. If the override is absent or empty, the mailer uses the application's Markdown theme. The worker resolves the stylesheet from the application's views and theme directories.

### Markdown extensions and secured encoding {#markdown-extensions-and-encoding}

CommonMark and tables are always available. Set `mail.markdown.extensions` in `config/mail.rs` to a list of supported names. The default list is empty. OpenRust supports `strikethrough`, `task_lists`, `footnotes`, and `smart_punctuation`. An unsupported name causes the mailer to return a configuration error.

Set `mail.markdown.secured_encoding` to `true` to render strings passed through `{{ $value }}` as literal text in the Markdown body. For example, a value containing `[View](https://example.com)` is displayed literally. An authored link can still use a dynamic destination such as `[View]({{ $url }})`. HTML escaping and URL filtering still apply. The default is `false`. The setting applies per application to generated Markdown mail, including the generated text alternative.

## Queueing mail

Return queue options from `Mailable::queue_options` to make `send` enqueue delivery. Use `sendNow` for immediate delivery. `PendingMail::queue` accepts connection, queue, delay and an optional transaction. Enable `after_commit` to defer dispatch until commit. The worker composes named views from the queued definition in the worker application, then sends the message. Use `./artisan queue:work --stop-when-empty` to process queued mail.

## Rendering mailables {#rendering-mailables}

Call `mailable.render().await?` to get the rendered body without sending or queuing mail. Rendering uses the mailable's locale and Markdown theme. It returns HTML when available and falls back to plain text.

### Previewing mailables in the browser {#previewing-mailables-in-the-browser}

Use `toResponse()` in an application route to preview the mailable. It returns HTML or plain text with the corresponding media type.

```rust
use openrust::{
    http::{HttpError, HttpFuture, Request, Response},
    mail::Mailable,
    support::facades::Route,
};

fn preview_order(_: &mut Request) -> HttpFuture<'_, Result<Response, HttpError>> {
    Box::pin(async { OrderShipped.toResponse().await })
}

Route::get("/mail-preview/order", preview_order)?;
```

## Mail transport extensions and events

Register a Rust transport factory with `MailManager::extend` in an application provider. Select it with the mailer’s `transport` config key. The dispatcher emits `MessageSending` before the transport runs and `MessageSent` after the transport accepts the message. A `MessageSending` listener can return `false` to cancel delivery. `send` returns `None` for a cancelled send, and `sendNow` returns `MailError::Cancelled`.

## Testing mail

Call attachment assertions on a mailable to check its declared sources without reading files or contacting storage. Use `assertHasAttachmentFromStorageDisk` to check a specific disk and `assertHasNoAttachments` to check that no regular attachments were declared.

```rust
receipt
    .assertHasAttachmentFromStorage("reports/monthly.csv", None, None)
    .assertHasAttachedData(b"total,42", "summary.csv", Some("text/csv"));
```

Install `Mail::fake()` within the test application to inspect mail without contacting a transport or pushing a queue job. Assertions distinguish immediate mail from queued mail. Use `Mailable::kind()` to select records, and use a matching assertion to inspect the envelope or queue options.

```rust
let mail = Mail::fake()?;
Mail::to("ops@example.test")?.sendNow(&receipt).await?;
mail.assertSentMatching(receipt.kind(), |entry| {
    entry.envelope.to.iter().any(|to| to.address == "ops@example.test")
});
mail.assertNothingQueued();
```
