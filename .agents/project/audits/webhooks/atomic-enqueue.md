# Webhook 接收与同库原子入队

本批处理 WH-03 的同库崩溃窗口。固定 Spatie Client `ff886d1bae33d35ad98b6c91403f280df158129d` 的 Processor 先保存、再派发、然后响应。默认路径维持该顺序与失败诊断。新增 `atomic_database_queue` 是应用可选增强。开启后用同一数据库事务保存两行，任一写入失败时回滚，提交成功后才执行响应。验签与 Profile 仍先于事务，正文解析也在获取事务前完成。

队列复用 QueueManager 的事务派发、事件和原生数据库队列协议。新增严格入口复核事务已打开，队列经核实为内置数据库队列，当前事务及队列使用同一个查询来源。普通派发允许跨连接回退，原子入口禁止这种回退，也不会注册提交后回调。不同名称的两个连接即使指向相同数据库，仍不共享事务。模式不引入额外队列表、不变更接收表或现有任务格式。

应用无法在退出的进程内返回确认。入队前退出、入队后但提交前退出的两阶段使用独立真实 HTTP 进程进行注入，再从另一连接观察收件表和队列表。即使收件和入队都已提交，HTTP 响应仍可能丢失，客户端重试去重、Worker 领取租约与代次、外部队列的提交后恢复及 Scheduler 补偿仍待验收。当前不宣称 WH-03 或双拓扑闭合。

隔离源码基线 `f49e2b67f`，Rust 1.94.0 和项目 build_guard。执行日志在 `target/tmp/webhooks-atomic`。触及项目磁盘阈值时，由守卫在取得锁后清理本项目编译产物并重建。

SQLite、PostgreSQL 18.7、MySQL 8.4.13 各通过 136 个真实 HTTP 请求和 83 次独立 Artisan Worker 运行。三种缓存状态均验证同库写入和读取，队列连接的 after_commit 默认值设为 true，原子入口仍在当前事务写队列。每库核对异连接、null 驱动、缺失队列表各自返回失败且没有新增记录。两个进程退出点分别退出 77、78，随后从外部连接确认收件与队列都没有多出行。旧 SQLite 接收与两种签名 HTTP／Artisan 回归、三语文档编译及文档站构建通过。

全仓格式及两项 Webhook feature 启用后的 workspace/all-targets 严格 Clippy 通过。隔离数据库、临时应用和站点产物已清理，保留验收日志及可复用构建缓存。
