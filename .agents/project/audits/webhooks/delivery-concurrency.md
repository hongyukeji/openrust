# 出站在途投递上限

`DeliveryConcurrencyLimits` 是可选的应用级策略。范围与端点分别设置上限。沿用内容审核远端任务租约以及 Webhook 速率事务的基于数据库方案。已有额度表的独立范围行用于串行取得名额，已有尝试表按可查询的范围、端点和租约时间保存占用。尝试结算后仍保留原来已有的历史语义，已结算行不占额度。跨端点的 SQL 协调只发生在短事务内，网络连接不占用锁事务。 [内容审核账户在途验收](../content-moderation/README.md#account-in-flight)

每次发送以同一领取令牌校验当前记录。获得授权后，在同一事务登记在途名额和速率扣减。容量用尽时回滚扣减，通过现有延期流程释放尚未开始的尝试，留下下次可领时间。具名端点以稳定 ID 计数，范围额度也适用于直接 URL。已完成尝试立即释放容量，进程丢失时等原领取租约过期。短投递截止不会提早释放仍在途的连接。领取完成与历史清理由既有流程处理。

## 验收

SQLite、PostgreSQL 18.7、MySQL 8.4.13 用两个独立节点目录、真实 HTTP、Artisan 迁移、配置／路由缓存及独立 Worker 实测范围上限、端点上限及跨范围隔离。两个节点同时争同一端点名额，只允许一个实际建立 HTTP 连接。占满后仍保留速率与领域尝试预算。完成后已有任务可再领。主动终止 Worker 后，未过期的名额仍占用。隔离库提前推进过期时点后，另一节点继续投递，旧尝试留为 Unknown。短截止的测试比对实际保存名额与领取租约。带未结算记录时拒绝迁移回滚，全部结算后可回滚重跑。另复测原发送速率、普通发送与 SQLite 接收套件。包测试、严格 Clippy、格式和三语站点渲染通过。
