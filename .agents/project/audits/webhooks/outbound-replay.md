# Webhook 出站人工重放

## 决策与边界

原投递的自动重试继续使用同一投递 ID 和尝试预算。人工重放经应用授权后，原子写入独立投递和审计行，并从原快照保留消息 ID、正文和目标。重放按原投递及代次分配稳定 ID，唯一约束阻止两个并发请求登记同一代次。已有活动重放时拒绝继续登记；重放投递本身不能用作新的原始投递。原投递的状态和尝试历史保持可查。此模型借鉴 Svix 分开处理人工和自动重试的做法，代次、预算及权限规则遵循本项目 WD-06。[Svix 重试参考](https://docs.svix.com/retries#manual-retries)

新增 `DeliveryService::replay`、`ReplayPolicy` 和 `webhook-server:replay`。请求权限按实际操作者、范围、端点、操作原因与来源状态核对，生产应用须提供自己的可信身份绑定。`--actor` 是传给应用策略的操作标识。成功项要求显式选择并由策略额外批准。请求与实际尝试都复核操作者授权、当前端点许可和凭据；策略区分申请和尝试阶段，可在申请阶段调用应用限流。包强制单个原投递最多十代、每代最多十次、最长一天，策略可进一步收紧。端点／账号共享配额和通用运维限流待端点管理批次。

策略可登记替换签名凭据的引用。审计表保存原凭据与重放凭据的引用、操作者、原因、代次、来源状态及登记时间。密钥保留在应用的凭据解析中。重放通过现有 Scheduler、Queue／Worker 或显式同步投递路径重新签名和发送。凭据撤销或已登记的批准范围变化会阻止实际传输。接收方仍可按稳定消息 ID 去重。原始正文失效时拒绝登记，重放审计存在时拒绝回滚相应迁移。

## 验收范围

Rust 1.94.0 隔离源码叠加 `eef630f3d` 的 Webhook 实现及本批文件。使用 SQLite、PostgreSQL 18.7、MySQL 8.4.13 的隔离数据库、实际 HTTP、Artisan、恢复扫描和独立 Worker。覆盖跨范围、无策略、操作者与申请限流拒绝、并发代次、活动冲突、保持原历史、实际 HMAC 凭据轮换、发送前撤销和批准的凭据引用变更、独立尝试与截止时间、成功项高权限、正文失效以及迁移保护。出站定时恢复和具名 Job 回归通过，SQLite 接收回归包含 136 个真实 HTTP 请求和 83 次独立 Worker。八个包测试、三语六组编译示例、全仓格式与双特性 workspace/all-targets 严格 Clippy 通过。记录在 `target/tmp/webhooks-outbound-replay/`。

本批覆盖已终结失败及显式获准的成功项。[端点当前许可](endpoints.md)已在后续批次接入。端点级额度、取消后恢复、批量重放、复制为新消息、保留期清理及多主机部署验收仍开放。WH-04／WH-05 仍在推进。
