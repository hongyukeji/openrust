# ADR-001 自有应用内核，基于 axum

- 状态：Accepted
- 日期：2026-10-25

## 背景

早期方案以 Loco 为基础生成项目。核实 Loco 1.2.0：基于 axum + SeaORM 2.0，feature 只有 `db-sqlite` 与 `db-postgres`，队列后端为 Redis / Postgres / SQLite，没有 MySQL 路径。若在 Loco 之上构建，OpenRust 只剩模板层，目录、配置、CLI、认证与错误模型全部由 Loco 决定，无法保证统一的设计风格；支持 MySQL 意味着长期维护 fork。

## 决策

OpenRust 自研应用内核（`Application` / `AppBuilder` / `Plugin` / `AppState` / `Config` / `Error` / 生命周期），直接建立在 `tokio` + `axum` + `tower` 之上，复用成熟 crate 承担 HTTP、ORM、会话、邮件、存储等底层能力。V1 按 Loco、Laravel、Goravel、OpenSpring 的顺序综合评估通用底层；RuoYi 若依、芋道仅作为 V2 现成后台参考，不参与 V1 底层选型。参考框架不作为底层依赖或完整复制目标；OpenRouter 用于后续 AI模型平台的产品能力对标，不属于 V1 框架设计参考。

### 成熟组件优先与 Laravel 式开发体验

OpenRust 以 Laravel 的约定优于配置、一致的能力入口、清晰的扩展契约和顺畅的开发流程为重要设计取向。优先整合优秀第三方组件，由框架建立可见、稳定的项目约定，让开发者直接进入业务开发。参考范围按上述版本分工，版本内顺序保持不变；公共 API 继续按 Rust 类型、trait、所有权和异步语义设计。

- 选型顺序为复用仓库已有能力、整合成熟组件、针对已证实缺口实现最小补充。新增自研实现须说明候选组件、无法满足的具体契约、维护成本和验证方式；不因追求统一风格重写已成熟的协议、ORM、密码算法或发送 SDK。
- 框架负责配置与安全默认值、注册和生命周期、统一错误、必要的公开扩展契约、测试替换、生成器和文档。包装层应减少调用方的整合工作；已有接口可直接复用时提供清楚入口与示例，不逐方法复制第三方 API。
- 组件评估包含维护状态、许可、安全、MSRV、异步资源行为和所需后端兼容性；新增依赖按 `stack.md` 登记。第三方组件支持某能力不等于 OpenRust 已完成集成和验收。
- 普通路径使用合理默认值，差异需求通过公开接口扩展，必要时保留明确的底层接口；统一基础语义，后端特殊能力显式声明，不用弱实现伪装等价保证。
- 扩展必须贯通配置、注册、执行、错误和测试。由独立 consumer 仅使用公开 API 接入并运行，证明无需改核心；不能只凭 trait 存在认定完成，具体领域契约见 [ADR-009](adr-009-extensible-capability-drivers.md)。
- 优雅体验通过实际任务验证：首次启动、增加业务资源、更换驱动、测试、诊断、部署及升级。记录步骤、耗时条件和阻塞点，随功能簇消除无必要的样板与配置，不以代码行数或链式调用数量判断质量。
- 已验证的内核、数据库队列和安全能力继续维护；本决策不自动触发重写或替换依赖。发现契约或维护问题时，按具体功能簇评估并保留回归证据。

### V1 通用底座优先

业务类型和流程具有多样性，V1 优先完成可复用的通用基础能力，减少开发者重复搭建和整合底层的时间；业务差异由应用与可选领域插件承接。V2 复用底座交付现成后台，AI 等领域套件独立排期，不挤占 V1 已确认范围。

- 常见需求开箱即用：从生成、配置到实际运行有完整路径。
- 差异需求容易扩展：公开驱动、接口与合理流程扩展点贯通，无需修改核心。
- 能力组合保持一致：配置、错误、生命周期与测试约定减少跨组件整合工作。
- 生产运行有证据：单机易部署，集群一致性、性能边界和故障恢复实际验收。

在已确认范围内按 `todo.md` 的依赖顺序推进，以完整使用路径、必要配置/步骤、重复样板和排错阻塞评估开发成本；不以业务模块数量或未经测量的性能口号代替交付。

## 影响

- 自研面集中在应用层约定与整合；协议、ORM、密码算法及通用中间件优先复用成熟组件。已按 ADR-003/037 比较并验证的数据库队列继续维护，新增自研部分遵守上述缺口与维护成本判断。
- 需要自行维护项目模板、生成器与文档站。
- 可完全控制双库支持、feature 粒度与公共 API 风格。
- 新功能 Spec 简述组件复用、框架附加价值和外部扩展验收；实际待办及顺序只在 [todo.md](../todo.md) 维护。
- 已批准的 V1 底层补强按 [补齐计划](../plans/v1-foundation-completion.md) 交付；公共签名、组件和版本在实施 Spec 核实，不把已确认范围当作已有实现，也不因此重写已验证能力。
