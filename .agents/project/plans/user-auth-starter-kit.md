## 目标与架构

交付可选安装的完整版用户认证入门套件，复用 Fortify、Sanctum、Auth、Session、CSRF、Hash、验证器、密码代理、签名链接、通知、限流和 ApiResponse。套件主要负责安装预设、应用 Action、必要的用户接口、输出资源、响应适配、链接落地和教程，不另建认证引擎、用户存储或令牌系统。

核心闭环是：安装配置 → 注册 → 登录 → 接收验证邮件 → 验证邮箱 → 获取当前用户 → 管理资料／密码／会话／令牌 → 退出 → 忘记密码 → 收信并重置 → 新密码登录。网页和API两条路径都要交付；提供可替换的账户注销Action，不默认提供修改任意用户、用户列表、角色后台、团队或多租户等独立扩展。

框架契约继续遵循[固定基线](laravel-rebuild-baseline.md)。应用可修改的校验和用户操作放在现有 `app/actions/fortify/`；必要的应用控制器、请求和资源放在所属应用目录。使用现有 Provider／包发现、路由与配置装配，不为套件增加平行 Manager 或全局响应拦截器。具体新增文件和公开名称须在实施前核定。

### 凭据与账户生命周期

- **修改密码：** 保留当前浏览器会话，使其他浏览器会话失效，撤销个人令牌；Token客户端须重新登录。当前会话的认证状态同步更新，不能因旧密码摘要导致本会话意外失效。
- **找回密码重置成功：** 旧浏览器会话和个人令牌全部失效，随后使用新密码登录。
- **个人令牌：** 套件默认有效期30天，允许配置；按设备命名及设置能力，明文只展示一次，持久化摘要。能力由应用定义并受服务端白名单限制，不能以客户端传入能力绕过授权。该有效期属于套件配置，不改变原生Sanctum默认值，也不创建默认刷新令牌体系。
- **退出：** 普通退出仅影响当前会话／令牌；“退出其他浏览器会话”“撤销个人令牌”和“退出所有设备”区分操作及影响范围，敏感操作要求近期密码确认。退出所有设备包含浏览器会话和个人令牌。
- **注销：** 提供可替换DeleteUser Action，要求近期密码确认；默认删除用户记录并清理其认证凭据。业务关联数据由应用定义，不擅自级联删除；存在未处理依赖时明确失败。应用可替换为软删除策略，部分失败不能报告完整注销成功。

上述生命周期在所属模块公开接口与既有事务／存储契约上实现；跨进程、会话驱动、Token客户端的失败与恢复都需实际验证，不能只验证当前进程的内存对象。

## 首版接口与协议细化

以下基础路由按已确认的路径策略实施，复用既有Fortify路由名称和控制器；业务API前缀继续读取 `config/api.rs`／`API_PREFIX`。Fortify自己的 `prefix` 与中间件配置保持独立，保留Session／CSRF。头像、设备会话、Token、注销和可选认证的新增路由，先核对既有模块与固定上游，再由实施时完成公开契约细化，不重复请求产品决策。

| 方法 | 默认路径 | 职责 |
| --- | --- | --- |
| POST | `/register` | 注册用户。 |
| POST | `/login` | Session 登录及必要认证挑战。 |
| POST | `/logout` | 退出当前会话。 |
| POST | `/forgot-password` | 请求重置邮件。 |
| POST | `/reset-password` | 提交重置令牌和新密码。 |
| GET | `/email/verify/{id}/{hash}` | 身份与签名校验后验证邮箱。 |
| POST | `/email/verification-notification` | 重发验证邮件。 |
| GET | `/api/user` | 获取当前认证用户。 |
| PUT | `/user/profile-information` | 更新本人姓名、邮箱。 |
| PUT | `/user/password` | 修改本人密码。 |
| POST | `/user/confirm-password` | 敏感操作前确认密码。 |

当前用户输出采用明确字段白名单的 `UserResource`，不返回密码摘要、remember token、双因素密钥或恢复码等内部属性。避免不加区分地序列化整个认证对象。

响应复用 ApiResponse、本地化及现有验证错误；保留登录200、注册201等语义和204空正文规则。登录／双因素挑战字段、各端点完整 JSON、错误 code、密码重置与验证状态映射，在实施时按既有响应契约逐项固定并同步教程。模板的字段错误同样使用既有翻译机制。

## 认证模式及可选能力

第一方同站网页／SPA默认使用Cookie会话。典型流程为 `GET /sanctum/csrf-cookie` → `POST /login` → `GET /api/user` → `POST /logout`；保留凭据 Cookie、CSRF、Session 轮换和可信来源配置。返回 JSON 不等于无状态认证。

移动端或简单外部客户端显式选择Sanctum个人令牌。签发、按设备命名、列出、撤销、有效期和能力限制遵循下方S01至S07契约，实施时复用现有能力接线；这些管理接口是套件扩展，不声称为上游默认自动注册的路由。签发不能绕过密码及已启用的双因素认证，明文只返回一次，持久化摘要，令牌只归属当前用户，当前设备退出和撤销所有设备须区分。

Sanctum 个人令牌不是 JWT，不默认创建刷新令牌体系；已有 JWT 显式可选决定保留，Passport OAuth2、OIDC／SSO继续独立按需启用。2FA、Passkeys、Socialite等底层能力复用，配套页面／接口纳入首版可选交付；仅启用所选能力，TOTP由用户自愿绑定。

## 安装与链接落地

沿用 `./artisan init` 提供已确认的套件预设，复用单项安装器。已有 `./artisan init --extensions=api,fortify` 是装配基础，不等于完整套件；具体命令选项／非交互参数由实施时定稿并验收，交付前不写成已可执行的新命令。

预设需要明确选择模式，发布应用 Action／Provider／资源／必要接口，开启一致的邮箱验证功能，配置视图或无界面模式，统一重建及提示迁移，并报告邮件驱动是否可实际投递。重入、覆盖、迁移和失败行为引用[现有 init 契约](../plan.md#artisan-init)，保留已有配置、路由、密钥及迁移历史；不额外创建用户或重置开发数据库。

关闭视图后，重置通知仍需正确的 `password.reset` 命名路由或自定义 URL 生成；签名验证链接须保持原始签名参数、有效期和认证用户校验。Token 客户端点击邮件时通常没有浏览器会话，必须独立验收相应前端／客户端落地流程，不能直接把令牌放入 URL、绕过认证或宣称所有客户端自动兼容。前端地址及跳转配置名称在实施时核定，默认自带最小落地页面；重定向范围受既有URL与安全契约约束。

## 审计补充执行契约

以下是实施前必须落实的行为与验收边界。表内拟新增端点是本套件的目标公开契约，尚未实现，不属于上游默认自动注册的路由；相对路径均跟随现有API前缀。复用既有Guard、Action、挑战、Cache、Session、Queue、事务和签名能力，缺失能力在所属模块补齐，不另建认证引擎、通用令牌体系或分布式事务框架。

### S01 Token客户端登录闭环

| 拟新增API路径 | 契约 |
| --- | --- |
| `POST /auth/token` | 接收配置的登录身份、密码、设备名称及请求能力。执行同一身份校验、账户规则和限流；启用额外因素时返回待挑战状态，不返回访问令牌。完成所需证明后签发。 |
| `POST /auth/token/challenge` | 以待挑战凭据完成已启用的TOTP／恢复码或受支持的Passkey证明，单次消费成功后签发。错误、过期、重放、用途或用户不匹配均不签发。 |
| `POST /auth/logout` | 纯Token客户端撤销当前请求实际认证使用的本人令牌，成功204空正文；不要求浏览器Session或近期重新认证，不撤销其他设备。未认证仍返回401，不接受客户端提供其他令牌ID代替当前凭据。 |
| `GET /user/tokens` | 仅列本人令牌的安全元数据，不包含摘要或明文。 |
| `POST /user/tokens` | 已认证且完成近期重新认证后签发本人令牌；不能扩大当前身份和应用允许的权限。与匿名凭密码登录的入口分开。 |
| `DELETE /user/tokens/{token}` | 仅撤销本人令牌，拒绝跨用户操作。本人管理入口受近期重新认证保护；普通当前Token退出沿用当前凭据撤销语义。 |

Session登录继续使用Fortify入口。Token客户端不需要先建立浏览器登录会话，不把 `fortify.guard` 直接改成不符合StatefulGuard契约的守卫。Passkey登录／确认复用已有选项及证明校验能力，提供Token模式适配并纳入路由清单，不用一次“已持有Token”代替重新认证。

目标JSON约定：直接签发或挑战完成签发返回201，`data` 包含 `token_type`、仅本次可见的 `token`、`expires_at` 和 `UserResource`；需要挑战时返回200、稳定code `auth_challenge_required` 及 `data.challenge` 的不透明标识、允许方法和到期时间，不包含访问令牌或因素秘密。所有消息本地化；校验、限流及未认证沿用相应真实状态码。恢复码成功消费只允许一次；失败或中断不得遗留可绕过挑战的授权状态。

待挑战凭据仅授权完成本次登录，不是资源访问凭据；绑定用户、用途、设备请求和已批准的能力，设置有限有效期，使用现有持久化／缓存机制支持跨Worker消费与原子一次性兑换。新的密码变更、撤销或账户删除后，旧证明不能继续签发有效令牌。

验收包含密码错误、因素未完成、挑战过期／篡改／重放、并发兑换、越权能力、跨用户／用途复用以及纯Token客户端完整流程。不得用Cookie登录通过代替本项。

### S02 会话、记住登录与撤销生效点

完整预设的新安装推荐database会话，以提供本人设备列表及IP／User-Agent／最近活动等已有元数据。保留现有file／Redis配置，不能静默改驱动。若所选驱动尚无受验收的安全枚举能力，预检明确报告设备列表功能的缺口；开发者选择受支持的驱动或明确关闭该项后才能继续，不能暗中降级却报告完整版就绪。参考[Jetstream会话驱动要求](https://jetstream.laravel.com/features/browser-sessions.html)。

设备列表与凭据失效是两个契约：列表不支持不代表允许旧凭据继续使用。修改密码、密码重置和全设备退出必须覆盖承诺支持的database／file／Redis会话、记住登录Cookie及Sanctum个人令牌，复用认证指纹、Guard和所属存储能力。必要的公开撤销能力属于A01-02前置补齐项；不以删除数据库sessions行、扫描缓存键或修改当前进程内存冒充通用撤销。

生效点定义为安全变更成功提交后：使用旧凭据的新认证请求必须被拒绝，其他节点不能因缓存身份继续放行，旧remember Cookie不能重新建立会话。已进入业务执行的请求不被宣称可追溯撤回；会签发或恢复安全凭据的并发操作须在提交前重新核验身份／撤销状态，并与安全变更用共同锁、条件写或等价现有持久化契约协调。密码变更不得与旧证明的并发签发共同留下有效新令牌。

会话驱动的失效机制、跨连接Token存储的完成条件及失败恢复须在相关写路径实现前定稿并记录；无法满足时明确报错或标为未交付，不能先返回完整成功。验收至少包含当前会话保留、其他会话拒绝、remember重新登录、各驱动、多进程／多节点、并发登录／签发、存储失败及重试；当前和其他设备归属不依据客户端提供的user_id信任判断。

### S03 近期重新认证与无本地密码账户

“近期密码确认”按现有认证契约表达为近期重新认证：有本地密码时验证密码；已绑定Passkey时允许现有Passkey确认写入同等确认状态。第三方登录账户使用受支持且实际验证过的重新认证流程，或先安全建立本地凭据；不能因为没有本地密码而跳过敏感操作验证，也不能用持有旧会话／Token本身充当证明。安装和功能预检明确各模式支持范围。

Cookie模式使用现有Session确认状态及配置有效期。Token模式须有独立可验证的近期证明，绑定用户、当前凭据、用途及有效期，不设置跨设备共享的“用户已确认”布尔值，也不要求开启浏览器Session。提供对应的确认端点及挑战适配，复用已配置的确认期限；凭据撤销、密码变化和用户删除后证明失效，不能提交给其他用户或设备使用。

可复用线索为现有Passkey确认成功后的 `session.password_confirmed()`，不是新建另一套因素验证器。验收覆盖密码账户、Passkey确认、无本地密码账户、过期确认、错误因素、其他设备复用、因素被撤销和敏感操作并发。不能将“无法确认”误报成已完成注销／令牌创建。

### S04 注销的事务与可恢复清理

注销分阶段定义结果：先验证当前身份、归属和近期重新认证，再预检应用定义的业务依赖；预检失败时不先撤销凭据或删除头像。用户、同事务内认证资料及必要清理工作在所属数据库事务中处理，事务失败回滚，保留可继续使用的账号和凭据，不能把失败呈现为已注销。

数据库提交与外部会话／存储清理不假装具有同一个事务。采用现有可靠任务／持久化机制保存需要重试的清理工作，在提交前确保不会因进程崩溃丢失；不提前删除仍被有效用户记录引用的资源。数据库提交后，旧账号身份不可再次认证；外部清理失败必须保留可跟踪、幂等、可重试的状态，不能尝试“回滚”已经提交的删除，也不能把清理入口建立在已删除用户还能继续登录的假设上。

200／204只表示约定的同步完成；采用异步清理时202明确表示受理／已提交而资源清理未完成，并提供受控的结果追踪，不宣称全部清理成功。具体队列驱动、事务连接、清理工作持久化及结果追踪契约在DeleteUser实现前核定，优先复用现有能力，不为套件引入通用工作流系统。

验收包含业务外键／应用拒绝、事务回滚、撤销存储失败、头像删除失败、提交前后强制中断、可靠任务未重复丢失、重复操作与可替换Action。业务数据和外部身份提供方账户不被默认级联删除；OIDC／供应商远端退出不混为本地注销已完成。

### S05 Web与JSON响应矩阵

网页GET返回HTML；普通表单沿用Fortify重定向、闪存状态、错误包及旧输入。密码、令牌、验证码、恢复码等秘密不进入old input或诊断日志。明确请求JSON的接口使用ApiResponse和本地化错误；Cookie请求同样可以协商JSON，但不因此变成Token模式。204始终零正文，浏览器退出保留正确重定向，不能把所有Web表单一律改成JSON。

实施前逐端点登记方法、预设、协商方式、成功／失败状态、重定向目标、完整JSON和挑战状态。通过现有Fortify响应绑定及ApiResponse扩展实现，套件之外的原生响应继续保留。对缺少Accept头、普通浏览器、Fetch/XHR、API前缀及错误回退分别验收，不能只测一组JSON成功请求。

### S06 权限与邮箱验证矩阵

| 入口类别 | 身份与邮箱状态 | 额外保护 |
| --- | --- | --- |
| 登录／注册／找回／重置 | 对应公开或guest流程；注册开关同时影响页面和后端入口 | 登录／邮件限流，浏览器状态请求的CSRF；不通过错误输出泄露秘密。 |
| 本人资料读取、姓名／头像更新 | 已认证，允许未验证邮箱；仅本人 | Token能力与应用授权均须满足；敏感元数据采用白名单。 |
| 修改邮箱／密码 | 已认证，允许修正尚未验证的邮箱 | 本人归属及相应密码校验／近期重新认证；邮箱或密码变化执行已确认生命周期。 |
| 验证／重发邮件 | 对应已认证用户，允许未验证邮箱 | 签名、有效期、当前邮箱归属和限流；重复行为见S08。 |
| Token管理、全设备退出、注销 | 已认证且具备所需能力；本人归属 | 近期重新认证；不能依赖客户端传入用户ID、Token能力或通用SPA token_can结果代替业务授权。 |
| 受保护业务 | 已认证且邮箱已验证 | 仍需对应业务授权和Token能力；不能因完成邮箱验证而取得未授予的能力。 |

未验证用户的Token登录必须能完成本人及邮箱验证流程，但只授予允许的账户／验证能力，不授予业务权限；验证成功不暗中扩张旧令牌能力，需按正常签发和授权流程获取新权限。不能给整个API组统一追加verified而挡住上述恢复入口，也不能遗漏业务路由的验证保护。开发者自定义用户、字段、路由与能力时运行相同访问矩阵回归。

### S07 30天令牌与过期清理

套件签发时用可信时钟及配置计算并写入每个令牌的expires_at，默认30天；不能只在响应显示到期时间而未持久化。显式有效期必须受服务端规则约束，不能让客户端自行延长至无期限。原生Sanctum全局过期配置仍有效，实际期限采用其现有校验与每令牌期限中更早的限制；不覆盖其他模块的原生默认值。

修改套件默认期限只影响之后签发的令牌，不追溯改写已有expires_at；原生全局限制变化仍依其原契约作用于已有令牌，文档须区分。到期即认证失败，不依赖清理任务先执行；使用已有过期令牌清理命令及调度机制处理残留，明确启用方式和保留窗口，不自建刷新／清理体系。

验收包含30天边界、配置变化、每令牌期限与更短全局限制、自定义令牌模型和主键、未清理的已过期令牌拒绝、清理幂等、错误时间输入及签发响应与持久值一致。

### S08 邮件签名、幂等与落地页面

密码重置令牌成功后单次消费，重复重置拒绝；邮箱验证在身份、签名与有效期检查通过后保持幂等，已验证邮箱再次访问不重复派发Verified事件，不把所有重复点击统一视为重放攻击。修改邮箱后旧链接的邮箱hash／身份检查失败；队列中延迟发送的旧邮箱通知不能错误验证新邮箱。参考固定[Fortify验证控制器](https://github.com/laravel/fortify/blob/v1.43.0/src/Http/Controllers/VerifyEmailController.php)。

完整预设包含全部页面；仅API预设仍发布已确认的最小重置／验证落地页面，不发布整套用户中心。API-only不等于删除一切HTML；自有前端可替换落地地址，但受信任Origin和跳转范围来自应用配置，不接受任意redirect参数改变目的地。

Token客户端携带Authorization执行认证请求，邮件URL不含Bearer令牌或长期访问凭据。通知生成、前端回调和API认证适配必须使用匹配的原始签名URL／路径／查询串；不能把Web链接参数搬到不同API路径后假定原签名仍有效。使用配置的前端或默认页面承接登录与继续操作，明确无会话／已登录／错误用户各分支，保留原有签名算法与用户归属校验。

验收覆盖链接缺失、过期、篡改、重复点击、并发验证、换邮箱、旧通知延迟、配置前端地址、伪造跳转、错误主机／路径、Cookie及纯Token客户端；本地邮件捕获与真实SMTP及最终收件结果分开记录。

### S09 头像上传与存储生命周期

头像默认只接受可实际解码的JPEG、PNG、WebP；SVG及可执行内容不列入默认允许范围。验证真实文件内容、大小和尺寸上限，不信任文件名或客户端MIME。具体限额集中在应用可调整的校验配置／Action中，使用既有验证、图片与Storage能力，随机命名并通过配置磁盘生成URL，避免用户控制路径或覆盖其他用户文件。

替换时先完成验证及新文件写入，再更新本人模型；写入或数据库更新失败保留旧头像，并回收本次失败的新文件。新引用提交后再回收旧文件，删除失败使用已有重试机制并保留结果，不把存储失败隐藏为完全成功。注销清理引用S04，不绕过相同生命周期规则。

验收包括伪装图片／MIME、SVG、超限大小／尺寸、畸形内容、路径穿越、跨用户归属、文件／数据库失败、并发替换及旧文件回收，分别核对本地磁盘与承诺支持的对象存储适配；真实云账号不足明确列为外部验收。

### S10 安装预检、资源清单与证据边界

两个预设在写文件前分别列出准确的Cargo特性、Provider、配置、Action、请求、控制器、资源、路由、Blade／静态资源、语言资源及迁移清单。模板必须能用于干净骨架和已有业务项目；先识别自定义User、主键、Guard、数据库连接和已有模块布局，无法安全自动接线则在受影响写入前停止并提供具体手工位置，不能等到最后验收才发现模型不匹配。

SPA预检明确Origin／stateful来源、Cookie域与Secure／SameSite、CORS credentials及CSRF。沿用现有配置并核对父域、端口和HTTPS要求；不把任意跨站前端都标为Cookie模式就绪，不因API-only关闭web必要中间件。预检还包含邮件、队列、会话驱动、头像磁盘、过期清理调度、可选SDK／静态资产与关闭选项的行为，不覆盖开发者已有凭据。

安装命令与预设仅在所有必需依赖就绪后报告相应可用；首个安装批次的内部验收不能对外宣称完整预设已完成。可选认证页面根据已注册且受支持的驱动生成，实施前固定驱动及客户端版本清单；缺真实第三方账号、物理设备或生产服务时列出精确待验条件，按既有证据分层报告，不无限扩展供应商范围，也不混淆本机功能与生产发布通过。
