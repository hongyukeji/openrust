## 目标与架构

交付可选安装的完整版用户认证入门套件，复用 Fortify、Sanctum、Auth、Session、CSRF、Hash、验证器、密码代理、签名链接、通知、限流和 ApiResponse。套件主要负责安装预设、应用 Action、必要的用户接口、输出资源、响应适配、链接落地和教程，不另建认证引擎、用户存储或令牌系统。

核心闭环是：安装配置 → 注册 → 登录 → 接收验证邮件 → 验证邮箱 → 获取当前用户 → 管理资料／密码／会话／令牌 → 退出 → 忘记密码 → 收信并重置 → 新密码登录。网页和API两条路径都要交付；提供可替换的账户注销Action，不默认提供修改任意用户、用户列表、角色后台、团队或多租户等独立扩展。

框架契约继续遵循[固定基线](laravel-rebuild-baseline.md)。应用可修改的校验和用户操作放在现有 `app/actions/fortify/`；必要的应用控制器、请求和资源放在所属应用目录。使用现有 Provider／包发现、路由与配置装配，不为套件增加平行 Manager 或全局响应拦截器。具体新增文件和公开名称须在实施前核定。

### 凭据与账户生命周期

- **修改密码：** 保留当前浏览器会话，使其他浏览器会话失效，撤销个人令牌；Token客户端须重新登录。当前会话的认证状态同步更新，不能因旧密码摘要导致本会话意外失效。
- **找回密码重置成功：** 旧浏览器会话和个人令牌全部失效，随后使用新密码登录。
- **个人令牌：** 套件默认有效期30天，允许配置；按设备命名及设置能力，明文只展示一次，持久化摘要。能力由应用定义并受服务端白名单限制，不能以客户端传入能力绕过授权。该有效期属于套件配置，不改变原生Sanctum默认值，也不创建默认刷新令牌体系。
- **退出：** 普通退出仅影响当前会话／令牌；“退出其他浏览器会话”“撤销个人令牌”和“退出所有设备”区分操作及影响范围，敏感操作要求近期密码确认。退出所有设备包含浏览器会话和个人令牌。
- **注销：** 提供可替换DeleteUser Action，要求近期密码确认；默认删除用户记录并清理其认证凭据。业务关联数据由应用定义，不擅自级联删除；存在未处理依赖时明确失败。应用可替换为软删除策略，部分失败不能报告完整注销成功。

上述生命周期在所属模块公开接口与既有事务／存储契约上实现；跨进程、会话驱动、Token客户端的失败与恢复都需实际验证，不能只验证当前进程的内存对象。

必须处理的已观察组合：

- Fortify 安装模板默认 `views=true`，但应用尚需提供视图回调；不能把只安装后端称为已有登录页面。
- 当前 Fortify 安装模板默认未启用 `email-verification`，默认 User 却具有邮箱验证能力。套件须有一致的功能组合，不将该问题留给开发者手动排查。
- Fortify 登录使用自己的 JSON，如 `two_factor:false`；普通 `Response::json` 不会自动套用业务封装。通过现有响应契约适配，不改变所有 Fortify 使用者的默认返回。
- 默认根应用已有公开的 `GET /api` 信息接口。`install:api` 保护自定义业务路由，套件须既保留该接口，又正确接入受保护的 `/user`；不能只运行安装器便假设用户接口已生成。
- 保留[待办](../todo.md)中尚无可靠根因的 Fortify 偶发 Session 失败记录。套件通过不能替代该问题的根因裁决。

## 首版接口与协议细化

以下基础路由按已确认的路径策略实施，复用既有Fortify路由名称和控制器；业务API前缀继续读取 `config/api.rs`／`API_PREFIX`。Fortify自己的 `prefix` 与中间件配置保持独立，保留Session／CSRF。头像、设备会话、Token、注销和可选认证的新增路由，先核对既有模块与固定上游，再由实施时完成公开契约细化，不重复请求产品决策。

| 方法 | 默认路径 | 职责 |
| --- | --- | --- |
| POST | `/register` | 注册用户。 |
| POST | `/login` | Session 登录及必要认证挑战。 |
| POST | `/logout` | 退出当前会话。 |
| POST | `/forgot-password` | 请求重置邮件。 |
| POST | `/reset-password` | 提交重置令牌和新密码。 |
| GET | `/email/verify/{id}/{hash}` | 身份与签名校验后验证邮箱。 |
| POST | `/email/verification-notification` | 重发验证邮件。 |
| GET | `/api/user` | 获取当前认证用户。 |
| PUT | `/user/profile-information` | 更新本人姓名、邮箱。 |
| PUT | `/user/password` | 修改本人密码。 |
| POST | `/user/confirm-password` | 敏感操作前确认密码。 |

当前用户输出采用明确字段白名单的 `UserResource`，不返回密码摘要、remember token、双因素密钥或恢复码等内部属性。避免不加区分地序列化整个认证对象。

响应复用 ApiResponse、本地化及现有验证错误；保留登录200、注册201等语义和204空正文规则。登录／双因素挑战字段、各端点完整 JSON、错误 code、密码重置与验证状态映射，在实施时按既有响应契约逐项固定并同步教程。模板的字段错误同样使用既有翻译机制。

## 认证模式及可选能力

第一方同站网页／SPA默认使用Cookie会话。典型流程为 `GET /sanctum/csrf-cookie` → `POST /login` → `GET /api/user` → `POST /logout`；保留凭据 Cookie、CSRF、Session 轮换和可信来源配置。返回 JSON 不等于无状态认证。

移动端或简单外部客户端显式选择Sanctum个人令牌。签发、按设备命名、列出、撤销、有效期和能力限制的接口在实施时复用现有能力定稿；这些管理接口是套件扩展，不声称为上游默认自动注册的路由。签发不能绕过密码及已启用的双因素认证，明文只返回一次，持久化摘要，令牌只归属当前用户，当前设备退出和撤销所有设备须区分。

Sanctum 个人令牌不是 JWT，不默认创建刷新令牌体系；已有 JWT 显式可选决定保留，Passport OAuth2、OIDC／SSO继续独立按需启用。2FA、Passkeys、Socialite等底层能力复用，配套页面／接口纳入首版可选交付；仅启用所选能力，TOTP由用户自愿绑定。

## 安装与链接落地

沿用 `./artisan init` 提供已确认的套件预设，复用单项安装器。已有 `./artisan init --extensions=api,fortify` 是装配基础，不等于完整套件；具体命令选项／非交互参数由实施时定稿并验收，交付前不写成已可执行的新命令。

预设需要明确选择模式，发布应用 Action／Provider／资源／必要接口，开启一致的邮箱验证功能，配置视图或无界面模式，统一重建及提示迁移，并报告邮件驱动是否可实际投递。重入、覆盖、迁移和失败行为引用[现有 init 契约](../plan.md#artisan-init)，保留已有配置、路由、密钥及迁移历史；不额外创建用户或重置开发数据库。

关闭视图后，重置通知仍需正确的 `password.reset` 命名路由或自定义 URL 生成；签名验证链接须保持原始签名参数、有效期和认证用户校验。Token 客户端点击邮件时通常没有浏览器会话，必须独立验收相应前端／客户端落地流程，不能直接把令牌放入 URL、绕过认证或宣称所有客户端自动兼容。前端地址及跳转配置名称在实施时核定，默认自带最小落地页面；重定向范围受既有URL与安全契约约束。
