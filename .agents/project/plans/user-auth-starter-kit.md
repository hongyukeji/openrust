## 目标与架构建议

建议交付可选安装的用户认证入门套件，复用 Fortify、Sanctum、Auth、Session、CSRF、Hash、验证器、密码代理、签名链接、通知、限流和 ApiResponse。套件主要负责安装预设、应用 Action、必要的用户接口、输出资源、响应适配、链接落地和教程，不另建认证引擎、用户存储或令牌系统。

核心闭环是：安装配置 → 注册 → 登录 → 接收验证邮件 → 验证邮箱 → 获取当前用户 → 退出 → 忘记密码 → 收信并重置 → 新密码登录。需要用户资料和密码更新能力，但不默认提供修改任意用户、用户列表、角色后台等管理功能。

框架契约继续遵循[固定基线](laravel-rebuild-baseline.md)。应用可修改的校验和用户操作放在现有 `app/actions/fortify/`；必要的应用控制器、请求和资源放在所属应用目录。使用现有 Provider／包发现、路由与配置装配，不为套件增加平行 Manager 或全局响应拦截器。具体新增文件和公开名称须在实施前核定。

必须处理的已观察组合：

- Fortify 安装模板默认 `views=true`，但应用尚需提供视图回调；不能把只安装后端称为已有登录页面。
- 当前 Fortify 安装模板默认未启用 `email-verification`，默认 User 却具有邮箱验证能力。套件须有一致的功能组合，不将该问题留给开发者手动排查。
- Fortify 登录使用自己的 JSON，如 `two_factor:false`；普通 `Response::json` 不会自动套用业务封装。通过现有响应契约适配，不改变所有 Fortify 使用者的默认返回。
- 默认根应用已有公开的 `GET /api` 信息接口。`install:api` 保护自定义业务路由，套件须既保留该接口，又正确接入受保护的 `/user`；不能只运行安装器便假设用户接口已生成。
- 保留[待办](../todo.md)中尚无可靠根因的 Fortify 偶发 Session 失败记录。套件通过不能替代该问题的根因裁决。

## 建议首版接口

以下为建议协议，尚未决定作为套件最终默认。优先复用既有 Fortify 路由名称和控制器；业务 API 前缀继续读取 `config/api.rs`／`API_PREFIX`。Fortify 路由自己的 `prefix` 与中间件配置保持独立，不因路径包含 `api` 就移除 Session／CSRF。

| 方法 | 默认路径 | 职责 |
| --- | --- | --- |
| POST | `/register` | 注册用户。 |
| POST | `/login` | Session 登录及必要认证挑战。 |
| POST | `/logout` | 退出当前会话。 |
| POST | `/forgot-password` | 请求重置邮件。 |
| POST | `/reset-password` | 提交重置令牌和新密码。 |
| GET | `/email/verify/{id}/{hash}` | 身份与签名校验后验证邮箱。 |
| POST | `/email/verification-notification` | 重发验证邮件。 |
| GET | `/api/user` | 获取当前认证用户。 |
| PUT | `/user/profile-information` | 更新本人姓名、邮箱。 |
| PUT | `/user/password` | 修改本人密码。 |
| POST | `/user/confirm-password` | 敏感操作前确认密码。 |

当前用户输出建议采用明确字段白名单的 `UserResource`，不返回密码摘要、remember token、双因素密钥或恢复码等内部属性。避免不加区分地序列化整个认证对象。

响应复用 ApiResponse、本地化及现有验证错误；保留登录200、注册201等语义和204空正文规则。登录／双因素挑战字段、各端点完整 JSON、错误 code、密码重置与验证状态映射，须讨论后逐项固定。模板的字段错误同样使用既有翻译机制。

## 认证模式及可选能力

建议第一方同站网页／SPA 默认使用 Cookie 会话。典型流程为 `GET /sanctum/csrf-cookie` → `POST /login` → `GET /api/user` → `POST /logout`；保留凭据 Cookie、CSRF、Session 轮换和可信来源配置。返回 JSON 不等于无状态认证。

移动端或简单外部客户端建议显式选择 Sanctum 个人令牌。签发、按设备命名、列出、撤销、有效期和能力限制的接口均须另定；这些管理接口是套件扩展，不声称为上游默认自动注册的路由。签发不能绕过密码及已启用的双因素认证，明文只返回一次，持久化摘要，令牌只归属当前用户，当前设备退出和撤销所有设备须区分。

Sanctum 个人令牌不是 JWT，不默认创建刷新令牌体系；已有 JWT 显式可选决定保留，Passport OAuth2、OIDC／SSO继续独立按需启用。2FA、Passkeys、Socialite等底层能力可复用，但本套件的默认启用范围仍待确认，不因后端已有实现就默认全部安装或要求用户绑定。

## 安装与链接落地

建议沿用 `./artisan init` 增加基础认证预设，复用单项安装器，不再并列增加多套用户安装命令。已有 `./artisan init --extensions=api,fortify` 可作装配基础，但不等于上述完整套件；新的预设名称、命令选项及交互项尚未确定，不应提前写成可执行命令。

预设需要明确选择模式，发布应用 Action／Provider／资源／必要接口，开启一致的邮箱验证功能，配置视图或无界面模式，统一重建及提示迁移，并报告邮件驱动是否可实际投递。重入、覆盖、迁移和失败行为引用[现有 init 契约](../plan.md#artisan-init)，保留已有配置、路由、密钥及迁移历史；不额外创建用户或重置开发数据库。

关闭视图后，重置通知仍需正确的 `password.reset` 命名路由或自定义 URL 生成；签名验证链接须保持原始签名参数、有效期和认证用户校验。Token 客户端点击邮件时通常没有浏览器会话，必须独立验收相应前端／客户端落地流程，不能直接把令牌放入 URL、绕过认证或宣称所有客户端自动兼容。前端地址及跳转配置的名称、默认值和允许范围待讨论。

## 待定事项

1. 第一批是否以无界面API为主；基础Blade页面是否同期提供。
2. 首版默认Cookie／SPA模式是否采用；Token客户端是否首批同时交付。
3. 默认保留Fortify原路径，还是套件选择统一API前缀；两类中间件与Guard如何明确区分。
4. 当前用户输出字段、资料可编辑范围、是否包含账户注销；不默认引入用户管理后台。
5. 各端点ApiResponse、认证挑战字段和状态码的最终协议。
6. 重置／验证邮件的前端落地地址、跳转策略及Token客户端流程。
7. init预设、默认功能、交互与安装范围；2FA／Passkeys等是否默认关闭或只安装不启用。
8. 批次顺序、发布目标及实际SMTP／收件验收条件。

上述事项均为讨论项，不可当作已批准的实现细节。后续确认在本文件更新最终决定与原因；项目上下文只维护接续入口，避免重复维护方案。
