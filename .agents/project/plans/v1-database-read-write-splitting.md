# v1 数据库基础读写分离计划

> 受众：AI Agent
> 更新：2026-10-25
> 摘要：已确认纳入 v1，尚未实现；归属 `openrust-db`，默认单库，按配置启用主库与只读副本。具体公共 API 与配置键在实现前形成 contract。

## 目标与边界

- 普通项目只配置一个数据库，维持现有使用体验；开启应用集群不要求数据库读写分离。仅在需要分摊读取负载时启用副本。
- 复用 SeaORM、`Db`、`DatabasePlugin` 和既有配置/生命周期，不创建第二个 ORM 或平行数据访问入口；多个命名数据库与同一逻辑库的主副本路由分别建模。
- v1 正式覆盖 PostgreSQL/MySQL。数据库自身负责复制与选主，框架负责连接、选择和错误语义；不交付复制系统、自动提升副本、分库分表或跨库事务。
- 不解析 SQL 字符串猜测所有操作的安全性，不宣称可以透明拦截全部 SeaORM/原生连接调用。公共契约必须说明受管理入口及逃生口的覆盖边界。

## 最低交付契约

| 场景 | 要求 |
| --- | --- |
| 配置与兼容 | 一个主库、可选多个只读副本，独立且有界的连接池；未配置副本时全部走主库；现有单库配置及自定义连接初始化保持可用或同步迁移全部调用方 |
| 路由 | 写入与锁定读取走主库；允许陈旧结果的普通读取可选副本；提供显式强制主库入口，原始 SQL 默认采取保守策略 |
| 事务 | 框架事务默认在主库开启，事务内所有读写使用同一事务连接，不能因查询是 SELECT 就切到副本；嵌套事务/savepoint 与重试边界沿用现有契约 |
| 写后读 | 显式主库读取可用；提供请求/工作单元内写后保持主库的能力，明确传播与释放边界。该能力不承诺跨请求、跨节点读后写一致性，也不能覆盖绕过框架的写入 |
| 副本选择 | 使用简单、可测试且低开销的策略；推荐先做轮询，避免无依据的复杂权重或自动拓扑发现 |
| 故障 | 副本连接/读取故障的主库回退可配置，建议默认禁用并明确报错以避免故障流量压垮主库；启用后有界、可观测，禁止重试写入或掩盖 SQL/业务错误 |
| 内部关键路径 | 认证撤销/权限判断、幂等判定、队列领取/状态、调度锁、迁移/seed 等依赖最新状态或锁的操作显式使用主库，不自动跟随普通读取路由 |
| 可观测性 | 区分主库/副本连接池与路由、故障、回退指标及日志，不暴露凭据；无法测量复制延迟时不得假称自动保证新鲜度 |

异步复制可能返回旧值；文档须用“修改资料后立即读取”的例子解释。跨请求要求最新数据时使用主库；不以固定等待时间、黏性会话或 Redis 标记冒充复制完成保证。

## 实施顺序与 Agent 提醒

1. 当前 M3 认证功能簇先闭环，不混入读写路由重构。开发认证时立即将强一致读取需求记录到 contract，避免给后续副本路由留下隐含假设。
2. 作为 M2 数据层增补，在依赖路由语义的后续数据功能簇前领取 `todo.md` 对应项；原 M2 完成标签不能覆盖此新增范围。先评估现有 API、下游、事务钩子和 Plugin 扩展，形成 5–15 行 Spec 与公共 contract，再实现。
3. 同步门面、`apps/server`、双库生成模板、示例及 crate README；默认示例保持单库，额外提供启用副本和强制主库的简明示例，不要求普通开发者部署副本。
4. 实际实现与验收后更新 `core/db.md`、`progress.md` 和测试基线；不能将本计划或底层库的多连接支持记成已交付读写分离。

## 验收

- 契约测试验证单库兼容、副本选择、强制主库、写后保持主库、事务/锁定读取固定主库、自定义连接扩展和错误分类；一个事务中不能泄漏出副本查询。
- PostgreSQL 与 MySQL 各使用真实主库及只读副本完成集成验证。通过受控暂停/恢复复制等方式验证可观察的旧读、强制主库新读、复制追平与故障/恢复；两个独立数据库不能冒充复制拓扑。
- 多 API 节点验证主库强一致路径和请求内状态隔离；覆盖撤销、幂等及队列/调度相关调用方的回归。全量 Rust 门禁和双库生成项目检查按仓库规范执行。
- 比较单库默认路径与启用路由的开销，记录池总连接预算；不以“增加副本”承诺未经测量的吞吐提升。
- 外部拓扑不可用时如实标注未验收，fake 或编译通过不能替代真实复制测试；不自动更改用户的数据库、凭据或服务器配置。
