# BCP 47 语言标识统一迁移方案

日期：2026-11-22。状态：A→E 已实施并完成本轮可执行的隔离验收；真实环境升级及未验平台见第 11 节和[验收记录](../audits/03-07/locale-bcp47-2026-11-22.md)。

用户后续已授权完整实施及隔离验收，随后明确授权暂存和本地提交；不包含操作开发／生产数据、推送或发布。首次实施保留实际 `.env`；后续要求全部处理好，已仅迁移本地三个语言值并完成隔离启动验收，见第11节。本轮基于 `59cb9f0d1` 及已有在途改动执行，保留其他协作者修改。本方案优先于此前“内部下划线、Web 连字符”的项目约定；旧审计结果只代表原源码，不作为新方案验收。

## 1. 目标与标准

项目公开语言标识统一采用 IETF BCP 47。应用配置、公开 API 参数和返回值、事件、翻译资源目录及文件名、文档目录及 URL、HTML、HTTP、生成应用和项目自有持久化语言值使用同一种标签。

默认三语为：

| 内容 | 目标标识 | 原有项目资源标识 |
| --- | --- | --- |
| 英文 | `en` | `en` |
| 简体中文 | `zh-Hans` | `zh_CN` |
| 繁体中文 | `zh-Hant` | `zh_TW` |

地区语言继续使用有效标签，如 `en-US`、`en-GB`、`zh-CN`、`zh-TW`、`zh-HK`、`sr-Latn-RS`、`es-419`。`zh-Hant-HK` 表示香港地区繁体中文，不能丢弃其地区信息。

标准分隔符为 ASCII 连字符 `-`；输出采用语言小写、文字代码首字母大写、地区大写的常见规范大小写，数字地区不变。BCP 47 比较不区分大小写，不意味着可以把路径一律转小写；磁盘目录和生成 URL 固定使用规范拼写。

“语言标签”与翻译键分开：`welcome.heading`、命名空间、错误码、数据库字段名不属于语言标签，不做机械替换。`APP_LOCALE` 等配置键和已有公开方法名也不因本次迁移重命名。

### 1.1 规范化与语言选择不能混为一谈

- 规范化负责合法格式与规范拼写，例如 `ZH-hant-hk` → `zh-Hant-HK`。
- `zh-CN`、`zh-Hans`、`zh-TW`、`zh-Hant` 都有独立含义。规范化不把地区改为文字体系，不自动增加或删除地区和文字代码。
- App／Lang 的设置、读取、判断、事件字段及缓存键采用一致契约。`setLocale("zh-CN")` 后读取 `zh-CN`；`isLocale("zh-cn")` 为真，`isLocale("zh-Hans")` 为假。当前选中三语资源与原输入标签分别处理，不伪装成同一个标识。
- 中文浏览器匹配是应用策略：`zh-Hans`、`zh-CN`、`zh-SG`、裸 `zh` 选择 `zh-Hans`；`zh-Hant`、`zh-TW`、`zh-HK`、`zh-MO` 选择 `zh-Hant`；显式文字体系优先于地区。`zh-Hant-CN` 选择繁体，`zh-Hans-TW` 选择简体。未知文字体系不按中文地区猜测，走既定无匹配回退。
- 通用翻译器不能无条件把所有中文地区资源合并为三语目录。调用者创建 `zh-HK` 或 `zh-Hant-HK` 资源时，应能准确读取，不能被欢迎页策略遮蔽。
- RFC 4647 的 lookup/filtering 与 CLDR likely-subtags 是不同机制。复用时分别说明职责，不声称中文地区推断是 BCP 47 强制要求，或把自动选择说成框架默认行为。

### 1.2 与固定上游的关系

固定 Laravel 文档在地区目录示例中使用 `en_GB`。本次是用户明确要求的项目标准调整：语言标识采用 BCP 47，优先于旧目录命名适配。其余配置名称、翻译职责、装配、事件顺序、请求／任务隔离及回退契约继续保持既定对齐，不借此改造平行框架。

## 3. 解析与依赖方案

1. 继续使用现有规范化入口，先查清全部调用方，不另造 LocaleManager 或维护两套全局语言状态。
2. 当前 `LanguageIdentifier` 与包含扩展的完整 Locale 不能直接视为等价。检查锁定版本 ICU4X 的 `Locale`、canonicalizer 及必要的成熟解析库，确定语法检查、弃用别名处理和扩展保留的实际支持。
3. 在实现记录中区分语法合法、IANA 已登记、规范化、支持翻译资源四个概念。缺少某语言目录不等于标签非法；不在线访问 IANA 做每次请求校验，也不自行抄写一份不断变化的完整注册表。
4. 覆盖文字／地区／variant、Unicode 扩展（如 `en-US-u-nu-latn`）、private-use（如 `en-x-demo`）及 grandfathered 标签的适用行为。优先复用库的现有实现；如确有支持边界，逐项写明并给出显式错误，不能默默截断扩展再声称完整 BCP 47 支持。依赖取舍在编码前记录，不将未经验证的覆盖列为已实现。
5. 格式化消费者可以消费 Unicode 扩展；翻译资源是否移除扩展进行 lookup 属于独立资源查找规则，须验证、文档化并保留原应用标签。Deprecated alias 的规范化依赖固定数据版本和实测，不用简单大小写替代真正的 canonicalization。
6. 非法标签、路径穿越、NUL、空字符串及恶意超长输入沿用结构化错误；文件路径不得直接拼接未验证输入。合理限制需依据现有机制和标准适配记录，不随意把合法长标签截断。

## 4. 资源匹配、回退与默认值

- 三语内置资源与文档分别迁至 `lang/zh-Hans/`、`lang/zh-Hant/`、`docs/zh-Hans/`、`docs/zh-Hant/`；同名句子键 JSON 同步迁移。英文目录保持 `en`。
- 对显式请求标签先准确读取对应资源。通用翻译的基础 fallback 继续遵循既定契约；如为地区到文字资源增加 CLDR／RFC 4647 查找，须作为单独明确的查找步骤实现，保留精确目录优先，核对分组翻译与句子键 JSON 原有差异，不能顺手改变缺键语义。
- 浏览器三语协商继续在应用中间件内定义，不重新引入 `app.supported_locales`。选定 `zh-Hans`／`zh-Hant` 后，全请求用相同标签，页面与响应头一致。
- 无匹配、缺 Accept-Language、q=0、非法权重、重复头、同权重、星号及未知语言均明确回退；支持的应用默认语言优先，否则按现有策略选英文，不更改项目原有默认语言偏好。
- 关闭浏览器中间件后，App 接受有效的其他标签，翻译器正常回退；欢迎页的文档链接只能选择实际存在的三语目标，不生成 `docs/fr` 等不存在路径。不为修复链接改动应用语言。
- `APP_FAKER_LOCALE` 也使用 BCP 47，例如原英文地区默认 `en_US` 对应 `en-US`，简体示例选择 `zh-Hans`；不得仅改分隔符而漏掉 provider 分派。Faker 某项需要地区、而输入仅有文字体系时，依据已有支持为 provider 建立明确适配，如简体对应原 zh_CN、繁体对应原 zh_TW；适配只在该消费者边界发生，不回写应用标签。

## 5. 迁移与兼容决策

### 5.1 项目自有代码与资源

一次迁移所有活跃资源和引用，不长期并行维护旧／新目录或两套配置。公开新配置和输出只用 BCP 47。新主线不默认保留下划线输入别名或旧 URL 重定向；旧环境需按升级说明显式修改。实施者若发现已有已发布兼容承诺，先记录具体冲突及范围，不默默另加永久兼容层。

| 旧项 | 新项 | 说明 |
| --- | --- | --- |
| 项目默认简体 `zh_CN` | `zh-Hans` | 本项目三语资源迁移，属于内容分类选择 |
| 项目默认繁体 `zh_TW` | `zh-Hant` | 同上，不是两个标签天然等价 |
| 独立地区资源 `en_GB` | `en-GB` | 保留地区语义 |
| 独立地区资源 `zh_HK` | `zh-HK` | 不自动并入繁体默认目录 |
| 文字与地区 `zh_Hant_HK` | `zh-Hant-HK` | 不丢弃信息 |

现有 `zh-CN`／`zh-TW` 本来就是有效 BCP 47 标签，公共解析不把它们无条件改为文字标签。原项目资源 `zh_CN`／`zh_TW` 的默认三语迁移映射必须只作用于已确认归属的资源／数据，不能在全局解析器偷换含义。

旧下划线形式作为新公开输入时显式报错并提示迁移；大小写变体等有效 BCP 47 输入正常规范化。一次性迁移工具或操作说明可识别旧形式，不把迁移识别扩散为永久运行时别名。

### 5.2 第三方与底层适配

第三方 Faker 类型名／provider 键、CLDR 原始数据、外部 API 字段、许可证和固定上游测试原文保持所属协议。确实必须的下划线转换仅存在于依赖边界，写明原因并验证；不得改第三方标识符造成依赖不可用，也不能借此让项目 API 再输出旧标识。

盘点 Faker `locale()`、`randomLocale()` 等公开返回值：项目自有输出若代表语言标签则统一 BCP 47；既有与外部 provider 原始数据的对应关系单独保留。不对所有包含 zh_CN 的文本做全局替换。

### 5.3 环境、缓存和数据

- 保留现有 .env 的非语言设置、凭据与密钥；说明 APP_LOCALE／APP_FALLBACK_LOCALE／APP_FAKER_LOCALE 的旧值迁移。首次实施由部署者处理；后续用户要求收尾，已备份并仅迁移本地三个语言值，不将该授权扩大为真实数据库或其他部署环境的数据修改。
- 配置缓存、翻译目录缓存、Blade 缓存及生成应用快照分别核对。需要失效或重建时通过已有正式入口执行，不增加启动时全盘扫描或静默改配置。
- 数据库翻译、设置、任务载荷等有旧语言值时，先列出字段、是否序列化、唯一键和关联范围；生成只读盘点／dry-run 及显式迁移步骤。映射发生键碰撞时报告并保留两份内容，不能覆盖丢失；需要时用事务验证回滚及幂等重跑。
- 禁止自动修改开发／生产数据。共享存储行为涉及迁移时，以三库隔离实例验收；缓存涉及旧键时按 Redis／database／file 范围核对。旧队列任务和旧应用进程按部署升级步骤排空或重启，不放任新旧标签混跑。
- 文档目录和 URL 按同一批迁移。升级说明列出旧新地址映射；不复制正文保留旧入口。已有部署若需要过渡重定向，由部署层另行明确配置，不默认增加项目路由与长期兼容壳。
- 历史审计、固定源码和第三方数据不伪装重写为新标准；活跃规范／上下文／待办／开发者正文必须同步，历史记录可加一处新方案入口说明适用版本。

## 6. 文档与使用体验

开发者示例统一展示 en／zh-Hans／zh-Hant，并使用 en-GB、zh-Hant-HK 等说明地区／文字差别。包括 README、环境模板、配置、翻译、校验、工厂、队列、邮件、通知、扩展、安装及部署等实际受影响章节。

VitePress 对象键含连字符时使用合法的字符串键，不靠变量名或 `toLowerCase()` 推导路径。切换语言保留章节，站内搜索按对应语种，默认首页偏好保持原意；检查默认语言入口、SSR HTML lang、sitemap／SEO 元信息、404、根目录与 /docs/ 子目录部署。GitHub Markdown 相对链接和实际文档目录同步可用。

三语同步描述“项目采用 BCP 47”，不把该调整宣称为固定上游原生目录约定。迁移说明面向实际使用，不把内部审计流水放到 docs 正文。

## 10. 调研来源与采用理由

2026-11-22 已联网读取以下原始资料，采用标准及现有成熟库，不新增自定义语言协议：

- [RFC 5646：语言标签](https://www.rfc-editor.org/rfc/rfc5646.txt)：BCP 47 标签结构、连字符、大小写无关、扩展与 private-use；用于公开标识契约。
- [RFC 4647：语言匹配](https://www.rfc-editor.org/rfc/rfc4647.txt)：区分标签语法与 filtering／lookup，避免把三语策略当标准等价关系。
- [Unicode UTS #35](https://unicode.org/reports/tr35/)：核对 Unicode Locale 与 BCP 47 的转换边界；CLDR 推断不与标签格式归一混用。
- [ICU4X Locale API](https://docs.rs/icu_locale_core/latest/icu_locale_core/struct.Locale.html)：确认 Locale 与 LanguageIdentifier／extensions 的结构差异。在线 latest 只作调研线索，实施以 Cargo.lock 的实际版本及源码／测试复核，不能直接升级依赖照抄。
- [固定 Laravel 本地化教程](https://github.com/laravel/docs/blob/960eedf0911155ad16326ade49c0ea5d18eda0b8/localization.md)：核实 en_GB／ISO 15897 目录示例，明确本次用户要求覆盖该命名适配，其余职责继续对齐。

旧版复用：已核对旧 v0.x 的 `translation.rs` 和相关实现，旧版使用自有 Locale、消息目录及不同 Loader，不整套迁入。复用现有规范化入口、ICU 依赖、作用域及资源复制机制；历史目录遗漏经验用于补齐本轮目录、链接及真实消费者验收。
