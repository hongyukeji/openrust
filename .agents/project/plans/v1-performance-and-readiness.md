# v1 性能与开箱即用补强计划

> 受众：AI Agent
> 更新：2026-10-26
> 摘要：补充 v1 完整使用路径、性能与生产验收要求，并列出实施前需要决策的问题及推荐方案。不是实现完成记录。

## 目标与执行边界

- 本计划补充 [v1 总计划](gen1-plan.md)，服务“高性能、开箱即用、可扩展，让开发者直接进入业务开发”的定位。
- 用户已要求按复盘建议补强；验收路径纳入 v1。已有 ADR 和公共接口优先复用；下文尚未实现部分的“建议”是决策输入，不能据此重开已经落定的配置、供应商与存储契约。
- 实施前核对代码、当前 ADR 与活跃 WIP，将可闭环功能簇拆入 `todo.md`。不因本计划并发开启第二个功能簇，不覆盖其他 Agent 的改动。
- 尽早随里程碑建立代表性应用与性能基线，不把组合验证全部留到 M6；未完成的能力逐步接入，不先造空壳。
- 不新增前端后台、多租户、通知平台等业务系统；复用已规划能力。新增依赖需按 `stack.md` 记录理由。

## 当前证据边界

M2 读写路由、M3 认证/安全及新生成认证项目已有双库验证记录；M4 数据库队列与 scheduler 已有基础实现和局部多进程证据。数据库 `SELECT 1` 路由微基准只覆盖连接往返，不证明完整业务吞吐、框架开销或集群扩容收益。完整真实服务组合、持续负载、资源饱和、跨节点文件/实时投递、滚动升级与干净环境发布产物黄金路径仍待验收。

验证范围以 [测试基线](../memory/testing.md)、[验收口径](../memory/verification.md) 和相关 `core/` 为准；本计划不新增已通过声明。日常使用 PostgreSQL 18、MySQL 8.4 LTS、Redis 8；暂定最低 PostgreSQL 14+、MySQL 8.0+、Redis 6.2+ 在 v1 发布前复核完整能力路径。日常不重复全版本矩阵，主版本跨度、专属行为或明确兼容风险才加专项测试，且不能省略受影响数据能力的 PostgreSQL/MySQL 双库验证。

## 纳入 v1 的补强与验收

| 领域 | 要求 | 验收证据 |
| --- | --- | --- |
| 性能基线 | 建立最小 HTTP 与代表性业务路径；区分框架开销、数据库等待和外部依赖耗时 | 可复跑脚本、数据准备、固定环境、release 构建、预热/测量区间及重复测量报告 |
| 性能指标 | 记录吞吐、p50/p95/p99、错误率、CPU 与内存；测量日志、压缩、响应包装等组合开销 | 记录请求/响应大小、并发、连接池、版本及启用的 feature；测量工具不能先成为瓶颈 |
| 构建与依赖成本 | 分别测量无数据库、单驱动和标准应用的依赖范围、干净构建、修改业务代码后的增量构建及产物体积 | 固定工具链/平台/profile/缓存条件；`default = []` 不等于没有 ORM/邮件等依赖，按证据决定 feature 调整，不为指标机械拆包 |
| 并发与资源 | 为请求、连接池、阻塞任务和 worker 建立有界处理与过载策略 | 饱和、超时、拒绝、恢复及资源释放测试；具体限制值需实测决定 |
| 数据访问 | 生成物和示例具备合理分页、必要索引及显式关联查询 | 双库代表性查询验证；有能发现 N+1 或无界结果集问题的场景，不把性能结论等同于 SQL 次数 |
| 稳定性 | 依赖变慢/断开后可恢复，停机行为和任务状态明确 | 持续负载、故障注入、恢复与停机记录；区分请求终止、后台操作结束和外部副作用 |
| 双库项目生成 | 整套源码中的 `apps/<name>` 可通过本地依赖完成检查、测试、迁移、seed 与启动 | PostgreSQL/MySQL 模板分别走通；仓库 `apps/server` 测试不能替代生成物验收 |
| 开发入口 | `dev` 编排依赖就绪、显式迁移策略、服务运行及文件变更重启；失败时提供修复建议 | 干净环境端到端记录，包含端口占用、依赖缺失和重复启动；先复用符合条件的现有服务，不擅自重置已有数据 |
| 账号与通信 | 注册、登录、找回密码、邮箱验证与邮件/短信能力形成可运行路径 | 集成测试与示例，通信真实适配和实发边界遵循 [短信决策](../decisions/adr-011-sms-and-communication-baseline.md) |
| 异步一致性 | 明确事务提交、任务投递、失败重试与重复执行语义 | 事务回滚不派发，提交后投递失败有明确结果；可靠投递方案按下文决策 |
| 测试体验 | 统一应用启动、HTTP 断言、数据库隔离与 fake 驱动 | workspace 内生成应用可直接测试，不要求用户自行拼装测试框架；使用 fake 不代表真实驱动验收 |
| 业务开发体验 | 从首次启动到资源开发、驱动替换、测试、诊断、部署及升级形成一致入口 | 未参与该功能实现的走查者仅凭中文文档完成，记录环境/步骤/耗时/阻塞点；Agent 代走查如实注明，不替代真实用户反馈。与 Laravel 等对照任务流程，不复制 API 名称或承诺相同开发耗时 |
| 生产约定 | 区分开发和生产配置，明确迁移、API、worker 的启动与退出方式 | 生产配置示例、容器 smoke、反向代理部署说明、健康/就绪检查与诊断 |
| 外部扩展 | 独立适配示例仅使用公开契约完成配置、注册、执行、错误处理和测试 | 独立 consumer 验证完整路径，无私有构造器/内置枚举阻断；含非数据库队列执行同一 typed Job，不能仅以派发 fake 通过关闭执行扩展；各后端不支持能力明确拒绝 |
| feature 组合 | 库默认、无数据库、各单驱动与标准应用组合分别验证 | 标准生成应用默认启用 Redis cache，库层 Redis feature 可选；CI 对有效组合执行匹配的检查/测试，不能只用 all-features 代替用户实际组合 |
| 源码到部署 | 完整源码与模板使用同一 workspace/path 依赖，无需内部包发布或人工 Cargo patch | 干净源码副本中生成 apps 并走完黄金路径；源码 release 等对外动作仍需独立授权 |
| 源码升级与维护 | 保留业务应用的升级路径、支持平台、维护窗口和兼容约定 | 临时副本执行源码升级、冲突处理和回归；Schema/任务兼容及回滚限制明确，公开承诺以实际支持矩阵和验证为准 |

## 待决策事项与建议

### 1. 基准、阈值与执行环境

- 建议先建立最小 Axum 对照服务和相同协议/负载的 OpenRust 服务，再增加数据库、认证、缓存、队列路径；确保比较的功能与日志设置可解释。
- 建议常规 CI 验证脚本可运行，稳定的专用环境执行性能回归；发布前保存完整报告。共享 runner 的抖动不宜直接作为严格性能门禁。
- QPS、延迟、内存及回归阈值从实测基线制定；待确定硬件、数据规模、重复次数和允许波动，不填写无依据的承诺值。

### 2. 过载、阻塞操作与超时

- 建议复用现有中间件与服务配置，限制在途请求和排队，避免无界等待；通用过载与按用户限流分别设计，拒绝响应遵循 ADR-008。
- 建议密码哈希、同步文件 I/O 等采用有并发边界的阻塞执行；不能仅调用 `spawn_blocking` 就认为资源有界。文件缓存、压缩、批量处理的实际开销需单独测量。
- 当前密码服务对单次 Argon2 参数有限制，但 `hash/verify` 直接提交阻塞任务；在生产资源簇补总体容量、排队/拒绝及恢复策略。登录限流和单任务参数上限不能替代全进程资源边界。
- 业务查询、数据库队列、Session 和限流共享数据库时，测量池等待、竞争及 API 尾延迟，按数据决定预算/实例隔离。替换 Redis queue 时仍须单独满足事务投递契约，不能用换后端代替一致性设计。
- 建议分别定义 HTTP 请求、连接获取、数据库操作、外部发送、worker 和停机的时间边界，避免层层无限等待；请求超时不能被描述为已撤销所有副作用。
- 默认数值、排队/拒绝策略和错误码须形成 contract 并验证，不在本计划直接定值。

### 3. 事务与任务派发

- 默认数据库队列已按 ADR-037 提供 `dispatch_in_transaction`：任务记录与业务写入同事务提交/回滚，worker 只能领取已提交任务。优先复用该入口，不把它重新排为待设计能力。
- 仍需补公开事务前后扩展及业务流程契约：提交前可验证/拒绝，提交后不能回滚已经提交的业务；after-commit 回调失败应有明确返回和补偿边界。普通提交后派发存在“已提交但投递失败/进程退出”的窗口，不能宣称可靠无丢失。
- 对 Redis 或外部消息系统，若 v1 承诺可靠投递，建议采用事务 outbox 并补清理/重放/监控；若不交付，必须明确保证较弱，不能将 after-commit 说成无丢失。
- 默认按至少一次执行设计，任务需可幂等；不承诺跨数据库与外部供应商的恰好一次副作用。ownership token 对确认/续租/状态更新的保护须补旧 worker 恢复后的接管竞态断言，不能将队列状态保护等同于所有业务副作用的 fencing。

### 4. 验证码与通信组合验收

- `VerificationCodes`、数据库共享 store、用途/身份绑定、一次消费、尝试限制及重发冷却已按 ADR-026 实现，账号流程复用 ADR-024；不重建第二套验证码服务。
- 邮件/短信发送由通信层负责，验证码原值不得进入生产日志；已有 fake 与协议测试不证明外部供应商送达。真实短信验收仍需授权凭据与目标。
- 在队列与薄通知层接入时补延迟发送导致过期、发送失败、重试重复与跨节点消费的组合测试；不因基础验证码测试通过就关闭这些验收项。数据库共享状态默认不要求 Redis。
- 手机号账号模型、短信登录、MFA 与图形验证码不是发送/验证码机制的自动附带功能，不未经评估加入。

### 5. 缓存未命中、并发加载与故障

- 建议区分未命中与驱动故障；回源、失败或降级必须显式配置或有明确文档，不隐藏驱动故障。
- 建议 `get_or_insert_with` 评估同进程同键加载合并，失败时释放等待者并允许后续重试；是否跨进程协调取决于驱动契约，不把本地合并称为分布式锁。
- TTL、容量、淘汰与过期清理由各驱动明确；tag 仍为后续候选，default/named stores 已按 ADR-014 定义，M5 实现后验收。标准应用默认 Redis，memory/file 显式选择；服务故障或缺少配置/feature 不得静默回退到本地缓存。

### 6. 生产默认值与开发编排

- 可信代理来源已按 ADR-028 明确，后续复用该机制；针对真实 TLS 终止拓扑补 Secure Cookie、来源校验与 CSRF 验收，配置错误应尽早暴露。
- 建议限制请求/上传大小、访问私有文件和外部调用等待，并为迁移并发、worker 退出、残留任务和回滚提供运行说明。
- `dev` 与测试编排必须先检查并复用版本/配置/连通性符合条件的现有服务；缺少或不适用时才创建本次隔离服务，并只清理自己创建的资源。文件监听由一个明确入口管理子进程，重复启动可恢复，避免多个 API/worker 残留。
- 默认配置、代理头规则、迁移锁和停机时限须由实现证据确定；不擅自修改用户系统或生产配置。

### 7. 上传下载与出站 HTTP

- Storage 与上传下载仍待 M5，实现时复用现有路由及签名链接能力；提供大小、类型校验、授权及临时访问示例。类型识别不能仅信任文件名或客户端 MIME，内容检测在发布前可拒绝且失败清理有界，不强制加入媒体处理平台。
- 出站 HTTP 已按 ADR-031 提供统一客户端、连接复用、超时、受控重试及注入 transport；后续供应商与业务调用复用它，继续验证有界流式处理与实际负载，非幂等调用不默认重试。
- 上传下载适配与统一出站 HTTP 均纳入 v1，具体要求见 [覆盖计划](v1-capability-coverage.md) 和 [通用能力计划](v1-common-capabilities.md)。新增公共 API 前形成最小 Spec，不因本计划直接增加新 crate。

### 8. 源码升级与维护约定

- 延续 ADR-039 的整套源码交付。在临时副本中建立有业务代码、配置和迁移的旧源码基线，升级到目标版本，验证 apps 内容保留、依赖及配置调整、迁移与任务兼容、测试和启动；说明上游变更冲突如何处理，已执行不可逆迁移不能用 Git 回退冒充数据回滚。
- 建议业务定制优先使用 apps 与公开扩展接口；框架修改明确保留为可识别补丁。提供最小可操作升级说明和回归样例，不先建设复杂自动升级平台，也不改成独立 Cargo 包发布。
- 发布准备时明确框架支持版本、维护/安全修复窗口及弃用规则；现有 MSRV 和数据库版本政策继续有效。Linux/macOS/Windows、x86_64/ARM64 分别列已验证、未支持或待验证状态，不把 Ubuntu CI 推广为全平台支持。
- HTTP 版本入口继续按 ADR-008；补公开 API、配置、Schema、任务载荷与生成客户端的兼容检查和破坏性升级说明。V2 的前端/移动端升级复用这些约定，不另设一套响应体系。
- 维护流程的实现与演练属于本地验收；源码发布、tag、推送及对外支持承诺仍按既有授权边界处理。

## 推进顺序与完成证据

1. 领取任务先按 `todo.md` 完成 ADR-039 源码交付及 C1–C3 中文整改；保留已验证能力，不重复迁移根模块或重做认证。
2. M4 复用已实现事件与队列编排，完成事务/请求幂等、流程扩展及通知组合，修正 worker 停机和错误传播、补旧 token 接管证据；开始串联 `examples/blog` 已可用的账号/权限/CRUD/异步路径。
3. M5 在可选 driver 前闭合数据库与队列外部扩展边界，交付缓存、存储、实时和可观测性；逐步接入示例，测量共享依赖竞争和资源限制，不预建空功能。
4. M6 收口干净环境到部署和源码升级、平台/维护约定、feature 与构建成本、外部扩展示例、性能和独立走查证据；不能只以编译与单测通过作为 v1 完成。

具体决策由负责设计的 Agent 按仓库分工形成 ADR/contract；实现 Agent 按已定 contract 编码，遇到冲突记录待办并交回设计，不自行扩大范围。各项完成后把稳定事实迁入 `core/`、架构或正式文档，并按项目约定清理已完成计划。
