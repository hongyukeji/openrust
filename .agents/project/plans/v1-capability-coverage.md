# v1 通用能力覆盖与归属

> 受众：AI Agent
> 更新：2026-10-26
> 摘要：补齐通用基础能力的交付范围，明确单一职责入口、复用位置与验收；不将底层库支持、内部专用实现或空壳视为框架交付。

## 交付原则

- v1 以迁入框架后可直接进入业务开发为标准。常见应用反复使用的底层机制由框架整合，不要求业务开发者重新拼装驱动、生命周期、错误处理和测试工具。
- 通用机制完整交付；具体业务规则、业务数据模型、后台 UI 与所有供应商实现不要求框架穷举。数据库正式矩阵仍为 PostgreSQL/MySQL，其他后端按 ADR-009 扩展。
- “待决策”表示还需确定公共契约、布局、默认值和实现方案，不能以此省略本计划已纳入的能力。
- 每类职责只有一个公共入口，复用既有模块和成熟 Rust crate。新增能力不等于新增 crate；内部函数具备相似行为不代表应用已有可用接口。
- 框架封装必须有明确附加价值：配置/注册、生命周期、安全默认值、统一错误、测试支持或跨驱动契约。避免没有价值的逐方法包装，也不让用户自己完成整合。
- 具体能力按 [通用能力计划](v1-common-capabilities.md)、[补强计划](v1-performance-and-readiness.md) 与本表协同实施；同一能力只登记一个 contract，不创建平行系统。

V1 按 [框架参考与对标](framework-design.md#框架参考与对标) 综合评估 Loco、Laravel、Goravel、OpenSpring；若依、芋道仅 V2 开发时参考。框架能力新增范围以 [底层补齐计划](v1-foundation-completion.md) F1–F10 为准；OpenRouter 仅对标后续 AI模型平台的产品能力。

每个功能簇须按 [扩展性自主判断](framework-design.md#开发-agent-的自主扩展性判断) 主动核对常见业务接入场景。示例不穷举，机制可灵活选择，合理扩展通过公开 API 完成且不增加重复能力。

## 当前交付边界

根 `src/` 框架模块、配置与 `.env`、M2 读写路由、M3 本地认证与通用安全能力已有实现及对应验收记录。M4 已有数据库队列、同事务派发、活动任务唯一键、worker、有限任务链/批次、UTC/calendar scheduler、类型化事件与固定内容多渠道通知；worker 停机、崩溃恢复和通知事务已在双库专项验收，见 [队列事实](../core/queue.md) 与 [调度事实](../core/schedule.md)。

缓存/存储、上传下载、WebSocket/SSE、gRPC、通用流程扩展，以及最终性能/完整集群路径仍须交付；请求幂等与薄通知编排已有实现及适用验收。下表是 v1 范围，不是完成清单；单机测试、独立实例共享测试或双进程竞争不能替代负载均衡、真实跨节点投递和故障恢复验收。唯一执行队列在 [todo.md](../todo.md)，已验证事实在 `core/` 与 `memory/`，不在本表维护第二套进行中状态。

## 需要决策的实现建议

- Session、签名链接、限流与审计已有公共入口，后续能力优先复用；只补实际缺口，不能重新建另一套认证或安全服务。流程扩展按既有事务、Plugin、队列与事件边界实施。
- 多实例是通用使用能力，先提供简单默认路径；具体配置布局、类型化选择方式及切换时机由设计确定。缓存入口仍叫 `Cache`，“store”不是新的顶层能力。
- 原子锁优先复用后端真实原语，锁由所有权令牌保护释放；业务锁、队列唯一性和调度锁共享契约或实现，但各自保证不能混淆。不用进程锁冒充分布式锁。
- 任务链与批处理优先复用数据库队列状态，限制批规模和并发；明确失败中止/继续、重试、取消与崩溃恢复，不承诺外部副作用恰好一次。
- 通知编排放在现有发送层之上，只解决渠道选择与派发；真实提交结果仍来自 Mail/SMS。当前不持久化业务发送记录；需要业务变更与所有通知任务一起提交时使用事务派发。
- SSE 与 WebSocket 共用资源控制、认证和停机约定；跨节点在线投递按 [集群计划](v1-cluster-deployment.md) 在 v1 交付，持久历史重放另行扩展，不将进程内事件描述为可靠消息总线。
- ORM 能力优先直接复用 SeaORM 的稳定接口并给出框架示例；仅在一致性、安全或易用性确有收益时封装。多连接与读写路由分别建模；基础读写分离按专题计划在 v1 交付，不要求跨库事务。
- 上传类型识别不能只信任扩展名/MIME；流式操作、请求幂等、响应包装与 OpenAPI 的兼容边界要有测试，不能为统一 JSON 而缓存整个流。

## 对标后的缺口分类与决策关口

V1 的比较依据按 [四框架参考规则](framework-design.md#框架参考与对标) 维护；若依/芋道只在 V2 对标。范围分为：

- **已确认 V1 必交**：gRPC、跨协议/出站/运行补强，以及 [底层补齐](v1-foundation-completion.md) F1–F10；具体方法与依赖可由设计 Agent 决策，不能把范围重新退回可延期候选。
- **已有计划继续交付**：缓存/存储/实时、事件/队列、通知、锁/幂等、公开驱动、生成器/TestApp/OpenAPI、集群与源码升级；在原任务深化，不创建第二套实现。
- **后续适配/评估**：更多数据库、外部 MQ、搜索、运行时功能开关、SSR/静态 Starter，以及独立 OAuth 授权服务器、Passkeys/SAML；完整清单在底层补齐计划，未计入 V1 完成承诺。

部门/岗位 DataScope、租户管理与套餐、导入导出业务页面仍归 V2；通用查询规则、租户隔离和数据交换归 V1。当前 i18n、调度、认证等已实现范围不因计划扩大而自动具备新能力。GraphQL、任意 DAG、分库分表/跨库事务及自建服务治理控制面保持原边界。

## 推进与完成定义

- M3：复用已实现的国际化、HTTP、安全、验证码、可选会话/限流和认证流程；真实短信投递仍需授权账号与目标，不能用协议 fake 关闭外部验收项。
- M4：复用现有队列/调度/事件，完成正确性与流程扩展、请求幂等，以及 F1 日历调度、F2 国际化、F3 邮件模板/通知组合。
- M5：外部扩展与运行保障、缓存/存储/出站、F4–F8，以及 gRPC/实时/观测按依赖交付；先有公共规则与共享后端，再验收跨协议和租户组合。
- M6：F9 应用模板覆盖、F10 fixtures、完整生成器/文档/示例、有效 feature 组合、性能/故障恢复与部署验收；不以方法或目录存在标记完成。
- 每项有唯一实现归属、公开调用路径、配置、成功/失败及并发测试、示例与可执行验收。具体公共 contract、依赖选型和默认值需设计审查后实施。
- 当前活跃功能簇继续独立闭环；按依赖顺序更新 `todo.md`，不把所有未执行能力同时标为进行中。本计划只要求本地开发与验证，不新增远端发布或外部通信授权。
