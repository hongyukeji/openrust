# AI 插件套件与完整平台应用计划

> 受众：AI Agent
> 更新：2026-10-26
> 状态：远期规划，套件与应用均未启动开发；须先完成框架 v1/v2 完整体成熟验收，再由开发者明确立项。
> 摘要：交付官方可选 AI 插件套件及完整平台应用，让开发者按需接入 AI 能力；全量组合继续对标 OpenRouter 公开功能与使用流程。当前不增加 v1/v2 交付范围，平台完全体验收后才可上线。

## 产品定位

- 形态为“官方可选 AI 插件套件 + 完整平台应用”，最终品牌待定。普通应用可只调用模型，网关应用可组合接入与治理能力，完整平台组合全部必交付模块及网站；“API 中转”是其中一项能力，不作为产品名称。
- 最终目标继续为 OpenRouter 公开产品功能与关键流程复刻，范围、基线、审计缺口和验收以 [完整对标计划](ai-platform-openrouter-parity.md) 为准。开发者按需启用插件不等于本项目可以省略完整平台的任何必交付项；不以软件交付承诺取得相同的供给、用户规模或历史数据。
- 套件与平台应用拥有独立于 OpenRust v1/v2 的版本、排期和验收，分别声明所支持的框架版本/commit、Rust 版本、依赖 feature、数据库与协议范围。框架 v1 提供通用运行能力，v2 后台套件可提供管理基础；AI 能力不属于框架 v1/v2 的隐含交付项。
- 当前仅维护规划，优先完成框架 v1、v2 已确认范围及成熟验收；此后由开发者明确决定是否立项，不自动启动。不得提前创建套件或应用源码、分支、数据库或部署环境；不因插件形态调整降低启动门槛或削弱框架契约。

## 启动、开发与上线硬性门禁

本节是 AI 套件及平台应用启动、完整平台上线时机的权威规则；阶段里程碑只表示内部开发顺序，不代表任何对外开放许可。

| 门禁 | 必须满足 | 未满足时 |
| --- | --- | --- |
| G0 框架完全体成熟 | OpenRust v1 完整通用底座与 v2 完整后台套件的已确认范围均实现并验收；全量工程门禁、双库、生成项目、核心用户流程、单机/集群、性能/资源基线、恢复/升级与文档有可复验证据；无影响产品依赖的未解决阻塞，开发者认可成熟基线 | 只维护规划，不启动产品实现；不以版本名、目录存在或部分能力可用替代成熟 |
| G1 产品立项 | G0 通过后由开发者明确授权 AI 套件与平台应用进入 P0 调研/规格与有界原型；P0 完成基线、插件边界、外部条件、预算及技术验证后评审退出，才进入全面实现 | 未授权时保持规划；P0 未通过时不进入全面实现。框架成熟不代表自动立项 |
| G2 完整体内部验收 | 在 `projects/*` 分支完成 P0–P8；最终细项矩阵全部实现/验证，未知项取证关闭，真实外部依赖就绪；独立宿主接入与完整平台的功能、网站、SDK、资金、权限、隐私、集群、性能和故障恢复全链路通过 | 继续内部开发和修复；MVP、阶段版本、Beta、部分插件可用或功能关闭不能绕过最终范围 |
| G3 上线决策 | G2 证据已汇总，产品/框架依赖版本与部署产物可追溯；完成独立审查、验收环境演练、备份恢复/回滚、监控告警、运营支持与费用配置检查；开发者明确批准上线 | 不执行生产发布、公开注册、对外服务或付费开放；不得因完成代码自动部署 |

- “框架完全体”指 v1/v2 已确认的正式交付范围，不把远期候选全部自动升级为框架要求。成熟性由实际验收决定；如需稳定观察期，其时长/负载与通过阈值在成熟评估时明确，不预先编造周期或性能数字。
- 完整平台的 P1–P7 均为内部增量、演示或验收构建；禁止以提前验证商业模式为由公开试用、邀请外部用户使用、开放 API、收取客户充值或上线缩水版本。必要的第三方联调/受控真实调用按授权在隔离验收环境完成，不等于产品上线。
- 完全体不等于复制对方用户数、私有合同与历史数据；仍以最终确认的功能/接口/角色流程基线为准。必需上游、支付、区域或企业能力受外部条件阻塞时，G2 失败并继续等待，不能通过注明差异提前上线。
- 完整范围的删除、降级或上线政策的更改只能由开发者明确决定并同步计划；Agent 不得以工期、成本、上游缺失或首版已可运行自行裁剪。
- 功能完成和发布授权分别判定。G0–G2 的“通过”须有证据，不由本计划预先保证；计划约束的是交付范围与门禁，不能替代开发、测试和实际成熟度。
- 可复用插件按自身声明范围独立验收与选择性交付；对外分发、发布遵守既有授权边界。可选交付不构成完整平台提前公开试用、收费或发布的授权，不能据此宣称已通过 G2/G3。

## 分支与工作区硬性约束

- 后续套件与应用的实现、配置、迁移、前端、测试和部署文件修改必须在 `projects/*` 分支上进行。推荐主分支 `projects/ai-platform`，功能分支 `projects/ai-platform-<topic>`；`projects/*` 表示 Git 分支命名空间，不代表必须建立同名源码目录。
- 使用独立 Git worktree 隔离产品开发。开始前核对分支、基线 commit、Git/WIP、其他 Agent 与数据库；不得在框架共享工作区切换产品分支，不移动或清理他人改动。worktree 放置仍遵守项目目录外写入授权边界。
- 当前框架主线仅保存本规划及索引；官方可选源码分发是已确认目标。可复用插件可在公开契约、兼容范围、依赖/许可证、配置迁移与默认构建隔离验证后独立纳入可选分发，实际合并、发布遵守既有授权边界。可复用平台模块及其迁移、视图资源也可作为可选套件交付；具体部署的业务数据、运营政策、供应商凭据与品牌网站由独立应用维护。不能将整个产品分支合并回框架主线，领域模型不进入框架核心。
- 独立 worktree 内保留完整框架源码。平台应用位于 `apps/<product>/`，插件套件放在与应用分离的可复用源码位置；实际位置与 workspace 成员在 P0 确定，不机械按每个能力拆 crate。在项目分支管理依赖锁定、配置、迁移、测试和部署，不改变主线默认 feature、启动和 CI 条件。
- 按 [ADR-039](../decisions/adr-039-source-workspace-distribution.md) 从明确框架 commit 获取整套源码。首期通过本地 workspace/path 静态源码引用和公开 `Plugin::build/finish` 装配；不以独立发布 crates.io、动态库加载或热安装为前提，不修改核心以适配私有调用。本计划不创建目录。
- 产品跟进框架升级时在产品分支验证兼容性；不得为维持产品旧行为冻结、倒退框架公共 API 或降低测试、安全、性能要求。
- 本地 commit 不代表授权合并、推送、发布或部署；这些动作遵守开发者明确授权与仓库边界。

## 框架与产品职责

| 层次 | 可复用或交付内容 | 边界 |
| --- | --- | --- |
| OpenRust v1 | 认证、事务、缓存、限流、HTTP/SSE、取消、加密、审计、幂等、队列、集群与观测 | 以实际公开 API 与验收为准；不依赖内部私有实现 |
| OpenRust v2 | 用户/角色/菜单、日志、任务、监控、生成器及后台组件 | 可选复用；不能把平台客户/渠道/账单模型反向塞进后台通用套件 |
| AI 调用插件 | 供应商 adapter、模型能力声明、统一调用、流式、工具调用与用量结果 | 可在现有应用内单独启用；不要求安装网关路由、平台用户表、计费或 UI |
| AI 网关插件 | 模型目录、消费 Key、路由/回退、RPM/TPM/并发限额、BYOK 与调用审计 | 依赖调用层和所需框架公开能力，通过宿主契约接入身份、权限与预算；不强绑平台账本 |
| 可选平台模块 | 定价、预算预占、账本、充值、组织与客户、供应商运营、控制台功能 | 模块拥有独立迁移与业务规则；启用收费时必须配置可验证的资金权威，不能以可选模块为由跳过结算 |
| 完整平台应用 | 组合全部必交付插件、平台模块与网站/管理界面 | 承接 OR-01–OR-23、P0–P8 与 G0–G3，应用按需组合不缩减项目完整交付范围 |
| 通用改进 | 经验证可普遍复用的框架缺陷修复或扩展能力 | 单独 Spec、变更与测试，不夹带模型名、供应商或定价分支；按框架流程独立审查，不自动回灌 |

分支隔离不能替代架构隔离。遇到框架能力缺口，先判断能否通过公开 Plugin/trait/配置在产品侧实现；确属通用缺陷则形成独立框架任务。不能用永久产品 fork、业务特判、放宽认证或弱化事务来绕过问题。提取通用改进前明确适用场景与兼容性，框架主线的纳入由开发者验收决定。

## 插件接入与宿主契约

- 依赖方向为“宿主应用 → 选用的 AI 插件/平台模块 → OpenRust 公开能力”，框架核心不反向依赖 AI。仅启用调用插件时，不注册网关或管理路由，不要求数据库账本、支付、Redis 或后台套件；只有选用功能实际需要的依赖才成为启动条件。
- 沿用现有 `Plugin::build/finish`、服务/配置注册、路由与命令扩展。现有接口只证明可以装配扩展，不表示已实现 AI 调用、协议兼容、流式取消或完整生命周期；后台任务复用命令 supervisor，不新建全局插件容器或在 `finish` 中留下无人管理的任务。
- 宿主通过公开且类型明确的适配契约提供主体、租户/workspace、授权结果及可选预算服务；插件不得直接依赖某张框架或应用用户表。公网网关身份从可信认证路径解析，缺失或不匹配时拒绝；禁用商业计费时显式选择内部使用政策，仍要限制上游调用资源与费用风险。
- 路由前缀、配置命名空间、服务冲突、所需 feature 和依赖缺失在启动时检查；公开的供应商适配器不得依赖私有构造器或闭合的内置 provider 枚举。只登记插件不应自动执行数据库迁移、创建默认管理员或发出付费网络请求。
- 插件拥有自身配置与迁移，应用显式组合并执行迁移；不静默修改宿主用户表。升级兼容、旧配置处理、schema 兼容窗口和卸载后数据保留按 [工程契约](ai-platform-engineering.md#插件版本配置与迁移契约) 执行；禁用插件不自动删表或数据。
- 独立接入样例与测试必须证明：只用调用层、组合网关并复用自有身份、全量平台三条路径均可行；前两者无需复制平台私有代码。验收以公开 API 为边界，不靠绕过可见性或修改核心源码实现。

## 早期内部开发范围

本节是内部开发的早期子集，不是独立上线版本；最终必交付领域见 [完整能力矩阵](ai-platform-openrouter-parity.md#完整能力矩阵)，不能依据首版表省略后期功能。

| 领域 | 最低交付 |
| --- | --- |
| 客户与消费 Key | 注册/登录、账户状态、Key 创建/哈希存储/一次性展示/撤销、模型白名单与消费上限；管理密钥与调用密钥权限分开 |
| 模型目录 | 统一模型 ID、上游 ID 映射、上下文/输出限制、工具/结构化输出等能力声明、上下架与价格版本 |
| 供应商渠道 | 少量明确目标的真实供应商适配；凭据加密及轮换、连接/超时、健康检查、独立启停和配额；目标清单启动时确认 |
| 兼容 API | 首先实现 OpenAI 风格 `models` 与 Chat Completions、非流式和 SSE；工具调用/结构化输出仅对声明支持且经测试的路径开放，不宣称全部协议兼容 |
| 路由 | 先按能力/上下文/权限筛选，再按明确优先级选择模型与渠道；有界重试/回退、熔断及冷却恢复；禁止无条件重试所有 POST |
| 配额 | 客户/Key/模型/渠道的请求速率、Token 速率、并发与消费预算，明确计数窗口和分布式原子边界；不能只用请求数限流代替 Token 配额 |
| 计量与定价 | 输入/输出/缓存/推理等实际适用计量项、上游成本与客户售价、请求价格快照；无法确认的用量进入待核实状态 |
| 余额账本 | 充值、预占、结算、释放、调账/退款与可追溯流水；金额用定点/Decimal，幂等键与唯一约束防重复，数据库为权威状态 |
| 订单与充值 | 首先完成沙箱或受控测试闭环；真实支付方式、结算单位/精度、退款与费用规则启动时确认；回调验签、重复/乱序处理与对账 |
| 客户控制台 | Key、余额、账单/用量明细、模型目录与接入文档、基础图表；在线试用复用正式配额与计费路径 |
| 运营后台 | 客户/模型/渠道/定价、订单/账本查询、受权限控制的调账、故障与成本利润观察；敏感凭据不可读取导出 |
| 隐私与安全 | 默认不记录提示词和回答正文，元数据留存/脱敏；配置变更审计；上游 URL、远程图片/文件处理防 SSRF，客户端不能自由转发服务端密钥 |

## 请求与结算规则

收费平台及启用商业计费的网关建议主路径：认证与模型权限 → 能力/政策筛选并冻结候选报价 → 配额与费用上界校验 → 持久化预占 → 按快照选择渠道 → 上游调用/流式转发 → 实际用量核验 → 幂等结算与释放剩余额度。回退前重新核对候选、费用与剩余预占，不能在无授权资金上界时切换更贵渠道。仅调用层不强制客户账本，由宿主明确承担上游费用并设置输出、超时、重试与并发上限；返回用量和未知执行结果，不自动向客户计费。

- 每个逻辑请求、上游尝试、额度预占与结算分别可关联；客户幂等重试与内部渠道回退不能混成一条不可解释记录。
- 已向客户端输出内容后，不无缝切换另一模型并拼接结果；首字节、块间空闲、总时限分别控制，慢客户端有背压与有界缓冲。
- 客户断开应尝试取消上游，但不能假定上游已停止或没有计费。超时同样不证明未执行；失败尝试的上游成本与客户收费分别记录并遵循明确政策。
- 以可信上游 usage 为主要计量来源；本地估算标明模型、算法与版本，不以同一 tokenizer 推算所有模型。流末 usage 缺失、崩溃与未知执行结果进入待核实/补偿状态，不直接按零消费或盲目释放全部预占。
- 价格、单位与舍入规则绑定请求快照；历史账单不随当前定价变化。充值、人工调整与结算保留可审计流水，通过反向分录更正而非覆盖历史。
- 并发预占与最终扣款使用数据库事务/约束，余额及权限关键判断走主库；Redis 仅承担允许的加速/共享配额，不成为无法重建的唯一资金账本。
- 后台任务负责核实、对账与修复，但不能把无持久记录的扣费异步“发出去就算完成”；实际一致性方案先形成 contract。

## 里程碑与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| P0 启动与契约 | G0 通过并获 G1 的 P0 授权后开始调研/规格与有界原型；创建 `projects/*` 分支及独立 worktree；确定来源版本、插件组合/宿主契约、上游/协议矩阵、价格/结算规则、布局与数据模型 | 框架依赖清单、版本兼容及配置/迁移归属可核验，产品隔离和缺口处理规则明确，不改框架默认行为 |
| P1 网关闭环 | 可独立接入的调用/网关插件、模型目录、消费 Key、少量真实渠道、兼容 API、流式与取消、基础配额/路由及使用记录 | 外部宿主通过公开接口接入；目标 SDK/客户端契约测试；工具流、错误流、背压、超时、取消与回退边界 |
| P2 商业闭环 | 价格快照、预占/结算账本、充值订单、客户控制台与运营基础页面 | 并发不透支、重复不扣两次、回调乱序可恢复、账目可核对；仅为内部阶段验收，不能单独上线 |
| P3 稳定运营 | 熔断、全局配额、异常补偿、对账告警、成本利润、集群与发布流程 | 至少双 API/多 worker，故障注入、滚动发布、限流协调、长连接排空、账本恢复与性能基线 |
| P4–P8 完整复刻 | 多协议、多模态、网站/Chat、BYOK/workspace、供应商/企业、工具/Agent、SDK 生态及最终对标验收 | 按 [完整对标计划](ai-platform-openrouter-parity.md) 分阶段必交付，不再属于按需候选；实际外部阻塞须明确记录 |

P0–P8 是内部开发与验收顺序，完整平台全部完成并通过 G2/G3 后才上线。套件与应用均须等待框架 v1、v2 完整体成熟及 G0/G1 通过；不能只因 v1 可用便提前启动，也不能以部分插件可用或 P2/P3 商业闭环代替平台完全体。

## 验证与启动前决策

- 使用可控上游模拟器验证流切片、UTF-8/事件边界、错误、延迟、重复回调、取消失败和用量缺失；再做少量授权真实调用，fake 不能代替供应商接入验收。
- 以 PostgreSQL/MySQL 的实际产品支持矩阵决定验证范围；首版可选一个作为产品默认，不降低框架双库要求，也不宣称未测试的产品后端正式支持。
- 覆盖跨客户越权、Key 撤销、敏感日志、共享配额、账本并发与恢复、升级迁移，以及客户创建 Key 到调用和查询账单的浏览器流程。
- 性能记录网关额外延迟、首 Token 时间、活跃流数量、内存/连接预算和结算积压；区分上游生成耗时与平台开销。
- 启动时明确：品牌、上游/模型、协议与目标客户端、收费单位/精度/舍入、余额不足策略、支付方式、隐私留存、部署规模及商业开放条件。无明确决定时提供建议与测试替身，不擅自启用真实付费或外部服务。
- 当前不把 AI 套件或平台应用的实现任务加入框架 `todo.md` 活跃队列；明确启动后在项目分支维护独立任务和状态，框架通用缺口才按框架流程进入框架待办。
