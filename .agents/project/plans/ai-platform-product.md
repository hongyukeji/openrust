# AI 平台独立产品开发计划

> 受众：AI Agent
> 更新：2026-10-25
> 状态：规划，未启动开发；后续须由开发者明确要求启动。
> 摘要：基于 OpenRust 构建独立 AI 平台，最终目标为 OpenRouter 公开功能与使用流程对标，首版先完成网关、计费与客户服务闭环；产品开发必须使用 `projects/*` 分支，不改变框架定位。

## 产品定位

- 暂称“AI 平台（AI Platform）”，最终品牌待定。“API 中转”是产品能力，不作为产品名称；最终目标为 OpenRouter 公开产品功能与关键流程复刻，范围、基线、审计缺口和验收以 [完整对标计划](ai-platform-openrouter-parity.md) 为准；不将首版当作最终目标，也不以软件交付承诺取得相同的供给、用户规模或历史数据。
- 产品版本与 OpenRust v1/v2 独立命名、排期和验收。框架 v1 提供通用运行能力，v2 后台套件可提供管理基础；不能把本产品当作框架 v3 或 v1/v2 的隐含交付项。
- 当前继续框架开发，不创建产品源码、数据库或部署环境，不提前创建产品分支。启动时先核验依赖实际可用程度；基础能力未验收时标记阻塞，不能因产品赶进度削弱框架契约。

## 分支与工作区硬性约束

- 后续产品实现、配置、迁移、前端、测试和部署文件修改必须在 `projects/*` 分支上进行。推荐产品主分支 `projects/ai-platform`，功能分支 `projects/ai-platform-<topic>`；`projects/*` 表示 Git 分支命名空间，不代表必须建立同名源码目录。
- 使用独立 Git worktree 隔离产品开发。开始前核对分支、基线 commit、Git/WIP、其他 Agent 与数据库；不得在框架共享工作区切换产品分支，不移动或清理他人改动。worktree 放置仍遵守项目目录外写入授权边界。
- 框架主线仅保存本产品规划及索引，不纳入产品运行代码、业务表、供应商配置、密钥、前端或产品依赖。不能将整个产品分支合并回框架主线。
- 产品使用独立 Cargo workspace、依赖锁定、配置、迁移命名空间、测试数据与构建部署流程；不把产品加入框架 workspace members/default-members，不改变框架默认 feature、默认启动和 CI 通过条件。
- 推荐通过发布版本依赖框架；发布前本地联调可在产品 workspace 使用显式 path/patch 锁定框架 commit，不能修改框架核心以适配私有调用。具体源码位置在启动 Spec 中确定，本计划不创建目录。
- 产品跟进框架升级时在产品分支验证兼容性；不得为维持产品旧行为冻结、倒退框架公共 API 或降低测试、安全、性能要求。
- 本地 commit 不代表授权合并、推送、发布或部署；这些动作遵守开发者明确授权与仓库边界。

## 框架与产品职责

| 层次 | 可复用或交付内容 | 边界 |
| --- | --- | --- |
| OpenRust v1 | 认证、事务、缓存、限流、HTTP/SSE、取消、加密、审计、幂等、队列、集群与观测 | 以实际公开 API 与验收为准；不依赖内部私有实现 |
| OpenRust v2 | 用户/角色/菜单、日志、任务、监控、生成器及后台组件 | 可选复用；不能把平台客户/渠道/账单模型反向塞进后台通用套件 |
| AI 平台 | 模型与供应商、协议适配、渠道/路由、消费 Key、价格、用量、余额账本、订单、客户及运营界面 | 产品独立数据模型、迁移、业务规则、前后端与文档 |
| 通用改进 | 经验证可普遍复用的框架缺陷修复或扩展能力 | 单独 Spec、变更与测试，不夹带模型名、供应商或定价分支；按框架流程独立审查，不自动回灌 |

分支隔离不能替代架构隔离。遇到框架能力缺口，先判断能否通过公开 Plugin/trait/配置在产品侧实现；确属通用缺陷则形成独立框架任务。不能用永久产品 fork、业务特判、放宽认证或弱化事务来绕过问题。提取通用改进前明确适用场景与兼容性，框架主线的纳入由开发者验收决定。

## 首版功能范围

本节是早期交付子集；最终必交付领域见 [完整能力矩阵](ai-platform-openrouter-parity.md#完整能力矩阵)，不能依据首版表省略后期功能。

| 领域 | 最低交付 |
| --- | --- |
| 客户与消费 Key | 注册/登录、账户状态、Key 创建/哈希存储/一次性展示/撤销、模型白名单与消费上限；管理密钥与调用密钥权限分开 |
| 模型目录 | 统一模型 ID、上游 ID 映射、上下文/输出限制、工具/结构化输出等能力声明、上下架与价格版本 |
| 供应商渠道 | 少量明确目标的真实供应商适配；凭据加密及轮换、连接/超时、健康检查、独立启停和配额；目标清单启动时确认 |
| 兼容 API | 首先实现 OpenAI 风格 `models` 与 Chat Completions、非流式和 SSE；工具调用/结构化输出仅对声明支持且经测试的路径开放，不宣称全部协议兼容 |
| 路由 | 先按能力/上下文/权限筛选，再按明确优先级选择模型与渠道；有界重试/回退、熔断及冷却恢复；禁止无条件重试所有 POST |
| 配额 | 客户/Key/模型/渠道的请求速率、Token 速率、并发与消费预算，明确计数窗口和分布式原子边界；不能只用请求数限流代替 Token 配额 |
| 计量与定价 | 输入/输出/缓存/推理等实际适用计量项、上游成本与客户售价、请求价格快照；无法确认的用量进入待核实状态 |
| 余额账本 | 充值、预占、结算、释放、调账/退款与可追溯流水；金额用定点/Decimal，幂等键与唯一约束防重复，数据库为权威状态 |
| 订单与充值 | 首先完成沙箱或受控测试闭环；真实支付方式、结算单位/精度、退款与费用规则启动时确认；回调验签、重复/乱序处理与对账 |
| 客户控制台 | Key、余额、账单/用量明细、模型目录与接入文档、基础图表；在线试用复用正式配额与计费路径 |
| 运营后台 | 客户/模型/渠道/定价、订单/账本查询、受权限控制的调账、故障与成本利润观察；敏感凭据不可读取导出 |
| 隐私与安全 | 默认不记录提示词和回答正文，元数据留存/脱敏；配置变更审计；上游 URL、远程图片/文件处理防 SSRF，客户端不能自由转发服务端密钥 |

## 请求与结算规则

建议主路径：认证与模型权限 → 配额校验 → 持久化预占 → 渠道选择 → 上游调用/流式转发 → 实际用量核验 → 幂等结算与释放剩余额度。

- 每个逻辑请求、上游尝试、额度预占与结算分别可关联；客户幂等重试与内部渠道回退不能混成一条不可解释记录。
- 已向客户端输出内容后，不无缝切换另一模型并拼接结果；首字节、块间空闲、总时限分别控制，慢客户端有背压与有界缓冲。
- 客户断开应尝试取消上游，但不能假定上游已停止或没有计费。超时同样不证明未执行；失败尝试的上游成本与客户收费分别记录并遵循明确政策。
- 以可信上游 usage 为主要计量来源；本地估算标明模型、算法与版本，不以同一 tokenizer 推算所有模型。流末 usage 缺失、崩溃与未知执行结果进入待核实/补偿状态，不直接按零消费或盲目释放全部预占。
- 价格、单位与舍入规则绑定请求快照；历史账单不随当前定价变化。充值、人工调整与结算保留可审计流水，通过反向分录更正而非覆盖历史。
- 并发预占与最终扣款使用数据库事务/约束，余额及权限关键判断走主库；Redis 仅承担允许的加速/共享配额，不成为无法重建的唯一资金账本。
- 后台任务负责核实、对账与修复，但不能把无持久记录的扣费异步“发出去就算完成”；实际一致性方案先形成 contract。

## 里程碑与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| P0 启动与契约 | 确认开发授权；创建 `projects/*` 分支及独立 worktree；确定来源版本、上游/协议矩阵、价格/结算规则、产品布局与数据模型 | 框架依赖清单可核验，产品隔离和缺口处理规则明确，不改框架默认行为 |
| P1 网关闭环 | 模型目录、消费 Key、少量真实渠道、兼容 API、流式与取消、基础配额/路由及使用记录 | 目标 SDK/客户端契约测试；工具流、错误流、背压、超时、取消与回退边界 |
| P2 商业闭环 | 价格快照、预占/结算账本、充值订单、客户控制台与运营基础页面 | 并发不透支、重复不扣两次、回调乱序可恢复、账目可核对；商业开放前必须通过 |
| P3 稳定运营 | 熔断、全局配额、异常补偿、对账告警、成本利润、集群与发布流程 | 至少双 API/多 worker，故障注入、滚动发布、限流协调、长连接排空、账本恢复与性能基线 |
| P4–P8 完整复刻 | 多协议、多模态、网站/Chat、BYOK/workspace、供应商/企业、工具/Agent、SDK 生态及最终对标验收 | 按 [完整对标计划](ai-platform-openrouter-parity.md) 分阶段必交付，不再属于按需候选；实际外部阻塞须明确记录 |

P1 可进行受控技术验证，不能因转发成功就商业开放；客户付费使用前完成 P2 与相关 P3 安全、集群正确性及恢复门禁。产品可以复用已验收的 v1；是否等待 v2 管理界面由启动时评估，不能为本产品改变框架 v1/v2 排期。

## 验证与启动前决策

- 使用可控上游模拟器验证流切片、UTF-8/事件边界、错误、延迟、重复回调、取消失败和用量缺失；再做少量授权真实调用，fake 不能代替供应商接入验收。
- 以 PostgreSQL/MySQL 的实际产品支持矩阵决定验证范围；首版可选一个作为产品默认，不降低框架双库要求，也不宣称未测试的产品后端正式支持。
- 覆盖跨客户越权、Key 撤销、敏感日志、共享配额、账本并发与恢复、升级迁移，以及客户创建 Key 到调用和查询账单的浏览器流程。
- 性能记录网关额外延迟、首 Token 时间、活跃流数量、内存/连接预算和结算积压；区分上游生成耗时与平台开销。
- 启动时明确：品牌、上游/模型、协议与目标客户端、收费单位/精度/舍入、余额不足策略、支付方式、隐私留存、部署规模及商业开放条件。无明确决定时提供建议与测试替身，不擅自启用真实付费或外部服务。
- 当前不把本产品任务加入框架 `todo.md` 活跃队列；明确启动后在产品分支维护独立任务和状态，框架通用缺口才按框架流程进入框架待办。
