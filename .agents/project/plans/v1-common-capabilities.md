# v1 通用能力补齐计划

> 受众：AI Agent
> 更新：2026-10-25
> 摘要：请求级国际化、出站 HTTP、应用数据加密与本地 key rotation 已独立实现；WebSocket、审计及请求幂等仍待完成。

## 范围与决策规则

- 本计划补充 [v1 总计划](gen1-plan.md)、[性能与开箱即用补强](v1-performance-and-readiness.md) 及 ADR-009 的扩展原则。
- 剩余通用能力均纳入 v1；其余通用能力的补齐与唯一归属见 [覆盖计划](v1-capability-coverage.md)。具体公共 API、配置键、依赖、默认限制、feature 和模块布局仍需设计 Agent 形成 Spec/contract，不能把本计划中的建议直接当成已定接口。
- 优先扩展既有能力 crate 与成熟库；不为每一项能力机械新增 crate，不以自研密码算法、HTTP 协议栈或消息平台替代成熟实现。
- 实施按单功能簇闭环，先完成当前 WIP；新增依赖先记录 `stack.md`，公开名称按 ADR-006 登记。设计与实现职责遵循仓库契约。

## 1. WebSocket

- 交付：复用 HTTP 栈的握手/升级与路由接入，连接生命周期和身份授权入口，可运行收发示例、客户端示例及真实网络集成测试。
- 建议复用 axum 生态；接口采用类型化处理和明确注册方式，不建立独立平行服务器。
- 握手前复用认证/权限，明确 Cookie 或令牌的接入方式、Origin 校验、令牌过期/撤销及连接清理策略；不把 HTTP CORS 自动视为 WebSocket 的来源防护。
- 建议明确消息/帧大小、每连接发送队列、连接数、心跳/空闲超时、慢消费者处理与停机关闭的边界；不以无界队列吸收背压。
- HTTP 统一响应包装仅适用于可处理的握手前 HTTP 响应；升级后的消息协议单独约定，不能将帧强行按普通 HTTP JSON 响应包装。业务消息格式允许应用自定义。
- 集群部署为必须项：连接由所在节点维护，跨节点目标路由/广播必须通过至少一个真实 transport 实现，按 [集群计划](v1-cluster-deployment.md) 验收；业务频道授权可扩展。持久离线历史重放、完整聊天服务仍不自动纳入，不将重连说成自动恢复历史消息。
- 验收：认证拒绝、来源拒绝、消息收发、超限、慢消费者、异常断开、资源释放与优雅停机；记录连接/消息负载的延迟和内存行为。

## 2. 通用加密与密钥轮换

- 已按 [ADR-034](../decisions/adr-034-application-encryption-and-key-rotation.md) 完成：加解密在框架进程内完成，断网可运行；默认和 v1 验收不依赖云 KMS、Vault、第三方加密 API、账户或服务。复用成熟 Rust 密码库不等于依赖外部服务，不自研密码算法。实现审计状态与目标平台性能仍属 v1 发布前复核项。
- 普通开发者最小路径已提供 `openrust key generate`、现有配置机制、`EncryptionPlugin` 与 `Encryptor`；框架负责版本化密文、nonce、完整性校验、错误映射与配置验证。算法、nonce 和标签不要求业务逐次管理。
- 交付：认证加密、安全随机密钥生成方式、密文版本与密钥标识、篡改检测及本地密钥轮换。密码哈希继续由认证能力负责；签名能力按覆盖计划复用，密钥用途隔离方案需设计明确。
- 已固定 AES-256-GCM-SIV/RFC 8452 与随机 nonce，不向普通用户暴露算法/模式/填充组合菜单；`aes-gcm-siv` crate 文档声明目前没有该 crate 实现的完整独立审计，需在发布前复核库审计和维护状态。
- 轮换采用一个当前加密密钥加少量只用于解密的历史密钥。新密文只使用当前密钥，旧密文依据非敏感密钥标识选择历史密钥；重复标识、非法长度与缺失配置应尽早报错。
- 建议密钥配置在启动时加载，轮换按配置更新和正常重启/滚动发布执行；不强制热更新、远程密钥中心或复杂 provider 管理。滚动发布时先让所有实例能解密新旧密钥，再切换写入密钥，验证后退休旧密钥。
- 移除历史密钥前须确认仍需访问的密文及备份可解密；轮换不会自动重加密数据库。提供清楚的迁移步骤和示例，不默认扫描改写用户数据，不自动删除旧密钥。
- 密钥通过现有显式配置和环境变量接入，不内置共享生产密钥，不写入日志或 `config show`。密钥生成命令的名称先按 ADR-006 决策；只向操作者明确输出结果，不擅自写全局配置或修改凭据。
- v1 不建设企业密钥管理平台。将来若确有外部密钥服务需求，再按公开边界扩展，不能使当前应用背负额外流程或必需服务。
- 验收：禁用网络/无第三方账户环境中的加解密、篡改/错误密钥拒绝、非法密文与配置、旧密文跨轮换解密、新密文使用当前密钥、缺失历史密钥的明确错误、日志遮蔽及独立应用最简示例。高风险代码需独立审查，按上层约束选择不同 Provider 或模型。

## 3. 审计事件与记录

- 交付：统一审计事件、显式记录入口、可扩展 sink，以及至少一个真实持久化实现与测试 fake；覆盖账号/权限变更示例，不强制后台 UI。
- 建议区分审计与请求追踪：主体、动作、对象、结果、时间、请求 ID 为核心字段，变更内容按白名单记录并脱敏，避免默认存储完整请求/响应。
- 优先评估数据库持久化与既有事务/事件机制；明确授权失败、事务回滚、写审计失败时的行为，关键审计是否随业务提交须形成 contract。
- 明确保留/清理、访问权限、可信代理后的来源信息及测试隔离；最小实现不承诺不可篡改、法律合规或自动记录所有业务动作。
- 验收：成功/失败/回滚事件、记录故障、脱敏和扩展 sink；数据实现需 PostgreSQL/MySQL 证据。

## 4. 请求幂等

- 交付：供明确选中的变更接口启用的幂等机制，支持身份/接口/键隔离、请求指纹、并发竞争、结果状态与过期策略。
- 建议用数据库唯一约束与事务作为默认基础，无需 Redis；提供可扩展存储边界。不同内容复用同一键、请求处理中和过期后的行为须明确。
- 业务写入与幂等结果能否原子提交须由 contract 保证或说明限制；进程崩溃、超时和租约恢复不能被忽略。对外部副作用仍需供应商幂等或事务 outbox 协作。
- 建议只存有界且脱敏的可重放响应，考虑授权重新校验；不将用户之间的响应互相复用，不无界缓存大文件或流式响应。
- 与限流、防重复点击、数据库唯一性校验区分，不承诺跨所有外部系统的恰好一次执行。
- 验收：并发同键只执行业务一次、不同身份隔离、指纹冲突、失败与崩溃恢复、过期清理，双库验证事务边界。

## 里程碑与交付证据

| 阶段 | 安排 |
| --- | --- |
| M2 收口后至 M3 | 国际化与出站 HTTP 已按 ADR-032/ADR-031 完成；M3 认证/通信接入并补加密、密钥、审计与验证码设计和实现 |
| M4 | 请求幂等与业务事务/队列派发边界落地，审计和通信接入后台任务；不强制所有记录异步化 |
| M5 | 完成 WebSocket 与有界资源/可观测性集成；前置认证与相关 HTTP 配置已有明确契约 |
| M6 | 各项能力在独立生成项目和聚合宿主验证；文档、测试、feature 矩阵、扩展示例、性能与生产说明齐全 |

代表性应用按能力实现顺序逐步覆盖，只有实际执行验证并更新 crate 事实后才能标记完成。正式发布、供应商实发、凭据写入等操作不因本计划获得额外授权。

## 通用能力补齐与后续边界

SSE、薄通知编排、常用任务链/批处理，以及 Session、API 输出、缓存与锁等通用能力已纳入 [覆盖计划](v1-capability-coverage.md)，不再仅列为后续候选。业务通知中心/UI 归 [v2 现成后台](v2-admin-platform.md) 核心；跨节点在线投递归 v1 集群必须项；持久离线重放、更多数据库及 OAuth/SSO 归 v2 评估候选，任意 DAG 工作流不作为两个版本核心承诺。通用底座不因这些边界而缺少已有明确交付范围的能力。
