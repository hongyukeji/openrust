# 完整实现后的发布仓库整理

> 状态：仅规划；在阶段一固定Laravel+正式modules基线及已纳入阶段二框架增强全部验收后领取，不在开发中执行。

## 目标与依赖

对外提供反映最终架构的代码、文档和按最终功能簇组织的 Git 历史，减少开发期反复调整带来的阅读负担。依赖[总计划](laravel-rebuild.md)及[唯一队列](../todo.md)中[阶段一+已纳入阶段二](laravel-rebuild.md#两阶段框架主线)的V1框架/扩展范围真实服务与生产门禁关闭（排除[冻结V2](v2-admin-platform.md#冻结与开工闸门)与未启动产品，不无限等待它们）；不能用整理历史代替功能完成，或提前以清理名义丢弃 WIP。精选扩展仅按已批准的交付范围验收，不无限等待未启动产品或未来版本。

这是完整实现后、首次正式远程交付前的独立功能簇。用户已要求最终整理后推送；本轮仅记录，不授权立即改写历史或执行推送。实际操作前依据当时本地/远程状态写操作 Spec，明确目标远程、分支与提交映射；不默认 force push、删除远程或改写已被他人依赖的历史，涉及这些情况按 AGENTS 授权边界处理。

## 整理范围与顺序

1. 冻结已验收交付快照，确认无未交接 WIP、在途写入或待领取的本次范围缺口。记录原 HEAD、最终文件树、测试命令及结果；先生成可恢复的本地历史备份并校验可读取，再开始历史整理。备份位置不得污染最终源码；项目外持久写入按授权边界处理。
2. 以最终职责盘点文档和 ADR：保留必要的目标、最终有效决策、关键取舍、Rust 适配依据、安全边界、第三方来源/许可证与当前验收限制。合并同义和重复内容，移除已失效的草案、旧提示词、迁移中间态和开发流水；删除受控文件走 git rm，不把有效的失败边界或未解决缺口当冗余删除。
3. 统一 README、生成模板、公开 API 文档、配置示例、贡献指南及 Agent 规则。ADR 按最终主题收敛，修复编号引用、替代关系、路径与锚点；不要求抹掉所有历史理由，也不另存一套面向用户的开发过程档案。
   Agent 记录同样按成品整理：`AGENTS.md`、`.agents/project/` 和项目 skills 只保留最终有效目标、规范、架构事实、后续维护流程和必要验收边界；清除开发流水、旧提示词、已完成任务堆积、失效方案及过期进度，修复旧提交 hash 引用。已完成发布范围的实施计划不再作为活跃待办，未来版本需求仍明确保留。仅本机使用的守护日志与状态继续忽略 Git，不随整理纳入发布；不删除仍在运行任务的状态，也不借此清理项目外的用户记录。
4. 根据最终依赖顺序设计提交：基础结构与内核、HTTP、数据/模型、安全、缓存/存储、通信、队列/调度、扩展和开发工具等，以实际成品边界为准。每簇包含相应代码、文档和高价值测试，避免一个巨大初始提交或只有名字的切分；不得伪造开发日期、测试结果或来源归属。记录原提交到新功能簇的可追溯关系，承认旧 hash 在重组后失效。
5. 在本地组织并审查新历史：最终文件树应与整理后获准发布的快照一致；有意义的依赖节点可构建，拆分次序不引入缺失依赖。历史备份和来源归属不得丢失；具体 Git 操作方式在执行 Spec 决定，不提前创建分支、孤儿历史或第二源码仓库。
6. 在新历史最终 HEAD 复跑适用完整门禁：格式、静态检查、测试、文档、依赖与许可证检查、生成项目、默认启动、PostgreSQL/MySQL 及适用 Redis/SQLite、多节点与迁移恢复。检查全历史中的凭据、临时产物和不应发布的本地运行记录；既有已泄露凭据按真实情况处置，单纯删历史不视为撤销秘密。
7. 交付清晰的差异、提交序列、有效 ADR 目录、验证证据及残留限制。确认当时远程状态、发布范围和授权边界后，再按用户本次要求推送整理后的历史；推送不等于发布 release、打 tag 或发布包，不附带执行这些动作。

## 完成标准

- 最终代码和文档只描述有效成品，开发者能从入口快速定位功能、配置和扩展方式。
- Git 提交按实际功能簇及依赖组织，最终树一致性与恢复备份已验证，许可证和来源归属完整。
- 文档去重、旧引用扫描及完整实现验收通过，公开限制未被隐藏；整理、验证与推送分别报告。
- 未覆盖他人工作；对外动作仅在此后置任务真正满足前置条件时执行。本计划本身不表示历史已整理或已推送。
