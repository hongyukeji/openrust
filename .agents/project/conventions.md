## 方案调研与复用

- 设计新功能、重构或解决技术问题前，先核对项目已有实现和固定 Laravel 基线，再联网调研 Laravel 生态、GitHub 热门项目及相关官方资料，查找已有的成熟解决方案。本原则适用于各类开发任务。
- 优先借鉴或复用经过实践验证的设计，遵循 Laravel 的命名、结构和使用习惯，避免重复造轮子和过度设计。以源码、文档和测试判断方案是否适合当前需求，兼顾维护状态、许可证、依赖成本和 Rust 适配；不以 Star 数作为唯一依据，也不为复用而引入无必要的依赖或抽象。
- 在对应设计或验收记录中简要注明参考项目、链接、版本或提交、采用理由及必要差异。生态方案与固定 Laravel 基线冲突时，仍以项目的上游契约为准；联网不可用时明确记录调研限制，不将未经核实的方案写成已验证结论。

## Laravel 到 Rust 的移植原则

- 把固定 Laravel 基线当作从 PHP 翻译到 Rust 的原文。像多语言翻译一样，保留原意和结构，用 Rust 表达相同的机制。默认装配、生命周期顺序、默认值和用户可观察行为均按上游保留，让熟悉 Laravel 的开发者可以逐项对照 PHP 源码阅读 Rust 实现。
- 对应的公开方法名、类型名、参数名、配置键、环境变量名和内部变量名，凡 Rust 能直接表达，尽量保留 Laravel 的原名和大小写。例如 `$basePath` 对应 `basePath`，PHP 命名参数 `web:` 对应 Rust Builder 的 `.web(...)`，`APP_BASE_PATH` 保持原样。
- PHP 的命名参数、动态加载、异常等按需转换为 Rust 的 Builder、静态注册、`Result` 和异步接口，保留原有职责和调用时机。对应方法保留 Laravel 的拼写和大小写，例如 `withRouting` 与 `withExceptions`。
- Rust 机制能带来更好的性能时，可以替换内部实现，前提是保持 Laravel 的核心机制、公开契约、默认值和错误行为。以针对性的测试验证等价行为，以测量支持性能收益。对每项语言适配或性能取舍，记录对应的 Laravel 源码、采用的 Rust 实现、原因和验证结果，并在交付时告知用户。

## 骨架与开发顺序

1. **骨架按正式版设计。** 编码前按[固定 Laravel 基线](plans/laravel-rebuild-baseline.md)确定应用、框架和扩展的边界，明确目录、文件路径、模块、公开导入路径、类型名、配置键、命令和三语文档入口。已确认的结构可先预留，尚未确定的契约列为待定。
2. **命名跟随上游。** 公开接口及对应的内部变量按[移植原则](#laravel-到-rust-的移植原则)命名。上游名称中含 Laravel 品牌段时，将品牌段替换为 OpenRust。Rust 的文件和模块按语言惯例组织。因语言或运行时限制调整接口时，记录对应关系、具体约束和等价行为的验收方式。可参考固定 Goravel 版本的跨语言实现。
3. **Artisan 先定契约。** 逐项核对命令名、命名空间、公开别名、参数及顺序、选项、默认值、帮助、输出、退出码和副作用。目录和说明可以先行，未实现的命令标记为占位，执行时明确失败。相同命令合并，行为以 Laravel 为准，Goravel 独有命令单独标明来源。机器可读输出也按契约核对。
4. **按依赖逐簇填充。** 每一簇先核对固定源码、文档和适用的上游测试，再填实现、独立测试与对应文档。验收覆盖实际入口、默认行为和关键失败路径。骨架定稿、实现完成和验收通过分别记录。

## 代码与测试目录

- 应用代码放在根应用的对应目录，框架源码放在 `vendor/openrust/framework/`。
- 测试代码单独存放。根应用测试放在根目录的 `tests/`，crate 测试放在所属 crate 的 `tests/`。

## 默认应用与扩展装配

- 默认 `app/providers/` 只登记应用自身必要的服务，不提前注册可选扩展、示例业务类型或包迁移；`#[cfg(feature = "…")]` 只控制编译，不能作为把示例写入默认骨架的理由。`bootstrap/providers.rs` 只列应用 Provider。
- 扩展通过已有 `[package.metadata.openrust.discovery]` 与 `openrust_providers()` 参与包发现，自身 Provider 负责服务绑定、配置合并及适用的迁移登记。需要发布或安装的应用配置／路由／模型由显式安装器按已确认契约生成；不为新扩展继续增加根 AppServiceProvider 分支。
- 包默认配置和可发布模板放在所属包目录，由包 Provider 合并；默认根 `config/` 不预装可选包配置，不为可选包增加 feature 分支。根应用保留核心驱动连接配置，不因此装配可选服务端。显式安装通过现有发布与源码锁机制接入编译型配置，重复安装保留应用定制；OIDC 身份提供方等业务示例只在显式选用后生成。配置缓存命中时跳过包默认配置的环境读取与合并，以缓存快照为准。
- 业务示例、集成测试专用类型和装配放在文档或所属包的 tests／fixtures 中。用户应用实际采用某个业务组时，才在该应用的 Provider 中显式注册；框架仓库默认应用不承载所有扩展的演示接线。
- 验收同时检查启用／关闭扩展、包发现、注册与启动不访问未迁移数据库、迁移登记及自定义配置边界。运行 `cargo +1.94.0 test --test application_skeleton`，检查根应用 Provider／业务目录的扩展引用及根配置的可选包预装；配置验收同时覆盖包独立使用、应用覆盖、缓存快照及显式安装保留定制，阻止 Provider 再出现扩展引用或 feature 分支；该测试约束仓库默认骨架，不限制用户应用的正常定制。

## 旧版实现复用

1. **先定契约，再查旧版。** 实现前优先查阅同级 `openrust-v0.x` 工作树的 `v0.x` 分支。没有该工作树时，在当前仓库用 `git show v0.x:<仓库内路径>` 查阅。没有本地分支时，可用已有的 `git show origin/v0.x:<仓库内路径>`。两种方式均无需切换分支。记录对应源码、测试和修复的提交与路径，来源不可用时明确记录。
2. **按职责提取。** 可直接复用符合契约的内部实现、驱动适配和回归用例。旧版公开接口或目录与当前契约不一致时，提取有用的实现并接入当前模块。涉及依赖或跨组件调用时，核对许可证、Rust 版本、生命周期和安全边界。
3. **新主线按当前契约交付。** 每批只引入对应功能所需的代码和测试。旧 API、配置键、数据格式及迁移历史不作为兼容目标。与固定基线冲突的行为按当前契约修正，旧版缺口按依赖顺序补齐。
4. **用当前入口重新验收。** 复用旧测试时同步更新路径、接口和断言。以固定上游用例、当前应用入口及失败路径验证本批行为，分别记录复用范围、差异和实际验收结果。

## 文档规范

1. **章节对齐上游。** 按[固定 Laravel 文档基线](plans/laravel-rebuild-baseline.md#文档导航核对)组织章节和阅读顺序。英文、简体中文、繁體中文使用相同的章节相对路径和顺序。OpenRust 独有能力在导航中标为「扩展」。
2. **同一内容只维护一处。** 一个主题只有一个正文页面。其他章节用相对 Markdown 链接引用，确保在 GitHub 和部署到子目录的 VitePress 站点都能跳转。上游多个入口指向同一主题时，保留对应导航入口，共用正文。
3. **正文面向应用开发者。** `docs/` 介绍安装、配置、公开接口、用法、示例、错误行为及影响使用的支持限制。语言适配说明应解释调用方式、所有权或运行时约束。贡献指南可说明贡献流程。正文不放内部任务编号、交付批次、进度与待办、代理交接、源码对账、验收经过、测试计数、临时环境、清理记录及无关的性能免责声明；不以“本批完成”“后续单元交付”等过程用语描述功能。
4. **内部材料按职责归档。** 开发计划和待办放在 `.agents/project/plans/` 及相应计划文件，设计取舍放在对应架构或主题记录，验收环境、命令、结果和证据放在 `.agents/project/audits/` 对应主题目录。混合段落先提取开发者需要的操作和限制，仅将仍有效的计划、设计决定或待办并入既有对应主题。历史原文和差异由 Git 保存，不另存逐页副本、补丁、文件清单或可从提交重建的源码哈希。工作区临时备份不作为长期验收材料，也不逐批复制到审计目录；清理未跟踪补丁前，须逐项确认改动已提交、仍存在于工作区或已被现行实现取代，无法确认的独有改动继续保留并注明用途与清理条件。一次性整理只保留必要的范围、验证结果和来源提交号；仅在复现或独立审计确有需要且 Git 无法提供时保存额外证据。开发者正文不依赖 `.agents/project/`、代理指令或验收日志才能理解；文档站维护与验收命令见[维护指南](guides/documentation.md)。
5. **功能验收后同步正文。** 按 Laravel 对应章节介绍默认行为、配置和用法。Rust 示例与 Artisan 命令须实际验证。因 Rust 语言或运行时产生的差异须说明原因，并以测试验证等价行为。尚未提供的导航章节写明具体支持边界和已有原生入口，不使用空白占位，不把包骨架或仓库内部测试工具写成可用框架能力。发布说明只保留面向开发者的版本、兼容范围、变更及迁移影响，历史复验流水和待验矩阵归入内部记录。
6. **三语一起校验。** 同步更新三个语言版本的正文和导航，统一术语、标题层级与章节顺序。检查章节路径和内部链接，运行 `node docs/tests/check_content.mjs`、文档构建及现有浏览器验收。自动检查之外，逐段判断内容是否服务于应用开发者；站点命令见[维护指南](guides/documentation.md)。

## 配置文件注释

- **配置组。** 在每组上方使用 Laravel 风格的简体中文 `/* … */` 块注释，标题上下加横线，标题和正文各行以 `|` 起首。说明用途和对应环境变量，按需写明默认值、回退行为或覆盖顺序。调整配置时同步更新注释。 [应用配置](../../config/app.rs)
- **辅助方法。** 优先级、回退或解析规则不明显时，在方法声明正上方使用多行简体中文 `/* … */` 块注释。正文每行以 `*` 起首，不加分隔线。先说明用途，再交代适用条件、处理顺序和必要的错误行为。 [环境变量读取](../../config/env.rs)

## 验收清单

- **Rust 代码。** 在仓库根目录使用最低支持工具链 Rust 1.94.0 运行 `cargo +1.94.0 fmt --all --check` 和 `cargo +1.94.0 clippy --workspace --all-targets --locked -- -D warnings`。按改动验证实际入口、默认行为和关键失败路径。骨架改动验证公开导入和签名编译，分别记录骨架、实现与行为验收状态。
- **方言修饰符。** 按固定 Laravel grammar 分别核对每个驱动的输出和忽略行为；某项仅由 MySQL 输出，不代表其他驱动应报错。共享迁移使用 `first`／`after` 时，非 MySQL 驱动忽略排序提示，保留其原生列顺序。回归同时覆盖跨驱动 SQL、实际迁移和数据保留。
- **测试范围。** 日常使用 Rust 1.94.0；数据库覆盖 PostgreSQL 18、MySQL 8（现有夹具为 8.4）、SQLite，缓存覆盖 Redis 8、database、file。执行与改动相关的定向测试：共享数据库行为在三库分别验收，共享缓存行为在三种缓存驱动分别验收；database 缓存涉及 SQL 的路径同时覆盖三库。驱动专属能力核对对应驱动和其他驱动的适用行为，不将单一驱动通过扩展为全部通过。筛选、隔离和版本核对见下文；缺少覆盖如实列为未验，不延后到发布才发现日常三库兼容问题。
- **文档。** 纯指引改动检查引用、路径和锚点。文档站改动按[维护指南](guides/documentation.md)在本地构建三语站点，并运行[浏览器检查](../../docs/tests/check_browser.mjs)，覆盖 `/` 与 `/docs/`。
- **模拟与实机边界。** 真实目标清单包括第三方账号/权限、最终收件人、商户资金、物理设备、平台后端和正式部署。先复用成熟服务及已有夹具运行实际HTTP/浏览器/Artisan与失败恢复；使用REQUIRE或显式入口防止缺服务静默跳过。每轮SQS FIFO使用独立队列，避免去重窗口污染。证据注明模拟器/客户端版本、源码快照、实际驱动和TLS终止位置，不能把本地协议、虚拟认证器或分开的TLS与明文链路写成真实供应商/设备/全链路TLS通过；人工发布批准始终单列。
- **记录。** 记录实际执行的命令、环境和结果，说明跳过项或外部服务限制。检查本批差异及空白错误，暂存、提交和推送遵循当次授权。
- **验收收尾。** 每批验收保存记录后，确认产物归属本批、无人占用且可重建，再直接删除，跳过系统废纸篓或回收站。复查磁盘并记录实际释放和剩余空间，再开始下一批。保留源码、未提交改动、验收记录、数据库及数据卷、共享缓存和发布产物。清理容器时，`docker container rm` 和 `docker compose down` 均省略 `-v`／`--volumes`。操作前后核对数据卷，匿名数据库卷同样保留。

### 构建产物管理

- `.cargo/config.toml` 使用 Cargo 原生 `build.incremental=false`、`jobs=3`，使根应用与 IDE 自动检查同样受控；不只依赖验收 shell 临时设置。环境变量和命令行能够覆盖原生配置，因此代理不得开启增量编译或提高并发来绕过本规则。IDE仍保留默认调试信息，不修改全局工具链。
- 本机（macOS/Linux）代理的 Cargo 验收统一从主工作区调用[构建入口](../../tests/build_session.py)：`python3 -B tests/build_session.py --source /绝对路径/隔离源码 -- <命令>`。源码仍按固定 Git 归档加核定改动准备；入口拒绝活跃工作树，在源码的父目录创建唯一空 target，向全部子进程传递 Rust1.94.0、jobs=3、增量关闭和dev/test debug=0。同批测试／Clippy／Rustdoc／浏览器检查放在同一命令或脚本中，最后退出时自动清理；日志和要交付的API／站点须先保存到 target 之外。不覆盖其 CARGO_TARGET_DIR，不使用 --target-dir 绕开回收，不从其他 target 克隆整份缓存。Windows实机仍按对应宿主的隔离验收与清理入口执行，不能声称此POSIX进程入口已在Windows验证。
- 构建入口使用本项目进程锁避免多个受管批次同时增长；启动前和运行中检查可用空间，触及31,250,000 KiB即拒绝或终止本批并清理。根 target 超过8 GiB时拒绝新验收，先核对用途和占用再清理。此8 GiB为根IDE缓存的验收准入上限，不能将其说成IDE自身的磁盘配额。闲置清理不删除Cargo下载缓存／源码／数据库／卷／发布产物，不中断其他人的在用任务。
- 正常退出、命令失败、SIGINT及SIGTERM都回收本入口创建的 target，信号同时终止本批子进程；不接受外部删除路径。SIGKILL、断电或宿主崩溃无法执行finally：下一批前必须盘点本项目临时目录（包括 `openrust-build-target-*`）与根 `target`，确认所有者已退出、无进程占用且可重建后清理，不能以“任务失败”为理由直接开启下一轮。历史手动构建的独占 target 同样核对收尾；运行日志和开发数据不随目录名一并删除。
- 根 `target` 属于IDE与手工命令的另一类缓存，不能以“只清自己的临时目录”将其永久排除。清理根debug缓存前取得 `target/debug/.cargo-lock` 的排他锁并检查进程占用；持锁清理时保留锁文件本身，防止另一Cargo进程通过新建锁文件进入。不能只执行一次 `df` 或只统计 `/tmp` 就声称完成全项目清理。
- 生命周期回归：`python3 -B tests/build_session_lifecycle.py -v`。只执行入口自身的轻量进程测试；不为验证清理再次构建整个workspace。记录清理前后df读数，并区分目录占用与实际磁盘回收量；APFS共享块及并行写入可能使两者不同。

### 日常数据库与缓存验收

2026-11-21 用户将日常开发与验收调整为 PostgreSQL 18、MySQL 8、SQLite 三库，以及 Redis、database、file 三种缓存驱动，覆盖此前仅 PostgreSQL 或仅 MySQL 的日常验收规则。数据库其他版本、SQL Server 和商业嵌入端点仍按发布矩阵验证。仓库不通过工具链文件固定版本；保留 `Cargo.toml` 的 `rust-version` 声明最低版本，日常验收显式使用 `cargo +1.94.0`。通过验收环境分别选择数据库与缓存驱动；本地 `.env` 的默认连接不代表完整验收范围，也不要求切换或搬迁已有开发数据。

临时数据库验收使用 `python3 -B tests/postgres_acceptance.py -- <验收命令>`，本地 Docker 须已有 `postgres:18`。入口核对镜像数据目录 `/var/lib/postgresql`（包含 18 的版本化 PGDATA），以 1 GiB tmpfs 承载数据，使用随机回环端口、临时凭据和批次标签。通过同一账号／数据库的 `SHOW server_version_num` 确认 18.x 后，向命令提供 `OPENRUST_TEST_POSTGRES_URL`、`OPENRUST_REQUIRE_POSTGRES=1` 和 `OPENRUST_ACCEPTANCE_POSTGRES_CONTAINER`。不把开发库连接传给会建表／删表的测试。

现有定向测试读取各自的 URL／REQUIRE 变量，调用时显式映射并精确筛选；未适配 PostgreSQL 的 MySQL 专项不能只改变量后声称通过，也不能将缺变量导致的跳过计作成功。例如：

```sh
python3 -B tests/postgres_acceptance.py -- sh -c '
  export OPENRUST_TEST_POSTGRES_JSON_URL="$OPENRUST_TEST_POSTGRES_URL"
  export OPENRUST_REQUIRE_POSTGRES_JSON=1
  cargo +1.94.0 test --locked -p openrust-framework --test database_query \
    json_predicates_run_on_postgres_in_both_prepare_modes -- --exact
'
```

MySQL 日常验收使用 `python3 -B tests/mysql_acceptance.py -- <验收命令>`，现有夹具核对 MySQL 8.4，属于 MySQL 8 验收范围。SQLite 使用独立临时数据库文件或适合测试生命周期的内存数据库，记录实际版本；不复用开发数据库文件。三库分别运行同一受影响行为的用例，连接变量按各测试实际读取的名称映射。

Cargo 仍在独立源码快照与独占 target 中运行，不在活跃工作树构建；增量关闭，遵守当前交接中的 jobs、32 GB 磁盘停线与清理规则。会在内部运行 Cargo 的安装器、生成应用和验收夹具，须向子进程传递 `RUSTUP_TOOLCHAIN=1.94.0` 并核对实际工具链；仅给外层 Cargo 加 `+1.94.0` 不能保证内层构建使用相同版本。用 `-p`、`--test` 和 `--exact` 定位函数，显式核对每项测试及辅助夹具连接的驱动，分批执行以控制资源；不依赖无筛选 workspace 测试偶然覆盖三库。

缓存共享行为分别通过 Redis、database、file 实际驱动验证，按改动覆盖读写、过期、删除及锁等相关路径。Redis 使用专属隔离实例，先核对 `INFO server` 为 8.x 与 `PING`；不在开发 Redis 执行清库或修改 ACL。database 缓存使用对应三库的隔离数据库／表，file 缓存使用批次专属临时目录；不对开发缓存执行清空操作。仅影响某一驱动的变更可定向验收，但须说明范围，不能计为其他驱动已通过。

入口完成、失败或收到可捕获取消信号后只回收当次标签容器，不删除数据卷。生命周期回归运行 `python3 -B tests/postgres_acceptance_lifecycle.py -v`。强制杀死或 Docker 不可用时按日志批次标签复核收尾。MySQL 夹具及其生命周期测试同样用于日常验收。不删除开发数据库、开发缓存或数据卷；仅清理本批独占的 SQLite 文件和 file 缓存临时目录。
