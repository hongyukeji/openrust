## 上游参考

- 以[固定 Laravel 基线](plans/laravel-rebuild-baseline.md)确定目录、公开契约、默认值和可观察行为。

## 版本来源与发布

- 框架及同步发布的官方包统一继承根 `Cargo.toml` 的 `[workspace.package].version`，成员使用 `version.workspace = true`；第三方 vendor、协议元数据和独立测试应用的版本保留各自语义。
- 默认应用骨架也继承此版本；业务应用可单独声明 `[package].version`，`app.version`／`APP_VERSION` 与框架 `App::version()` 分开。修改版本后重新构建；配置缓存须重新生成才能刷新默认应用版本。
- 发版只修改统一入口，用 Cargo 完整 metadata 解析刷新锁文件并审查差异；运行 `tests/workspace_versions.py` 的隔离单点升级与独立应用检查。历史发布记录不批量改写。三语发布页使用 VitePress 原生 TOML region，不另加版本文件、解析器或手工数字。
- 当前 `publish = false` 保持不变。源码分发保留 workspace 元数据；注册表归档使用 Cargo 的标准清单归一化，不能只复制继承版成员清单并假定其可独立解析。

## 方案调研与复用

- **先核对，再选型。** 设计新功能、重构或解决技术问题前，先核对项目已有实现、固定 Laravel 基线及旧版可复用代码。涉及新设计、新依赖或现有方案无法满足需求时，联网调研官方资料、Laravel 生态、固定 Goravel 参考及成熟 Rust 项目。调研深度与改动范围和风险匹配；注释修正、局部修复及已有方案内的调整，可沿用仍适用的调研结论，出现新差异或失效证据时再补查。
- **基线优先，按质量复用。** 公开契约遵循固定 Laravel 基线及项目已确认的 Rust 适配，第三方方案作为实现参考；发生冲突时按项目既定契约处理。以源码、文档和测试评估适用性，兼顾维护状态、许可证、依赖与维护成本及 Rust 适配，不以 Star 数作为质量结论。优先复用现有机制、成熟组件和回归用例，避免重复造轮子，不为复用引入无必要的依赖或抽象。
- **留依据，用行为验收。** 在对应设计或验收记录中简要注明参考项目、链接、版本或提交、采用理由及必要差异；复用已有调研时直接引用原记录。实现后用实际测试验证契约和可观察行为，性能收益须有测量依据。联网不可用时明确记录调研限制，不将未经核实的方案写成已验证结论。

## Laravel 到 Rust 的移植原则

- 把固定 Laravel 基线当作从 PHP 翻译到 Rust 的原文。像多语言翻译一样，保留原意和结构，用 Rust 表达相同的机制。默认装配、生命周期顺序、默认值和用户可观察行为均按上游保留，让熟悉 Laravel 的开发者可以逐项对照 PHP 源码阅读 Rust 实现。
- Rust 标识符采用原生命名：类型／trait／枚举及变体用 `UpperCamelCase`，函数／方法／变量／参数／字段／模块／宏用 `snake_case`，常量与静态变量用 `SCREAMING_SNAKE_CASE`。例如局部变量使用 `base_path`，Builder 方法使用 `with_routing`。2026-11-23 用户确认此规则替代此前保留上游标识符大小写的要求；现有代码按[命名统一计划](plans/rust-naming-unification.md)分批迁移，不将待迁移代码视为已完成。
- PHP 的命名参数、动态加载、异常等按需转换为 Rust 的 Builder、静态注册、`Result` 和异步接口，保留原有职责和调用时机。公开 Rust 方法采用 `with_routing`、`with_exceptions` 等表达；命令、配置键、环境变量、序列化字段、事件字符串、模板表达式和外部协议按各自既定契约保留，不能随 Rust 标识符机械替换。必要的命名例外限定最小范围并记录原因，迁移范围和验收见上述计划。
- 所有 workspace 包通过 `[lints] workspace = true` 继承三种命名 lint 的 `deny`；不再为旧大小写保留命名豁免。`python3 tests/rust_naming.py` 核对成员策略和真实 Cargo 正反消费者。宏展开声明、生成源码和三语 Rust 示例须一起验收，FFI／外部字段与字符串契约独立裁决；历史验收不改写。
- Rust 机制能带来更好的性能时，可以替换内部实现，前提是保持 Laravel 的核心机制、公开契约、默认值和错误行为。以针对性的测试验证等价行为，以测量支持性能收益。对每项语言适配或性能取舍，记录对应的 Laravel 源码、采用的 Rust 实现、原因和验证结果，并在交付时告知用户。

## 对齐审计与缺口闭环

1. **按所属类型核对契约。** 以固定上游的命名空间／类型／方法为核对单位，映射到本地实际公开类型与入口，检查可见性、参数、返回值、默认值、装配、执行时机、状态隔离和错误行为。继承、trait、宏生成及 Facade 转发须追踪到实际实现；其他类型或包中的同名方法不能证明入口存在。例如 HTTP 客户端的 `post` 不能证明路由器提供 `post`。
2. **扫描只提供线索。** 关键词、正则、全仓名称索引和声明数量只用于建立候选；即使使用语法树，也不能直接证明行为等价。区分名称命中、入口确认、实现核对及行为验收，不把 `name_declared_in_rust` 等初筛结果当成已对齐。存在性和语义分别核对，不能只检查名称缺失项而跳过同名项。
3. **逐模块落实，不挂空泛总任务。** 在已有计划或审计账本中，把承诺核对的模块／类型公开接口逐项关联到本地入口、裁决、测试和剩余事项；人工核对或现有工具均可，不为此另造审计框架。尚未逐项复核的记录明确为待核对，不能只放进“全量复核”总任务而在模块收尾时遗漏。修复过程中发现的新缺口同步补入清单，检查同类型相邻方法和相关 Contracts／Facade／调用方；不能把最初选出的缺陷清单当作完整上游接口集合。
4. **遇到绕行写法必须追查。** 因公开入口缺失或行为不符而改用通用接口、底层对象、手工拼装或修改测试时，先核对是否为框架缺口。在本次授权范围内直接修复并回归；临时绕行保留明确任务、原因、影响和后续验收要求，外部阻塞或超出授权的部分如实列出。不能为了让当前用例编译或通过而悄悄降低公开契约。例如用 `match([POST], ...)` 完成请求分发，不代表 `Route::post(...)` 已提供。
5. **从开发者入口验收。** 验收须实际编译并调用承诺的公开导入和方法，再核对可观察行为及关键反例；不能只测试被委托的内部实现。底层类型和 Facade 都属于交付范围时，分别确认可用性，并核对受影响的生成器、脚手架、默认用法与三语示例。薄封装可采用共享或参数化用例，避免重复测试，但不能让通用入口替代专用入口的覆盖。
6. **差异必须有依据。** Rust 适配记录具体语言约束、上游契约、替代表达及实际验证；简单缺方法、尚未实现或尚未验收不能包装成语言限制或“不适用”。有等价内部机制也不能据此省略可以直接表达的上游公开入口。用户确认的扩展与上游对齐分别记录。
7. **完成结论受覆盖范围约束。** 声明模块完整对齐前，该模块全部约定范围的公开接口须有明确裁决；存在待核对、缺实现或缺验收的项时，保留未完成状态及具体剩余。局部修复可以按已验范围交付，不据此关闭模块或全仓。编译、Clippy、旧测试通过和大量对照数量均不能替代尚未覆盖的入口；源码变化后复核受影响结论。收尾列出实际完成项、未完成项及阻塞，不能以改状态文字或汇总数量代替证据。

## 骨架与开发顺序

1. **骨架按正式版设计。** 编码前按[固定 Laravel 基线](plans/laravel-rebuild-baseline.md)确定应用、框架和扩展的边界，明确目录、文件路径、模块、公开导入路径、类型名、配置键、命令和三语文档入口。已确认的结构可先预留，尚未确定的契约列为待定。
2. **职责对齐，Rust 命名统一。** 公开接口及对应的内部变量按[移植原则](#laravel-到-rust-的移植原则)采用 Rust 原生命名，以对应关系和行为验收核对上游，不要求大小写相同。名称中的品牌段按[品牌表述](#品牌表述)逐项判断，既有公开契约不因文案清理改名。Rust 的文件和模块按语言惯例组织。因语言或运行时限制调整接口时，记录对应关系、具体约束和等价行为的验收方式。可参考固定 Goravel 版本的跨语言实现。
3. **Artisan 先定契约。** 逐项核对命令名、命名空间、公开别名、参数及顺序、选项、默认值、帮助、输出、退出码和副作用。目录和说明可以先行，未实现的命令标记为占位，执行时明确失败。相同命令合并，行为以 Laravel 为准，Goravel 独有命令单独标明来源。机器可读输出也按契约核对。
4. **按依赖逐簇填充。** 每一簇先核对固定源码、文档和适用的上游测试，再填实现、独立测试与对应文档。验收覆盖实际入口、默认行为和关键失败路径。骨架定稿、实现完成和验收通过分别记录。

## 代码与测试目录

- 应用代码放在根应用的对应目录。`vendor/` 按 Cargo 的单层布局组织，每个包直接放在 `vendor/<Cargo 包名>/`，例如 `vendor/openrust-framework/` 和 `vendor/openrust-ai/`。`cargo vendor` 生成的依赖目录按 Cargo 的规则处理同名多版本。工作区成员按 `vendor/openrust-*` 发现。见[待办](todo.md#vendor-目录统一)和 [Cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html)。
- 测试代码单独存放。根应用测试放在根目录的 `tests/`，crate 测试放在所属 crate 的 `tests/`。
- 构建脚本自动注册清单时，供应用装配调用的入口函数声明放在正式源码，生成文件只提供模块和清单数据。保留最小可见性，并验证编译、同级模块调用及 IDE 导航；不要通过扩大可见性、关闭检查或手改生成文件消除诊断。

### 上游对照脚本与许可证

- Git 跟踪及发布源码不包含 `.php` 文件；不得为对齐上游而让应用构建、启动或运行依赖 PHP／Composer。普通 Rust 回归读取已保存的必要对照数据，保留实际 Rust 消费者与来源说明。
- PHP 对照脚本仅作本地开发工具，由 `.gitignore` 排除；既有脚本取消跟踪时保留本地内容，新建脚本、固定上游源码及依赖、临时运行环境和原始输出统一放在项目根 `target/tmp/`，遵守[构建产物管理](#构建产物管理)。不以修改扩展名或嵌入其他文件的方式继续提交 PHP 脚本。
- 历史审计中的 PHP 路径与命令保留为当时的验收记录，不代表新克隆仓库包含脚本。重新执行上游复验须另行准备本地脚本、固定源码与依赖；缺少这些材料时明确记录无法复验，不能把已保存数据或 Rust 回归通过当作重新执行上游通过。
- 修改预期数据时，须以固定上游重新生成或说明具体来源与变更依据，并核对实际消费者；不能只修改预期值让 Rust 测试通过。记录固定版本、复现条件、对照桩与未执行的上游行为，避免因取消跟踪而夸大证据完整性。
- 第三方版权和许可证原文保持完整；纯文本许可证使用 `LICENSE` 或明确的许可证文件名，不使用 `.php` 等代码扩展名。调整名称时同步来源说明、代码注释与第三方声明，不删除许可内容。

## 模型、数据库访问与业务服务分层

- **按职责放置实现。** 数据库访问层负责连接、具体查询与条件更新、行映射、驱动差异及持久化适配；模型负责表字段映射、属性转换、关系、查询作用域和自身状态行为；服务负责业务规则与流程、跨对象协调、外部服务调用及业务层面的事务编排。沿用现有 Repository、Store、Provider、Actions、Manager、Server 等结构，按实际调用链判断职责，不凭目录名或类型名认定已经分层。
- **目录服从归属与需要。** 应用专用查询按需放在 `app/repositories/`，业务流程按需放在 `app/services/`；通用数据库机制与生成逻辑留在框架对应模块，扩展实现留在所属 crate，目录遵循[代码与测试目录](#代码与测试目录)。包内沿用现有模块布局，不为统一名称搬动公开类型，不新增空服务或只逐层转发的抽象。安装／发布命令生成的应用配置、路由与模型接入属于消费者产物，不能据此改变包源码归属或顺带提交安装残留。
- **保留 Active Record 契约。** 模型的查询、保存、删除、关系及单实体状态方法可以保留；服务可调用这些公开模型接口。不能仅凭 `query()`／`save()`／`revoke()`／通知能力入口判为职责混合，也不能为分层删除固定基线的模型方法。对需收敛的具体连接与查询实现、跨职责副作用编排，保留入口及覆写能力，将内部实现委托给已有存储模块或 Action／服务。固定上游明确放在模型 trait 中的自身行为可以保留，不因实现较长就强制增加服务层；通用 ORM 本身的查询构造与持久化实现属于数据库层，不按应用模型裁决。
- **映射与生成分开。** 表名与列名属于模型的数据库映射，生成区域统一位于对应模型文件顶部附近，与手写区域清楚区分并支持独立刷新；数据库结构读取、源码修改、生成锁与命令实现由框架负责，不写进应用模型。已有映射与生成规则见[模型字段记录](audits/model-fields/README.md)。
- **适配器保持边界。** 类型擦除、模型注册、实例转接与存储适配可以独立存在；区分真正的模型定义与 `*_model`／`*Record` 适配器。将凭据校验、状态生成／加密、持久化和业务事件串联的流程，不应隐蔽地堆在模型或注册适配文件中。模型文件中的监听器、数据库回读、批量导入和提交后调度，按实际职责拆到 Observer／存储／服务模块；单纯的文件组织改善与行为缺陷分别记录。
- **重构先保契约与一致性。** 保留公开导入路径、签名、模型覆写钩子、具名绑定及安装模板行为；必要时重导出原路径。不得因移动实现改变连接、表前缀、主键与邮箱等身份条件、受影响行语义、模型观察器、事件载荷与顺序、事务／保存点／行锁、提交后动作、幂等与失败状态，以及数据库失败时的内存状态。不要将分层整理与移动外部调用时机、缩短锁周期等行为优化混做一批。
- **核对与验收可追踪。** 核对生产模型、模型 trait、Record／注册适配器及直接服务消费者，为具体文件记录调用链、职责问题、建议归属、保留契约和后续验收；允许保留基线约定的模型行为，不以关键词零命中作为目标。实现调整后从公开入口验证成功和失败路径，按受影响范围实测 HTTP、Artisan、事务及相应数据库驱动，同步相关三语文档；仅规则／静态审查改动执行链接与差异检查，不把旧验收记作新代码已通过。参考[分层验收与复核记录](audits/model-layering/README.md)。

## 默认应用与扩展装配

- 默认 `app/providers/` 只登记应用自身必要的服务，不提前注册可选扩展、示例业务类型或包迁移；`#[cfg(feature = "…")]` 只控制编译，不能作为把示例写入默认骨架的理由。`bootstrap/providers.rs` 只列应用 Provider。
- 扩展通过已有 `[package.metadata.openrust.discovery]` 与 `openrust_providers()` 参与包发现，自身 Provider 负责服务绑定、配置合并及适用的迁移登记。需要发布或安装的应用配置／路由／模型由显式安装器按已确认契约生成；不为新扩展继续增加根 AppServiceProvider 分支。
- 应用包清单入口固定为 `bootstrap/packages.rs` 的 `pub(super) const fn manifest() -> PackageManifest`，`bootstrap/app.rs` 通过 `.withPackages(super::packages::manifest())` 装配。生成文件仅在 packages 模块的私有 compiled 子模块中引入，Rust 别名通过 `crate::bootstrap::packages::package_aliases` 按需访问，不在应用入口暴露生成常量，不手工维护扩展清单；`bootstrap/providers.rs` 继续只登记应用 Provider。保留现有 Cargo 编译期发现和框架 `withPackages(PackageManifest)` 契约，不为入口写法新增注册库、回调层或运行时扫描。
- 包默认配置和可发布模板放在所属包目录，由包 Provider 合并；默认根 `config/` 不预装可选包配置，不为可选包增加 feature 分支。根应用保留核心驱动连接配置，不因此装配可选服务端。显式安装通过现有发布与源码锁机制接入编译型配置，重复安装保留应用定制；OIDC 身份提供方等业务示例只在显式选用后生成。配置缓存命中时跳过包默认配置的环境读取与合并，以缓存快照为准。
- 业务示例、集成测试专用类型和装配放在文档或所属包的 tests／fixtures 中。用户应用实际采用某个业务组时，才在该应用的 Provider 中显式注册；框架仓库默认应用不承载所有扩展的演示接线。
- 验收同时检查启用／关闭扩展、包发现、注册与启动不访问未迁移数据库、迁移登记及自定义配置边界。运行 `cargo +1.95.0 test --test application_skeleton`，检查根应用 Provider／业务目录的扩展引用及根配置的可选包预装；配置验收同时覆盖包独立使用、应用覆盖、缓存快照及显式安装保留定制，阻止 Provider 再出现扩展引用或 feature 分支；该测试约束仓库默认骨架，不限制用户应用的正常定制。

## 旧版实现复用

1. **先定契约，再查旧版。** 实现前优先查阅同级 `openrust-v0.x` 工作树的 `v0.x` 分支。没有该工作树时，在当前仓库用 `git show v0.x:<仓库内路径>` 查阅。没有本地分支时，可用已有的 `git show origin/v0.x:<仓库内路径>`。两种方式均无需切换分支。记录对应源码、测试和修复的提交与路径，来源不可用时明确记录。
2. **按职责提取。** 可直接复用符合契约的内部实现、驱动适配和回归用例。旧版公开接口或目录与当前契约不一致时，提取有用的实现并接入当前模块。涉及依赖或跨组件调用时，核对许可证、Rust 版本、生命周期和安全边界。
3. **新主线按当前契约交付。** 每批只引入对应功能所需的代码和测试。旧 API、配置键、数据格式及迁移历史不作为兼容目标。与固定基线冲突的行为按当前契约修正，旧版缺口按依赖顺序补齐。
4. **用当前入口重新验收。** 复用旧测试时同步更新路径、接口和断言。以固定上游用例、当前应用入口及失败路径验证本批行为，分别记录复用范围、差异和实际验收结果。

## 文档规范

**文档语言范围。** `docs/` 当前只维护英文（`en`）、简体中文（`zh-Hans`）和繁體中文（`zh-Hant`）。待框架完整交付后，再评估是否将开发者文档扩展到 18 种语言。运行时翻译的语言范围见[请求与模板国际化](#请求与模板国际化)。

1. **章节对齐上游。** 按[固定 Laravel 文档基线](plans/laravel-rebuild-baseline.md#文档导航核对)组织章节和阅读顺序。英文、简体中文、繁體中文使用相同的章节相对路径和顺序。OpenRust 独有能力在导航中标为「扩展」。
2. **同一内容只维护一处。** 一个主题只有一个正文页面。其他章节用相对 Markdown 链接引用，确保在 GitHub 和部署到子目录的 VitePress 站点都能跳转。上游多个入口指向同一主题时，保留对应导航入口，共用正文。
3. **正文面向应用开发者。** `docs/` 介绍安装、配置、公开接口、用法、示例、错误行为及影响使用的支持限制。语言适配说明应解释调用方式、所有权或运行时约束。贡献指南可说明贡献流程。正文不放内部任务编号、交付批次、进度与待办、代理交接、源码对账、验收经过、测试计数、临时环境、清理记录及无关的性能免责声明；不以“本批完成”“后续单元交付”等过程用语描述功能。
4. **内部材料按职责归档。** 开发计划和待办放在 `.agents/project/plans/` 及相应计划文件，设计取舍放在对应架构或主题记录，验收环境、命令、结果和证据放在 `.agents/project/audits/` 对应主题目录。混合段落先提取开发者需要的操作和限制，仅将仍有效的计划、设计决定或待办并入既有对应主题。历史原文和差异由 Git 保存，不另存逐页副本、补丁、文件清单或可从提交重建的源码哈希。工作区临时备份不作为长期验收材料，也不逐批复制到审计目录；清理未跟踪补丁前，须逐项确认改动已提交、仍存在于工作区或已被现行实现取代，无法确认的独有改动继续保留并注明用途与清理条件。一次性整理只保留必要的范围、验证结果和来源提交号；仅在复现或独立审计确有需要且 Git 无法提供时保存额外证据。开发者正文不依赖 `.agents/project/`、代理指令或验收日志才能理解；文档站维护与验收命令见[维护指南](guides/documentation.md)。
5. **功能验收后同步正文。** 按 Laravel 对应章节介绍默认行为、配置和用法。Rust 示例与 Artisan 命令须实际验证。因 Rust 语言或运行时产生的差异须说明原因，并以测试验证等价行为。尚未提供的导航章节写明具体支持边界和已有原生入口，不使用空白占位，不把包骨架或仓库内部测试工具写成可用框架能力。发布说明只保留面向开发者的版本、兼容范围、变更及迁移影响，历史复验流水和待验矩阵归入内部记录。
6. **三语一起校验。** 同步更新三个语言版本的正文和导航，统一术语、标题层级与章节顺序。检查章节路径和内部链接，运行 `node docs/tests/check_content.mjs`、文档构建及现有浏览器验收。自动检查之外，逐段判断内容是否服务于应用开发者；站点命令见[维护指南](guides/documentation.md)。 导航浏览器检查从当前英文正文的支持状态声明计算期望数量，并核对三语一致，不以固定常量维护尚未提供功能的篇数。
7. **命令使用正式入口。** 面向开发者的源码命令统一使用 `./artisan`，部署后的命令使用 `./main artisan`，Windows 分别使用 `.\artisan.bat` 与 `.\main.exe artisan`。不得将 `target/debug/`、`target/release/` 或目标平台子目录中的二进制作为 Artisan 使用入口；构建与部署章节可以说明产物位置和复制操作。源码入口运行可选扩展时，须说明在应用 `Cargo.toml` 的 `[features].default` 中启用所需 feature，保留已有功能，避免只给出一次性的 `cargo build --features` 后又通过默认 Cargo 配置运行命令。现有内容检查和 `npm --prefix docs run build` 必须通过命令入口门禁。

## Docker 配置

镜像、构建及应用挂载变量保留已约定的 `APP_` 前缀（如 `APP_IMAGE_NAME`、`APP_IMAGE_VERSION`、`APP_STORAGE_PATH`、`APP_PUBLIC_PATH`、`APP_BUILD_FEATURES`、`APP_BUILD_JOBS`）；容器连接覆盖专用变量使用 `DOCKER_` 前缀（DOCKER_DB_HOST、DOCKER_DB_PORT、DOCKER_REDIS_HOST），不新增 `OPENRUST_` 别名；数据库、Redis及Nginx沿用所属服务的变量命名。

- Compose 只维护 `docker/docker-compose.yml`，默认启动应用与全部配套服务，需要部分服务时显式指定服务名，不新增dev／public覆盖文件。通用环境模板为根 `.env.example`，Docker专用配置参考集中在 `docker/.env.example`，按镜像／构建／挂载／容器连接／配套服务分组，文档说明将所需项合并至根.env；该参考模板不构成第二份运行配置。本地与部署均只加载各自的根 `.env`，不再创建或读取docker/.env。命令从根目录统一传`--env-file .env`，应用env_file固定为../.env，不增加启动包装器或额外运行依赖。宿主连接使用DB_HOST／DB_PORT／REDIS_HOST，容器可用DOCKER_DB_HOST／DOCKER_DB_PORT／DOCKER_REDIS_HOST覆盖；未设置时依次回退普通连接参数和postgres／5432／redis。MySQL须按实际驱动设置主机名及3306，不能把pgsql默认端口用于MySQL。显式environment覆盖env_file同名字段，插值保留Shell原生优先级。整合旧文件须迁移有效值、保留应用密钥、实际账号、容器命名及数据挂载；不得为配置整合清空数据。

容器统一使用 `${APP_NAME:-openrust}-服务名` 命名；应用宿主绑定复用 `APP_HOST`／`APP_PORT`，容器内部固定监听 `0.0.0.0:8000`；不再增加重复的绑定地址、端口变量或应用 profile。应用镜像为 `${APP_IMAGE_NAME:-openrust}:${APP_IMAGE_VERSION:-latest}`，名称使用合法的小写镜像仓库名；发布版本显式配置APP_IMAGE_VERSION，未配置时使用标准latest开发标签。Compose不解析Cargo.toml，应用自身版本仍按原有Cargo默认逻辑；不为自动同步镜像版本增加脚本，镜像名称与标签分别由APP_IMAGE_NAME和APP_IMAGE_VERSION配置。`REDIS_PORT` 同时控制 Redis 服务监听、宿主映射、健康检查和应用连接端口。应用等待配套服务健康后启动。Compose 变更须同步根环境模板、README、三语配置／部署正文、服务指南与当前交接；历史审计注明版本边界，不将旧结果写成新配置已验收。

本项目本地Compose数据库账号按用户要求统一为根 `.env` 的 `DB_USERNAME=root`、`DB_PASSWORD=root`。MySQL root使用镜像专用 `MYSQL_ROOT_PASSWORD` 初始化，不设置 `MYSQL_USER=root`；已有数据目录须通过SQL修改实际账号并验证，再更新容器环境，不能仅改.env后宣称账号已生效，不能清空数据目录重建。

Docker 方案调研区分开发环境与发布运行环境：Sail／Laradock用于核对服务装配和命名，不直接搬用PHP运行时、工具包装器或全套可选服务。优先复用原生Compose、BuildKit及现有Artisan入口；构建参数须确认Compose实际传入Dockerfile。反向代理请求大小与超时须和框架及流式／WebSocket行为一起核对，避免代理以更低默认值提前拒绝请求；发布迁移显式执行，镜像回滚不等于数据库回滚。

## 品牌表述

- **优先按职责表达。** 面向开发者的配置说明、命令帮助、日志、错误提示、注释、示例、生成模板和文档，减少 OpenRust、Laravel、Goravel 及其大小写、缩写、分隔符变体等不必要的品牌表述。直接说明功能、行为和约束；新增名称默认使用准确易懂的职责名称，例如文档端口使用 `DOCS_PORT`，不增加无必要的品牌前缀。缩写须结合用途判断，不能把通用术语误判为品牌。
- **保留身份、来源与契约。** 许可证、版权、来源、第三方声明，以及必要的项目身份、包名、crate 名、导入路径、仓库地址、外部协议、供应商和依赖名称保持准确。影响兼容性的公开名称、命令、配置键、事件字符串、序列化标识、缓存键及数据库内容不随文字清理改名；逐项或按同类契约列明位置与保留原因，确需修改时先列影响、迁移方案，等待用户确认。不得把必须随分发提供的许可或声明仅移入内部记录。
- **对齐机制不变。** 继续按固定上游基线验收目录、机制、装配及使用方式，公开 API 的命名遵循[移植原则](#laravel-到-rust-的移植原则)；中性化不触发接口迁移，不改变行为、默认值或数据格式，也不把来源品牌机械替换为项目品牌。
- **先清单再修改。** 扫描生产源码、应用骨架、生成模板、配置、脚本、测试和三语文档，结合实际用途列出文件位置、现有表述、中性建议、是否公开契约、兼容影响及修改或保留理由。先列与现行规则的冲突，再直接处理不影响契约的展示文案和私有命名；契约调整等待确认。根应用与生成项目同步核对。
- **验证实际消费者。** 检查受影响的命令帮助、错误输出、生成文件与文档展示，三语同步；再次扫描并区分已清理、必要保留、待确认和历史记录。关键词命中不是缺陷，零命中不是验收目标。代码注释和未国际化提示按下一节使用简体中文；已国际化的提示继续使用语言资源。
- **集中维护与保留历史。** 本节为唯一规则来源，通用代理入口只引用本节。调研、差异清单和验收记录归入 `.agents/project/`；历史证据保留原貌，不为去品牌改写来源事实。临时扫描、日志与构建产物按构建产物管理要求保存和清理。

## 代码注释与提示语言

- **注释优先简体中文。** 新增或修改的代码注释、Rust 文档注释及示例说明尽量使用简体中文，说明用途、原因和必要的约束，方便开发者阅读；接口名、类型名、配置键及必要的技术术语保留原名。
- **未国际化的提示优先简体中文。** 项目自行编写且未接入国际化的异常信息、错误提示、断言说明、命令行提示和日志中的自然语言说明，尽量使用简体中文，清楚说明问题及必要的处理办法。已接入国际化的内容继续使用翻译键和对应语言资源，不硬编码中文替代国际化。
- **保留机器契约。** 不翻译错误码、协议字段、结构化日志键、命令及机器可读输出；协议标准或兼容契约要求固定的文本保持原样。第三方原始错误保留诊断信息，必要时补充简体中文上下文。
- **随改动落实。** 开发和审查时同步检查受影响的注释与提示；既有英文内容在相关代码修改时逐步调整，更新依赖提示文本的测试与文档，不为统一语言扩大无关改动。

## 请求与模板国际化

- **运行时翻译范围。** 运行时翻译直接支持 18 种语言，由框架内置语言资源提供默认译文，应用可在 `lang/` 按需覆盖。语言标识与覆盖范围见[语言资源计划](plans/localization-18-locales.md#目标与边界)。
- **语言标识标准。** 用户于 2026-11-22 确认全项目迁移至 BCP 47，覆盖配置、公开接口、资源及文档目录／URL。该决定覆盖旧下划线约定；规范化不混同文字体系与地区，第三方原生标识仅在边界适配。实现与迁移按[统一迁移方案](audits/03-07/locale-bcp47-2026-11-22.md)执行，实际结果见[验收记录](audits/03-07/locale-bcp47-2026-11-22.md)。旧下划线公开输入显式报错；不默认保留目录副本、旧 URL 或运行时兼容别名。

- 标签规范化复用现有 ICU Locale／CLDR canonicalizer，保留地区、文字、变体及支持的扩展；不把 `zh-CN` 改为 `zh-Hans`。ICU Unicode Locale 未覆盖的 grandfathered、独立 private-use、extlang 形式须显式失败，不能静默截断。浏览器从可用语言候选中选择语言资源，显式文字体系优先，未知文字不按地区猜测。Faker、外部 API、原始 CLDR／许可数据仅在消费者边界保留原生标识，公开接口与输出使用 BCP 47。
- 语言资源、文档路径／URL、配置、事件、缓存及生成部署同时变更；旧新资源或 JSON 键冲突必须阻断并交人工核对，不能覆盖。升级前排空旧任务、停旧进程、备份、清缓存；数据脚本默认回滚，用户审阅后手动执行，不自动改开发／生产数据。

- 文档以默认配置和 `App::set_locale`／`current_locale`／`is_locale` 为主线；浏览器自动识别按下述用户确认的默认全局扩展提供，说明候选配置和关闭方法，其与固定 Laravel 默认栈的差异记录于内部审计。Rust 的异步、Result 和 JSON 语言文件差异须说明，不能以新增同名空入口冒充行为对齐。

- 用户于 2026-11-22 明确要求将整个语言中间件迁入框架并加入默认全局栈。浏览器语言选择、简繁体资源映射、请求语言设置和响应头统一由 `openrust::http::middleware::SetLocale` 提供，默认候选从应用翻译资源发现（2026-11-23 用户确认，覆盖早期固定三语列表）；应用不保留同名实现或手动追加注册。此决定覆盖先前“识别放在应用中间件”的约定，属于 OpenRust 对固定上游默认栈的显式扩展。应用通过 `Middleware::set_locale(&[...])` 覆盖候选，空列表关闭识别；2026-11-23 用户随后授权新增可选 `app.supported_locales`／`APP_SUPPORTED_LOCALES`，环境变量未设置时默认 "*"，自动发现框架与应用来源中的全部可用语言，列表限制候选，空列表停用。用户同日确认移除重复的 null 写法：显式 null／(null) 环境值和直接 JSON null 配置报错；框架配置缺键时仍走默认发现。见[语言候选配置收口](audits/03-07/supported-locales-wildcard-2026-11-23.md)。使用既有 `App::set_locale` 和请求作用域，不为单页重复协商或引入共享可变全局语言。
- 迁移默认能力时只移除应用中的重复实现和注册，保留应用模块入口及空配置闭包，如 `app/http/middleware/mod.rs`、`app/http/mod.rs` 的模块声明和 `bootstrap/app.rs` 的 `withMiddleware`；逐项对照迁移前骨架，不因当前为空而删除开发者的扩展位置。同步核对安装器、测试和三语正文中的旧引用。
- 请求头语言解析、权重排序及通用候选匹配由框架 `Request::get_languages`／`get_preferred_language` 提供；默认 `SetLocale` 为配置头复用同一解析器并从配置或发现的语言候选中选择资源；标准接口始终描述 Accept-Language，业务与页面读取当前应用语言统一使用 App::current_locale()；配置类仅保存该应用的中间件实例与候选，不重复实现匹配。语言标签沿用 BCP 47，严格请求头过滤及与固定上游的差异须在主题记录和三语正文中说明。
- 自定义语言规则通过 `SetLocale::locale_using` 及同名中间件配置入口按实例保存同步回调，返回 `Some` 时严格验证 BCP 47 及候选精确成员，`None` 依次尝试配置的 URL 参数、安全 Cookie 偏好及语言请求头协商，错误交现有异常处理。候选与回调独立更新，非法候选不破坏旧设置；空候选停用整个实例且保留回调。默认实例在路由管线的 Cookie 解密／队列之后自动装配（普通 Web Session 之前）；有状态 API 在其安全包装器内执行。依赖 Session／认证时关闭默认识别，并将同一个中间件放到依赖之后；不能以回调代替执行顺序。响应继续保留已有语言／缓存头；`Vary: Accept-Language` 不代表 Cookie、用户资料或其他自定义来源已完成缓存隔离，应用须提供相应 Vary 与私有缓存策略。不引入探测器框架或共享可变全局状态。
- 默认 URL 语言选择由同一个 `SetLocale` 在回调之后、安全 Cookie 偏好之前处理，仅使用 `Request::query` 和既有 ICU 规范化；显式值须精确属于候选，空值、非法、非标量或不支持的值返回400。`app.locale_query_parameter` 缺键默认 `locale`、JSON null仅关闭query，名称须为可往返解析的非空顶层键；保留已有 APP_LOCALE_QUERY_PARAMETER 覆盖，不再新增同义配置入口。重复标量沿用既有解析器的后值覆盖前值规则。空候选关闭所有来源。欢迎页只消费请求的 `LocaleSelection` 显示元信息，安全 Cookie 管线中使用 CSRF POST 保存／删除偏好；无安全管线时复用 `Arr` 编码生成单次 GET 链接。回调已决定语言或无可用候选时隐藏无效控件，不再次选择语言。
- `app.locale_header` 缺键默认 Accept-Language，null 只关闭请求头识别，其他值按 HTTP 头名校验；回调 Some → URL → 安全 Cookie 偏好 → 配置头 → 既有兜底，空候选仍停用整个实例。Request 标准语言 API 始终读取 Accept-Language；自定义头复用既有解析器且不得混用缓存。Vary 跟随启用的实际头名，保留已有项和通配符；不把语言头的 Vary 当作用户私有内容的完整缓存隔离。配置读取仓储及缓存快照，保留 APP_LOCALE_HEADER 环境覆盖，不新增同义 Builder 或配置文件；环境字符串 null 不等于 JSON null。停用 SetLocale 后配置不会独立选择语言。这些默认选择配置属于 OpenRust 扩展。
- **语言默认名称。** 2026-11-23 用户确认查询参数及偏好 Cookie 的默认名称统一为 `locale`，覆盖此前 `lang` 默认约定；应用配置和框架缺键回退须一致。保存入口保持 `POST /locale`／`store_locale`，表单字段 `locale`。既有配置键、APP_LOCALE_COOKIE／QUERY_PARAMETER／HEADER、自定义名称与 null 关闭语义保留；请求头仍默认 Accept-Language。不自动读取／迁移旧 lang Cookie 或参数，不双写；升级重新选择语言、更新书签并重建配置缓存，需要旧名称的应用显式配置 lang。资源 lang/、HTML lang 和第三方协议不变，历史验收保留当时边界。
- **语言偏好表单字段。** `app.locale_form_field` 由 `APP_LOCALE_FORM_FIELD` 覆盖；欢迎页直接使用 `config('app.locale_form_field')`，保存入口使用 `Config::string("app.locale_form_field")`，不另设兜底。默认locale只在应用配置定义；保存入口对缺键、null及非字符串报错，字符串原样保留。使用非空顶层字段名，避免与redirect、_token、_method冲突。修改后重建配置缓存；名称独立于Cookie／查询参数。不增加专用取值包装或重复字段名配置校验，输入、语言候选、Cookie及CSRF安全约束复用既有机制。
- **自动与固定偏好。** 2026-11-23 用户确认覆盖早期“不保存偏好”规则。自动协商与 GET／URL 覆盖不写偏好；显式安全写请求经现有 CSRF、Cookie 队列和加密保存，恢复自动删除。`app.locale_cookie` 缺键默认 `locale`，null 关闭；保留应用已有 APP_LOCALE_COOKIE 名称覆盖。Cookie 寿命及属性复用现有机制，失效／损坏／候选移除时恢复自动，不能信任原始或加密豁免 Cookie。当前应用语言与有效固定偏好分开提供；普通 API 只用显式来源，不默认启用 Session、数据库或 Cookie。安全 Cookie 参与页面选择时合并 Cookie Vary 与 private,no-store，路由缓存不得重新公开。默认实例在 Web 解密／队列之后执行一次，保留事件与请求隔离；依赖 Session／认证的规则显式放在依赖之后，不用重复切换弥补顺序。

- **视图读取。** 需要已支持的请求信息和应用配置时，优先使用 Blade 的 `config()`、`request()->…`、`app()->…` 助手；框架包元信息仍用已有常量，不为调用风格新增无必要的访问方法，不为这些值增加重复控制器传参。请求助手复用真实请求的异步渲染桥接及渲染树作用域，禁止引入跨请求可变全局请求对象；保留应用必须提供的业务数据和校验结果，不在模板中写入偏好或变更配置。 欢迎页配置读取不重复指定默认值，统一由配置文件定义默认值。 Blade 的 app()／app(service, parameters) 复用当前应用及命名容器；可调用服务通过 ViewObject 与既有类型投影／绑定接入，通用成员调用不得逐服务堆解析器白名单。运行期对象不能持久化为模板缓存，保留请求／应用隔离；未声明的 Rust 方法不包装成自动反射已支持。
- Blade 文案直接使用 `__`、`trans` 或 `trans_choice`，控制器只准备页面数据与显示元信息，不逐条翻译再传值。框架渲染跨线程时须传递并隔离语言作用域；验收覆盖缓存模板、子模板、组件和并发不同语言请求。
- 页面不得通过某个词条是否存在来推断整页语言，也不在控制器中重写译器的回退规则。HTML 语言元信息使用应用当前语言，文案通过语言资源逐键翻译与配置回退。欢迎页介绍使用 `:name` 占位符，由视图从 `config('app.name')` 传入，不在译文中写死应用名称。欢迎页仓库地址来自框架 `Application::REPOSITORY`（框架 Cargo 元信息），欢迎页文档链接在视图中通过 `__('welcome.documentation_locale')` 获取文档语言目录，不在模板写死语言列表。当前语言缺少此键时使用 en，不借用文案回退语言的文档目录。该资源键仅表示现有文档的语言标识：随附资源中 en／zh-Hans／zh-Hant 指向对应文档，其余语言指向 en；新增对应文档后可在该语言的应用 `welcome.json` 中覆盖此键。仓库地址及章节相对路径仍由视图统一组装，语言资源不保存完整 URL；应用当前语言、翻译回退和响应语言不受影响。核心译器不感知具体页面或文档目录。

- **语言候选发现（2026-11-23）**：默认译文位于框架 localization/lang 并编入产物；应用lang保留en／zh-Hans／zh-Hant三份可编辑欢迎页，其他词典只在需要覆盖时创建。APP_SUPPORTED_LOCALES默认"*"，由get_supported_locales读取并解析，显式null报错；Provider先加载默认值、再按键递归合并应用覆盖，原句JSON按顶层键覆盖；应用lang只放自定义内容。默认候选由 FileLoader::available_locales 在 HTTP Provider 引导后发现一次，合并框架内置语言及实际应用语言根、add_path与add_json_path。规范标签、分组或顶层 JSON、稳定排序去重；忽略包命名空间、vendor、隐藏项、符号链接与空语言目录。显式 set_locale（含空列表）优先，其次 app.supported_locales 配置列表，否则自动发现；非文件来源用列表配置或显式候选。不逐请求扫描、不新增语言管理器；APP_SUPPORTED_LOCALES 复用现有配置与缓存生命周期。控制器传 LocaleSelection 候选，模板遍历，不再写死三语。母语名称仅查精确语言，缺少显示代码；languages.direction 的 rtl 只负责页面方向。翻译完整性及文档语言仍独立处理。

## 错误转换与传播

- 先确认实际来源类型、接收边界与原有分类；重复、确定且无须运行时上下文的转换由目标错误提供具体 `From`，调用方优先使用 `?`。复用现有转换，禁止覆盖任意错误的泛型实现或另建万能错误体系。
- 底层继续返回领域错误，HTTP 转换归 HTTP 边界；检查依赖方向、类型推断、trait 冲突与公开契约。问号不自动串联多层转换；闭包标明结果类型，尾表达式按需用 `Ok(operation()?)` 或具体转换。
- 保留路径／操作／请求／阶段上下文、状态码区分、恢复、重试、日志及脱敏的映射；不得把结构化错误提前字符串化。转换应保留原始错误与 `source` 链；强制 `Internal` 与已有专用 HTTP 转换不能机械互换。
- 每类验证公开消费者的成功／失败、错误分类与原始来源，HTTP 另核对状态、响应与敏感信息保护；同步扩展、测试、生成器模板与三语公开示例。扫描数量和编译通过不代替行为验收。

- **Rust 代码。** 在仓库根目录使用最低支持工具链 Rust 1.95.0 运行 `cargo +1.95.0 fmt --all --check` 和 `cargo +1.95.0 clippy --workspace --all-targets --locked -- -D warnings`。按改动验证实际入口、默认行为和关键失败路径。骨架改动验证公开导入和签名编译，分别记录骨架、实现与行为验收状态。

### 构建产物管理

- **临时产物位置。** 本项目临时目录、隔离源码快照、验收日志、测试临时文件及编译构建产物统一存放于项目根 `target/tmp/`（已由Git忽略）下，按工作流建立子目录；不得在 `/tmp`、`/private/tmp`、用户目录其他位置或其他项目中创建。为测试、构建、安装器及其子进程设置项目内 `TMPDIR` 和独占 `CARGO_TARGET_DIR`，避免默认临时路径绕过此规则。既有外部工作目录在占用进程安全退出并核对归属后同盘迁入，保留源码、日志、锁文件与缓存，不复制整份target，不以外部软链继续写入。历史审计中的旧绝对路径只代表当时证据位置，迁移后由当前交接记录新位置。移动目录本身不会释放磁盘空间；32GB停线清理规则仍独立执行。
- **源码快照完整性。** 优先用 Git 归档建立验收快照；复制生成应用时只排除根目录的运行产物，不按 `storage`、`tmp` 等名称递归过滤，否则会丢失包内同名源码。同步修改后核对内容，并让文件时间反映本次写入；不得因保留较早时间戳而误用 Cargo 旧产物。
- **嵌套临时目录保护。** `target/tmp/` 同时保存隔离源码、验收日志和独立交付文件，不得将根 `target/` 整体删除，也不得对根 target 直接执行无范围的 `cargo clean`。清理时只处理核对归属且已闲置、取得锁的编译子目录（如根 `target/debug`、`target/release`、平台产物及 `target/tmp/` 各工作流中的独占构建目录），保留源码、日志、依赖下载、交付文件及锁文件原 inode。迁移根 `tmp/` 前须等待占用进程退出并更新调用方路径，同盘 rename，不复制缓存、不以兼容软链继续写旧路径。应用自身的运行期目录与锁文件契约不因仓库验收目录迁移而改名。
- 日常开发沿用 Cargo 原生增量编译和并发策略，保留 IDE 的调试能力及热缓存。不得仅为减少磁盘占用而全局关闭增量、固定低并发或强制所有任务串行；确有资源压力时，只对当前受影响命令按需设置，记录原因。不新增工具链文件或改变 Cargo.toml 的 rust-version。
- 源码验收仍使用独立快照，构建缓存按工作流复用：同一工作流复用已登记的独占 CARGO_TARGET_DIR，并沿用 Cargo 自身的缓存与锁；不同工作流核对归属和占用，避免每批复制一份完整 target。一个任务完成不代表其缓存已废弃，不要求下一批从零构建。一次性复现或发布验收需要干净构建时，明确理由后单独进行。
- 新大型构建前及验收阶段边界检查 df，并盘点根 target 与本项目临时构建目录的归属、用途和占用。可用空间小于或等于32 GB（31,250,000 KiB）时停止新增构建，自动清理本项目全部编译产物，无需再次确认清理；范围包括根及项目隔离验收目录中的Cargo target（含增量／依赖编译缓存）、文档构建dist／cache，不因仍可复用而保留。先通知协作者暂停相关构建，等待当前构建安全退出，核对目录归属与进程占用，取得Cargo排他锁后清理并保留锁文件原inode；无法安全取得锁时先报告阻塞，不带锁外删除。保留源码、未提交改动、验收日志、依赖下载缓存、独立交付文件、数据库及全部数据卷，不删除其他项目产物。清理前后记录df实测GB／GiB及净释放量，空间仍不足则保持停线；恢复执行遵循当前交接及用户暂停指令。未触及停线时继续复用缓存，只回收确认废弃且闲置的产物，不每批清空；根缓存达到8 GiB本身不构成清理理由。
- 代理构建与验收命令统一通过 `python3 -B tests/build_guard.py --workflow <工作流> -- <命令>` 执行。已有缓存用 `--target-dir` 指定项目内独占目录；需要短临时路径时用 `--tmp-dir`。守卫向子进程传递项目内 `TMPDIR`、`CARGO_TARGET_DIR` 与 `RUSTUP_TOOLCHAIN=1.95.0`，在启动前、运行中及退出后检查磁盘。触线时安全停止自己的进程组，核对协作构建、持有全部 Cargo profile 锁后清理；其他构建占用时保留产物并报告，不能直接删除。运行中触线返回75，清理完成后由代理继续原命令；成功或失败退出后的触线清理保留原退出码。记录位于 `target/tmp/build-guard-events.jsonl`。原生 Windows 使用 `py -3 -B tests/build_guard.py --workflow <工作流> -- <命令>`，同时设置 `TMP` 和 `TEMP`，通过 Windows Job Object 管理验收进程树，并用与 Cargo 兼容的 Windows 文件锁保护清理。Windows 的进程清单无法可靠提供工作目录，因此遇到可能仍在运行的 Rust 或文档构建会停止清理。守卫不修改增量与并发，不会拦截绕过入口直接启动的 Cargo，仍须执行上述阶段边界检查。
- 成功、失败、取消及崩溃后的下一轮都要核对临时资源；区分可复用缓存和废弃产物，不将“退出即删所有target”作为统一策略。实际清理前确认所属任务结束、无进程占用；必要时使用 Cargo 原生清理命令并指定已废弃目录。手工清理根debug缓存还须取得其 .cargo-lock 排他锁，持锁保留锁文件本身，避免其他 Cargo 通过重建锁文件进入。记录真实回收量，不能只报告 du 逻辑总量。

### 日常数据库与缓存验收

2026-11-21 用户将日常开发与验收调整为 PostgreSQL 18、MySQL 8、SQLite 三库，以及 Redis、database、file 三种缓存驱动，覆盖此前仅 PostgreSQL 或仅 MySQL 的日常验收规则。数据库其他版本、SQL Server 和商业嵌入端点仍按发布矩阵验证。仓库不通过工具链文件固定版本；保留 `Cargo.toml` 的 `rust-version` 声明最低版本，日常验收显式使用 `cargo +1.95.0`。通过验收环境分别选择数据库与缓存驱动；本地 `.env` 的默认连接不代表完整验收范围，也不要求切换或搬迁已有开发数据。

临时数据库验收使用 `python3 -B tests/postgres_acceptance.py -- <验收命令>`，本地 Docker 须已有 `postgres:18`。入口核对镜像数据目录 `/var/lib/postgresql`（包含 18 的版本化 PGDATA），以 1 GiB tmpfs 承载数据，使用随机回环端口、临时凭据和批次标签。通过同一账号／数据库的 `SHOW server_version_num` 确认 18.x 后，向命令提供 `OPENRUST_TEST_POSTGRES_URL`、`OPENRUST_REQUIRE_POSTGRES=1` 和 `OPENRUST_ACCEPTANCE_POSTGRES_CONTAINER`。不把开发库连接传给会建表／删表的测试。

现有定向测试读取各自的 URL／REQUIRE 变量，调用时显式映射并精确筛选；未适配 PostgreSQL 的 MySQL 专项不能只改变量后声称通过，也不能将缺变量导致的跳过计作成功。例如：

```sh
python3 -B tests/postgres_acceptance.py -- sh -c '
  export OPENRUST_TEST_POSTGRES_JSON_URL="$OPENRUST_TEST_POSTGRES_URL"
  export OPENRUST_REQUIRE_POSTGRES_JSON=1
  cargo +1.95.0 test --locked -p openrust-framework --test database_query \
    json_predicates_run_on_postgres_in_both_prepare_modes -- --exact
'
```

MySQL 日常验收使用 `python3 -B tests/mysql_acceptance.py -- <验收命令>`，现有夹具核对 MySQL 8.4，属于 MySQL 8 验收范围。SQLite 使用独立临时数据库文件或适合测试生命周期的内存数据库，记录实际版本；不复用开发数据库文件。三库分别运行同一受影响行为的用例，连接变量按各测试实际读取的名称映射。

同批并行测试也必须隔离数据库对象；不能因为容器独占就让多个用例互删同名表。MySQL 优先复用 `TestApp::mysql` 的独立数据库与归属校验，确保 Artisan 子进程和验证连接共用各自夹具的 URL。异步用例须等待夹具关闭并核对数据库已回收；不得用全局串行化掩盖冲突，缺少必需连接变量时应失败，不能提前返回计为通过。

代理验收的 Cargo 仍在独立源码快照与按工作流复用的独占 target 中运行，不在活跃工作树编译变动源码；增量与并发按上述构建产物管理执行，不强制每批冷构建。保留32 GB磁盘停线与安全清理规则。会在内部运行 Cargo 的安装器、生成应用和验收夹具，须向子进程传递 `RUSTUP_TOOLCHAIN=1.95.0` 并核对实际工具链；仅给外层 Cargo 加 `+1.95.0` 不能保证内层构建使用相同版本。用 `-p`、`--test` 和 `--exact` 定位函数，显式核对每项测试及辅助夹具连接的驱动，分批执行以控制资源；不依赖无筛选 workspace 测试偶然覆盖三库。

缓存共享行为分别通过 Redis、database、file 实际驱动验证，按改动覆盖读写、过期、删除及锁等相关路径。Redis 使用专属隔离实例，先核对 `INFO server` 为 8.x 与 `PING`；不在开发 Redis 执行清库或修改 ACL。database 缓存使用对应三库的隔离数据库／表，file 缓存使用批次专属临时目录；不对开发缓存执行清空操作。仅影响某一驱动的变更可定向验收，但须说明范围，不能计为其他驱动已通过。

入口完成、失败或收到可捕获取消信号后只回收当次标签容器，不删除数据卷。生命周期回归运行 `python3 -B tests/postgres_acceptance_lifecycle.py -v`。强制杀死或 Docker 不可用时按日志批次标签复核收尾。MySQL 夹具及其生命周期测试同样用于日常验收。不删除开发数据库、开发缓存或数据卷；仅清理本批独占的 SQLite 文件和 file 缓存临时目录。
