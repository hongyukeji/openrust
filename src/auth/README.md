# Authentication and authorization

Authentication and authorization capabilities for [OpenRust](https://github.com/hongyukeji/openrust).

## Current surface

- `AuthPlugin::new()` registers the database authenticator and shared refresh-token service. It requires `DatabasePlugin`, PostgreSQL or MySQL, and the tables created by `AuthMigration`; refresh-token use also requires `AuthRefreshTokenMigration`.
- `SessionPlugin::new()` installs the shared database Session middleware. Register it with `DatabasePlugin` before `AuthPlugin`; custom stores can implement `tower_sessions::SessionStore` and use `SessionPlugin::with_store`.
- `AuthPlugin` registers `RefreshTokens` when `DatabasePlugin` has already registered `Db`. `RefreshTokens` creates high-entropy opaque credentials, persists only SHA-256 hashes, rotates atomically, revokes a token family on replay, and supports account-wide revocation. The caller supplies the initial family expiry; rotation never extends it.
- `openrust new --db postgres|mysql --auth` generates the JWT/Auth/AuthFlows plugins, auth migrations, JWT-protected `/api/me`, database-backed PAT-protected `/api/me/pat`, registration/email verification/login/refresh/logout/password-reset routes, and `[auth.jwt]` config; the signing key must be supplied via `APP_AUTH__JWT__KEYS__LOCAL` rather than embedded in generated config.
- `AuthPlugin::with_authenticator` registers an application or third-party `Authenticator` implementation through the existing `Plugin` lifecycle.
- `AuthPlugin` also registers the Argon2id `Passwords` service in `AppState`. It hashes with a random salt into PHC format and verifies on Tokio's blocking pool. Configure it with `AuthPlugin::new().with_password_config(PasswordConfig { memory_kib: 19456, iterations: 2, parallelism: 1 })`; defaults are 19456 KiB, 2 iterations and 1 lane, with bounded accepted ranges. Encoded algorithm, version and cost parameters are checked before verification to reject unsafe stored values. `EncodedPasswordHash::as_str()` is the persistence boundary; the wrapper intentionally has no `Debug` implementation. Empty and over-1024-byte passwords are rejected, mismatches return `Ok(false)`, and malformed stored PHC data is an internal error.
- With `DatabasePlugin`, `AuthPlugin` registers `VerificationCodes` using the shared database store and the same Argon2id password hasher. Add `AuthVerificationCodeMigration` to the application migrator before issuing codes. The default policy issues six digits for ten minutes, allows five incorrect attempts, and enforces a 60-second resend cooldown. The returned `IssuedVerificationCode` is redacted in `Debug`; send its code through Mail/SMS yourself and never log it. Apply the shared `RateLimiter` before issue/verify endpoints, using an endpoint and request-source key as well as any identity-specific policy.
- `AuthFlowsPlugin` registers `AuthFlows` after `DatabasePlugin`, `AuthPlugin`, and `JwtPlugin`. It composes account registration, email verification, login, refresh, logout, password-reset requests and password replacement; it does not define HTTP routes or send mail/SMS. The default refresh family lasts 30 days and the default shared fixed-window limit is five requests per endpoint/source/identity per 15 minutes. Pass a trusted request-source value (for example, the socket peer address or a value derived only from explicitly trusted proxies); never trust arbitrary forwarding headers.
- JWT login remains the default. Applications opting into Cookie Session login can call `AuthFlows::login_session`, which verifies credentials under the shared login limit, rotates the Session ID, stores the account ID and only a SHA-256 CSRF digest, and returns a redacted `SessionCredentials` value. Return its CSRF token to the client in the application response. Protect logout with `AuthMode::Session` and call `AuthFlows::logout_session`; it removes auth keys, rotates the ID, and preserves app-owned Session data. Both paths require `SessionPlugin`.
- `AuthFlows::register`, `request_email_verification`, and `request_password_reset` return optional `IssuedVerificationCode` values; the wrapper redacts its code in `Debug`. Duplicate registration returns `None` only for an email unique-constraint conflict; unrelated database errors propagate. `verify_email` and `reset_password` return a boolean for invalid/expired challenges. Handlers can keep public responses uniform while sending a code only when one is present. `login` returns the same unauthorized error for unknown, unverified, disabled, or wrong-password accounts. Successful login/refresh returns an `AuthCredentials` value whose `Debug` output redacts both bearer credentials. Handlers own DTOs, response shape, route authorization and delivery.

The `--auth` generated routes accept JSON with these fields: `/auth/register` and `/auth/login` use `email` + `password`; `/auth/request-email-verification` and `/auth/password-reset` use `email`; `/auth/verify-email` uses `email` + `code`; `/auth/refresh` and `/auth/logout` use `refresh_token`; `/auth/password-reset/confirm` uses `email`, `code`, and `new_password`. Credential responses expose access and refresh tokens once in the JSON response envelope. Rate-limit source keys use the public HTTP `ClientIp` extractor: the TCP peer is authoritative by default, and `X-Forwarded-For` is honored only when that peer matches `[server].trusted_proxy_ranges`.
- `JwtPlugin` validates an explicit key ring at startup, and `JwtTokens` signs/verifies short-lived HS256 access tokens. `AuthLayer` supports `AuthMode::Jwt` without Session middleware; `SessionOrToken` continues to interpret Bearer credentials as PATs.
- `CurrentUser` and `OptionalUser` extract the verified account identity. They expose the account ID, source, and PAT abilities; application handlers load their own business user model by ID.
- PAT database authentication checks revocation, expiry and account disablement on each request and updates PAT `last_used_at`; a committed change is visible to the next request on every node using the same database. Cookie Session authentication uses the shared Session runtime defined in [ADR-017](../../.agents/project/decisions/adr-017-generic-session-runtime.md).
- `PersonalAccessTokens` exposes account-scoped issue/list/revoke operations. The 256-bit bearer value is returned once, while only its SHA-256 digest and short prefix are stored. Listing excludes secrets; revocation is scoped by account and immediately shared by database-backed authenticators.
- `Policy` provides exact, database-backed role permissions. `ensure_role`, `assign_role`, `grant_permission`, and their revoke counterparts manage global role assignments. `allows` / `authorize` read the shared database every time; JWT and Session need a granted role permission, while PAT also needs the same exact token ability. Unknown permissions deny by default, and committed revocations are visible on the next check across nodes.

```rust,ignore
use openrust::auth::{AuthLayer, AuthMode, AuthPlugin, CurrentUser, SessionPlugin};

app.plugin(SessionPlugin::new())
    .plugin(AuthPlugin::new())
    .routes(|routes| {
        routes.get("/api/me", me).layer(AuthLayer::required(AuthMode::SessionOrToken))
    });

async fn me(user: CurrentUser) -> openrust::Result<openrust::http::Json<i64>> {
    Ok(openrust::http::Json(user.id()))
}
```

The application migrator must include `AuthMigration` once, `AuthRefreshTokenMigration` when refresh tokens are used, `AuthVerificationCodeMigration` when verification codes are used, and `AuthPolicyMigration` when Policy is used. The `--auth` project template registers these auth migrations plus `DatabaseRateLimitMigration`. By default these migrations create neutral `tb_users`, `tb_sessions`, `tb_personal_access_tokens`, `tb_auth_refresh_tokens`, `tb_verification_codes`, `tb_roles`, `tb_permissions`, `tb_user_roles`, and `tb_role_permissions` tables; `DatabaseConfig.table_prefix` and `table_names` can select other validated physical names, and authentication/authorization queries use the same resolver. Application-specific user columns and domain data remain application-owned. PATs, refresh credentials, and Cookie Session IDs are stored as SHA-256 hashes; generic Session data is stored in the shared Session record. Verification rows contain a purpose/identity digest and an Argon2id code hash, not the raw identity or code. The digest is pseudonymization, not encryption or protection from guessing low-entropy identities. Unsafe Session requests require a matching `x-csrf-token`; invalid selected credentials never become anonymous access.

`VerificationCodes::issue(purpose, normalized_identity, policy)` returns a numeric code without sending it. Purpose and exact identity must match on verify; the caller is responsible for normalizing values consistently. Only one active code exists per purpose/identity, and a successful verification consumes it atomically across nodes. Wrong formats and codes consume the bounded attempt budget; missing, expired, consumed, exhausted, stale and mismatching challenges all return `Ok(false)`. Reissue before cooldown expiry returns 429 with `Retry-After`. Custom storage can implement `VerificationCodeStore`; it must provide atomic cooldown, attempt and single-consumption semantics. See [ADR-026](../../.agents/project/decisions/adr-026-generic-verification-codes.md).

The service layer does not make verification-code consumption and account updates one database transaction: a code is consumed before the account mutation. If a later write fails, the caller must permit a fresh code request. Password replacement and refresh-family revocation share one database transaction. Logout revokes refresh credentials while already-issued access tokens remain valid until their short TTL expires. Generated routes use the public `ClientIp` extractor: the socket peer is authoritative by default, and `X-Forwarded-For` is honored only when the peer matches a configured `[server].trusted_proxy_ranges` entry. Configure those ranges to match the actual reverse-proxy hops.

`AuthCredential` intentionally does not implement `Debug` or serialization. Custom authenticators must not log its secret. Return `Error::Unauthorized` for invalid credentials, `Error::Forbidden` for CSRF denial, and an internal or explicit 5xx error for backend failures.

The generic Session store, Cookie middleware, expiry, deletion and shared invalidation are implemented and tested against PostgreSQL/MySQL. JWT access-token signing, strict validation, key IDs, overlapping-key rotation, and JWT route authentication are implemented. Refresh-token hash persistence, single-use rotation, replay-family revocation, account-wide revocation, and concurrent refresh serialization are implemented and tested against PostgreSQL/MySQL. The Argon2id password primitive, generic verification-code service, `AuthFlows` service composition, and basic database-backed role permissions are implemented and tested on PostgreSQL/MySQL. Session login/logout helpers have a unit test for ID cycling, CSRF digest storage, redaction, app-data retention and auth-key removal; their PostgreSQL/MySQL database integration is pending. Generated auth routes include an isolated-database/fake-mail HTTP integration test; the complete TCP flow passed on MySQL 8.4.11. Application handlers still own domain DTOs and route authorization.
